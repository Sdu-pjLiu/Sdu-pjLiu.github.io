测试框架学习-Python自检与面试

发表于 2026-07-31 更新于 2026-08-20 分类于 计算机
Python 测试工具链自检与面试导向问答；覆盖 pytest、覆盖率、mock 与 Hypothesis。

完成 软件测试基础 与 Python 测试工具链 后，重点不是背装饰器名，而是能讲清用例设计、资源生命周期、隔离边界与覆盖率含义。本篇用自检题查漏补缺，再用公开面经中的高频追问训练工程表达。

0. 使用说明

建议先遮住「推荐回答」，在 60～120 秒内口述：

  1. 先给结论，再讲机制（fixture 作用域、patch 路径、性质定义）。
  2. 点出失败模式：状态污染、假高覆盖率、过度 mock。
  3. 补充你会怎么落地（conftest、依赖注入、fail_under、@example）。
  4. 若只能说出 API 名，说不出何时不用，视为尚未掌握。

1. 学习自检

1.1 发现规则、布局与独立性

S1. pytest 默认如何发现测试？类上写 __init__ 会怎样？

推荐回答： 默认收集 test_*.py / *_test.py 中的 test_* 函数，以及无 __init__ 的 Test* 类中的 test_* 方法。测试类若定义 __init__，该类下用例通常不会被收集。命名或布局不符合约定时，表现为「用例消失」而非报错，排障应先看收集列表（如 pytest --collect-only）。

S2. 为什么强调用例独立，而不是靠固定执行顺序串业务流程？

推荐回答： 收集顺序、并行（xdist）、单测筛选都会打乱顺序；顺序耦合会导致偶发红与不可单独复现。流程依赖应下沉为 fixture 依赖链（如 token → product → order），由 pytest 保证准备顺序，并用 teardown 清理，而不是 test_a 写库、test_b 默认读到同一状态。

S3. conftest.py 解决什么问题？为什么通常不用显式 import？

推荐回答： 放置同目录及子目录共享的 fixture、hook 与本地插件注册；pytest 自动加载，避免每个测试文件重复 import 与循环依赖。它不是业务包的一部分，而是测试支撑面。全局过重的 session 资源仍要谨慎，避免隐式耦合。

1.2 Fixture、参数化与 Mark

S4. fixture 四种常见 scope 如何选型？举一正一反例。

推荐回答： function 默认，适合临时目录、易变数据；class/module 适合昂贵但只读的准备；session 适合进程级连接或全局配置。正例：DB 引擎 session 建一次，每用例用 function 级事务回滚。反例：session 返回可变列表且无重置，导致用例间污染。

S5. 为什么推荐 yield fixture？失败时 teardown 还会跑吗？

推荐回答： yield 前 setup、后 teardown，把生命周期写在同一处；用例失败时 teardown 仍会执行，降低泄漏连接、临时文件的概率。若只在测试末尾手写清理，断言失败可能跳过清理。

S6. @pytest.mark.parametrize 的工程价值是什么？如何避免组合爆炸？

推荐回答： 同一断言逻辑覆盖多组输入，数据与逻辑分离，报告中可按参数行定位。应先覆盖等价类与边界（空、零、负数、非法），再用 pytest.param(..., marks=...) 处理个别跳过；不要无脑笛卡尔积。可读性可用 ids= 改善。

S7. skip、xfail、自定义 mark 各解决什么？

推荐回答： skip 明确不跑（缺环境）；xfail 记录已知失败，修复后应变绿或调整；自定义 mark（如 slow）配合 -m 做分层回归。mark 应在配置中注册，避免拼写静默失效。

1.3 覆盖率

S8. 行覆盖率 90% 能否说明质量够好？你会怎么向面试官解释？

推荐回答： 不能。覆盖率只说明代码被执行过，不说明断言有效、并发正确或真实依赖行为正确。假高覆盖常见于「调用但不断言」或只测 happy path。工程上用 term-missing 补关键分支，设合理 fail_under 防回退，并强调错误路径与合同断言。

S9. 配置 source / omit 的目的是什么？

推荐回答： 把统计收窄到业务包，排除测试、venv、生成代码，避免数字被噪音稀释或虚高。本地与 CI 配置应一致，否则门槛行为不一致。

1.4 Mock

S10. patch 应该打在定义处还是使用处？为什么？

推荐回答： 通常打在 被测模块已绑定的名字（使用处导入后的命名空间）。若 service.py 写了 from api import fetch，应 patch service.fetch。打错路径会导致真实调用仍发生或补丁无效，这是高频踩坑。

S11. 依赖注入与到处 patch，你如何取舍？

推荐回答： 可测设计优先构造注入（传入 client/repo），测试塞 fake/mock，重构更稳。遗留代码或模块级单例不得已再用 patch/mocker。过度 mock 实现细节会使测试脆、与行为脱节。

S12. pytest-mock 的 mocker 相对手写 patch 多了什么？

推荐回答： 提供统一 fixture，用例结束自动撤销补丁，减少漏还原；API 与 unittest.mock 一致，学习成本低。简单改环境变量也可用内置 monkeypatch。

1.5 Hypothesis

S13. 属性测试与 parametrize 示例测试如何分工？

推荐回答： 示例测试表达明确业务故事与回归钉死；Hypothesis 用性质（交换律、round-trip、不变量）在输入空间搜索并 shrink 反例。二者互补：不删掉可读用例，也不指望性质测试单独讲清产品需求。

S14. 发现失败后为什么要用 @example？

推荐回答： 把已缩小的反例钉进仓库，保证回归稳定复现，不依赖生成器运气。同时应修正性质或实现，避免「偶发红」。

S15. 什么时候不该上 Hypothesis？

推荐回答： 性质说不清、强依赖未隔离的外部世界、或主要验证交互时序时，成本高且不稳定。应先把逻辑纯化为可测函数，再对纯层做属性测试。

1.6 基础概念与工具细节

S16. 「单元测试、边界测试、AB Test」是一类东西吗？

推荐回答： 不是。单元是 分层；边界（边界值）是 用例设计方法，常写在单元/接口层执行；AB 是 线上产品实验（分流比指标），不是 pytest 质量单测主线。详见基础篇 §1 三维对照。

S17. 等价类与边界值如何落到 parametrize？

推荐回答： 先划分等价类并取代表，再对边界（空、0、上下限±1）各补用例，最后写成 parametrize 的行；不要无脑笛卡尔积。框架只负责跑表，设计在基础篇 §5。

S18. stub、mock、fake 在 pytest 实践里怎么对应？

推荐回答： 固定 return_value 偏 stub；再断言 assert_called_with 则带 spy/mock 色彩；手写内存实现是 fake。面试能按基础篇 §6澄清即可，不必纠结商标。

S19. --lf / --ff 与 -x 各解决什么工程问题？

推荐回答： -x 首次失败即停，缩短反馈；--lf 只重跑上次失败，修 bug 时聚焦；--ff 先失败再全量，兼顾回归。本地调试常用组合，不替代绿灯全量。

S20. side_effect 适合模拟哪些场景？

推荐回答： 依次返回多值、直接抛异常、或按调用动态计算。适合「第一次超时第二次成功」等重试路径，比多次改 return_value 清晰。

S21. 分支覆盖比行覆盖多解决什么问题？

推荐回答： 行覆盖可能只执行了 if 为真侧；分支覆盖要求各分支走过。打开 branch = true 更能发现假高覆盖。仍不能证明断言有效。

2. 面试真题

以下题目按主题归纳、改写自公开面经与题库，用于训练表达，并非逐题对应某一场真实面试；综合参考来源见文末「参考面经与题库」。

I1. 为什么团队用 pytest 而不是只用 unittest？

推荐回答： pytest 用例写法轻（函数级即可）、原生 assert 失败信息可读、fixture 依赖注入与作用域比经典 setup/teardown 更灵活，参数化与插件生态（cov、xdist、mock）成熟。unittest 仍可兼容收集，但新项目默认 pytest 能降低样板代码。选型应落到「共享资源怎么管、数据驱动怎么写」，而不是潮流。

I2. 请解释 fixture，并说明 function 与 session 作用域怎么选。

推荐回答： fixture 负责准备与清理测试资源，并通过参数注入给用例。function 每用例一次，隔离最好，适合临时数据；session 全会话一次，适合昂贵且只读的连接或配置。扩大作用域必须处理可变状态污染：拷贝、重置或缩小 scope，并用 yield teardown 释放。

I3. yield 前后分别做什么？用例失败时清理还会执行吗？

推荐回答： yield 前 setup，yield 后 teardown。pytest 在用例结束后执行 teardown，失败场景仍会走清理，这比把清理只写在测试末尾更安全。面试应能举连接关闭、临时目录、测试账号删除的例子。

I4. 接口自动化里 Token、下单有依赖，你如何避免「必须先跑登录用例」？

推荐回答： 不靠用例顺序，而靠 fixture 链：token fixture 登录，product 依赖 token 建数据，test_order 只声明需要的 fixture。好处是解耦、可复用、可单独跑，并在 teardown 清理，避免脏数据。若必须端到端长流程，应标明是集成层，而不是单元层硬编码顺序。

I5. parametrize 怎么讲才像用过，而不是背装饰器？

推荐回答： 强调数据与逻辑分离、一组断言覆盖边界与异常、报告可定位到具体参数行；可提 ids、pytest.param 打 skip/xfail。补充：先等价类再组合，避免无意义爆炸。这与「提高覆盖率」相关，但覆盖率仍要有有效断言。

I6. conftest 放什么？不放什么？

推荐回答： 放共享 fixture、本地 hook、测试专用配置。不把生产业务逻辑塞进 conftest，也不让 conftest 隐式依赖复杂外部环境导致收集即失败。目录级 conftest 可分层，避免所有东西堆在根上造成加载过慢与耦合。

I7. 如何 mock 外部 HTTP/DB，保证可重复？

推荐回答： 单元层用依赖注入或 unittest.mock/pytest-mock 固定返回与异常；断言调用参数与次数。数据用样本 JSON/夹具文件。集成层另开少量真依赖测试。口诀：单元测逻辑，集成测接线。patch 路径对准使用处。

I8. 覆盖率在 CI 里怎么用才合理？

推荐回答： 作为防回退仪表盘：fail_under + 缺失行报告，聚焦业务包。不把 100% 当 KPI；结合代码审查看关键分支是否有 intentional 断言。解释清楚覆盖率≠质量，避免只刷数字。

I9. 大规模用例集如何分层跑？

推荐回答： 用 mark 区分 smoke/slow/integration；默认 PR 跑快测，夜间跑全量。fixture 按 scope 控成本；必要并行时注意隔离（独立库/前缀）。核心是可筛选与可独立，而不是一份巨型脚本。

I10. 什么是属性测试？和普通单元测试比优势在哪？

推荐回答： 属性测试声明对任意合法输入应成立的不变量，由 Hypothesis 生成并尝试证伪，失败后 shrink 成小反例。优势是覆盖「想不到的脏输入」；劣势是性质写错会假绿或假红。实践上与 parametrize 示例测试互补，并用 @example 钉死回归。

I11. 编码/解码函数你会用 Hypothesis 测哪些性质？

推荐回答： 至少 round-trip：decode(encode(x)) == x；可加「非法输入应抛约定异常」的策略过滤或单独示例。策略限制 max_size 控制成本。若实现有意不保持某性质，不要强写进测试。

I12. mock 过多导致重构全红，你怎么改进？

推荐回答： 回顾被测边界：改为测公开行为而非私有调用序列；能注入则注入；对稳定接口用 fake 对象代替细粒度交互断言。保留少量关键交互断言，删除与实现绑死的断言。必要时补一条轻量集成测试托底。

I13. 请用一分钟讲清测试金字塔，以及你们单测放哪一层。

推荐回答： 底层单元多、快、稳，上层 E2E 少、慢、贵。研发默认把断言放在单元与组件（Handler）层；真依赖集成少而精；浏览器 E2E 不作日常主量。若全靠 UI 测，反馈慢且脆，应下沉。

I14. assume 在 Hypothesis 里要注意什么？

推荐回答： assume 过滤不满足前提的生成值，避免非法输入干扰性质。滥用会导致有效例子过少、测试变慢或几乎不跑。优先在策略里收窄空间（max_size、filter），assume 作补充。
