容器编排学习-Kubernetes

发表于 2026-08-04 更新于 2026-08-20 分类于 计算机
Kubernetes 一篇收齐：无状态主路径，以及有状态生产、流量策略、弹性与生产操作；本地以 kind 为例。

接 Docker：单机容器不够时需要 编排——声明期望状态，由集群完成调度、自愈、滚动与服务发现。本篇以 kind 为本地集群口径；§1–§12 打通无状态，§13–§16 补生产向加深。

0. 本篇位置与边界

做 不做
核心对象与无状态主路径（§1–§12） Istio / 服务网格深潜
有状态生产要点、流量策略、HPA/PDB 多集群联邦 / 某云控制台截图
生产变更、节点维护、可观测认名 CKA 题海战术、etcd 搭集群实操

各节结构：是什么 → 机制 → 示例 → 注意点。

1. 为何编排；调谐心智

是什么： Compose 擅长单机。多机还要副本、节点故障自愈、滚动更新、统一服务发现。K8s 让你写 期望状态，控制面不断 调谐 到接近期望。

机制要点：

平面 角色
控制面 API、调度、控制器
节点 kubelet、运行时、代理数据面

注意点：

  1. 你几乎不 SSH 起进程；改的是 API 对象。
  2. etcd/控制面异常时，集群「失忆或失明」风险远高于单容器——生产要备份与高可用（点到）。
  3. 调谐是最终一致：短暂不一致（滚动中）是常态。

2. 声明式与 kubectl

是什么： 声明式 = 描述「要什么」并反复 apply；命令式 = 一条条命令改活对象。团队应统一声明式，便于 GitOps 与审查。

机制要点：

风格 例子 特点
声明式 kubectl apply -f 幂等对齐；清单进仓库
命令式 kubectl run / expose 快，但难复现、易漂

对象四段：apiVersion / kind / metadata / spec（状态常见于 status，由系统写）。

  1. create 与 apply 混用易触发字段管理冲突——统一 apply。

3. Pod 与探针；command/args

是什么： Pod 是调度原子。可含多容器，共享网络命名空间与卷——适合主业务 + sidecar（代理、日志），不适合强行塞无关进程。

机制要点：

探针 失败后果
readiness 从 Service Endpoints 摘掉，不接新流量
liveness 杀容器并重启
startup 成功前暂缓其它探针，护航慢启动

探针方式：HTTP / TCP / Exec。关键参数：initialDelaySeconds、periodSeconds、timeoutSeconds、failureThreshold。

与 Docker 对应：

Docker Kubernetes
ENTRYPOINT command
CMD args

注意点：

  1. liveness 过严 + 启动慢 → CrashLoop；应上 startup 或调参，而非无限加大 delay 掩盖问题。
  2. 探针不要强依赖外部 DB/下游——下游抖动会导致自重启风暴。
  3. readiness 与「进程活着」不是一回事：活着但未就绪应摘流量。
  4. 生产少用裸长期 Pod；用 Deployment 管模板。

4. Workload

4.1 Deployment（主路径）

是什么： 声明无状态应用的副本与发布方式；底层通过 ReplicaSet 维持 Pod 数量，并支持滚动与回滚。

机制要点：

  • selector.matchLabels 必须匹配 template.metadata.labels，且 创建后不要乱改 selector。
  • 滚动：maxUnavailable / maxSurge 控制不可用比例与浪涌。
  • imagePullPolicy：IfNotPresent / Always（:latest 时常 Always）影响是否重拉。

示例：

注意点：

  1. 无 readiness 的滚动 = 未就绪 Pod 可能已接流量。
  2. Recreate 策略会先删后建，有短暂中断——默认滚动更常见。
  3. 改错 label 导致 Service 选不中 Pod → 全面 断流。

4.2 StatefulSet（最小片段）

是什么： 需要稳定网络标识、有序部署/删除、稳定存储时用（有状态组件）。

注意： 通常配合 headless Service；PVC 模板与扩缩容语义更复杂。生产级注意点与备份/Operator 选择见 §13。

4.3 Job（最小片段）

是什么： 跑完就结束的批任务；成功/失败有明确结束态。

注意： restartPolicy 对 Job 只能 Never/OnFailure；失败重试看 backoffLimit。

4.4 DaemonSet / CronJob（认名）

类型 何时用 注意
DaemonSet 每节点（或选中节点）跑一个 Agent：日志、监控、网络插件 不要用它跑普通无状态业务副本
CronJob 定时创建 Job（备份、报表） 关注时区、并发策略 concurrencyPolicy、失败历史保留

卷挂载 文件可热更新（应用需重读或重启）；适合配置文件

Secret 默认多为 base64，不是加密；靠 RBAC、静态加密与最小权限。

6. Service 与 Ingress

是什么： 为动态 Pod IP 提供稳定虚服务（ClusterIP）与发现；Ingress 做 HTTP 路由（需 Controller）。

机制要点：

  • Service 用 label selector 选 Pod，后端是 Endpoints/EndpointSlice。
  • 仅 Ready 的 Pod 通常才进负载均衡（与 readiness 强相关）。
  • kube-proxy（iptables/ipvs 等）在节点实现转发（实现细节点到）。
类型 用途
ClusterIP 集群内默认
NodePort 节点端口临时暴露
LoadBalancer 云上外部 LB

示例（ClusterIP）：

注意点：

  1. 无 readiness → 启动中/半死 Pod 仍可能吃流量。
  2. Ingress 资源 不等于 已有入口：必须装 Ingress Controller。
  3. selector 与 Deployment 标签不一致 → Service 无后端。
  4. 本地 kind 常用 port-forward 调试，不等于生产暴露模型。
  5. Ingress / NetworkPolicy / Gateway API 生产要点见 §14。

7. 存储认名

是什么： PVC 表达「我要一块盘」；PV/StorageClass 由集群供给。无状态可用 emptyDir。

机制要点：

对象 角色
PVC 声明需求（容量、访问模式）
PV 具体卷
StorageClass 动态供给类
emptyDir 随 Pod 生命周期；换节点即丢

注意点：

  1. 删 PVC 是否删数据取决于 reclaimPolicy 与实现——删前确认。
  2. AccessMode（RWO/RWX）不匹配会 Pending。
  3. emptyDir 不适合数据库持久。
  4. 有状态优先理解 StatefulSet + PVC 模板，再上生产库（展开见 §13）。

8. 资源与调度

是什么： requests 影响调度与保证；limits 是运行上限。

机制要点（QoS 认名）：

QoS 典型条件
Guaranteed 所有容器 request=limit 且都设置
Burstable 有 request 但未全部 Guaranteed
BestEffort 未设 request/limit

Pending 常见：资源不够、污点、PVC 未绑、亲和不满足。

注意点：

  1. 内存超 limit → OOMKill；CPU 超常被节流。
  2. 只设 limit 不设 request 或乱设，易导致调度与噪音邻居。
  3. LimitRange / ResourceQuota 可在 NS 级约束（认名）。
  4. 副本随负载伸缩见 §15 HPA；节点压力与 QoS 驱逐是另一条线（面试点到）。

9. Namespace、标签、RBAC

是什么： Namespace 做资源与配额边界；label 关联对象；RBAC 控谁能对 API 做什么。

机制要点： Role/RoleBinding 限命名空间；ClusterRole/ClusterRoleBinding 可集群范围；主体常为 User / Group / ServiceAccount。

示例（只读 Pod，认名级）：

注意点：

  1. Namespace 不是强安全沙箱（网络策略等另配）；默认不挡同集群恶意横向。
  2. 默认 ServiceAccount 权限应收敛；CI 勿共用 cluster-admin。
  3. 业务 Pod 需要拉私有镜像时，用 imagePullSecrets 引用仓凭证 Secret，勿把仓密码写进镜像。

10. 排障与 Helm

现象 先查
Pending describe：资源/污点/PVC
CrashLoopBackOff logs、探针、OOM、命令
ImagePullBackOff 镜像名/标签、仓库可达性、imagePullSecrets、SA 是否挂上凭证

13. 有状态生产

是什么： 数据库、消息队列、协调服务等需要 稳定身份 + 持久盘 + 有序变更。Deployment 适合无状态；有状态主用 StatefulSet，或交给 Operator / 托管服务。

机制要点：

能力 含义
稳定 DNS pod-0.服务名.ns.svc…；常配 headless Service（clusterIP: None）
有序部署/删除 默认按序号启动；缩容先删最大序号
稳定存储 volumeClaimTemplates 为每个 ordinal 建独立 PVC
更新策略 RollingUpdate / OnDelete；可配 partition 做金丝雀式有状态滚动

示例（headless + PVC 模板，示意）：

生产决策（何时自建 STS）：

路径 适用
托管 DB / 云 RDS 优先：备份、多 AZ、补丁由平台负责
Operator（如官方/社区 DB Operator） 需要集群内跑、要自动化 failover/备份流水线
手写 STS 学习、简单单副本、或已有成熟运维剧本；多副本主从勿「只加 replicas」以为高可用

注意点 / 反模式：

  1. 缩容不删 PVC：replicas 从 3→1 后，data-pg-1/data-pg-2 通常仍在——占盘且含数据；扩回去会复用旧盘，未必是你想要的「干净实例」。
  2. 删 STS 默认不级联删 PVC——防误删数据；真要清数据须显式删 PVC，并确认 reclaimPolicy。
  3. RWO 卷常绑单节点：Pod 漂移到它节点可能 Pending（卷未释放/未多挂载）。
  4. 有状态滚动要懂应用语义（主从选举、成员列表）；盲目 kubectl delete pod 可能脑裂或丢写。
  5. 备份是一等公民：PVC 快照 / 逻辑 dump / 对象存储；定期恢复演练，而不是「有盘=已备份」。
  6. 密钥、连接串走 Secret；初始化 Job（建库/迁移）与 STS 生命周期分开（见 §4.3）。

14. 流量与网络策略

是什么： Service 解决集群内稳定入口；Ingress（或 Gateway API）做 L7 HTTP 路由；NetworkPolicy 做 Pod 间「谁可以连谁」的白名单。

14.1 Ingress 与 Controller

机制要点： Ingress 只是 API 对象；真正转发靠集群里的 Ingress Controller（nginx、traefik、云厂商等）。无 Controller → Ingress 一直「写了没用」。

示例（HTTP 路由示意）：

注意点：

  1. TLS 常由 Controller + Secret（证书）或证书管理器（cert-manager 认名）完成。
  2. 路径/Host 配错 → 404 或打到错误后端；先确认 Service Endpoints 非空。
  3. Gateway API 是更新一代流量 API（Gateway/HTTPRoute 等）——面试认名即可，本篇仍以 Ingress 为主路径。
  4. 生产对外：LB → Controller → Service → Pod；本地 kind 调试仍可用 port-forward，勿混为一谈。

14.2 NetworkPolicy

是什么： 在支持策略的 CNI 上，按标签限制入站/出站。默认（无策略）往往 全通；有策略后同 NS 也可能变「默认拒绝 + 显式允许」。

注意点：

  1. 策略是否生效取决于 CNI（部分环境需显式开启）。
  2. DNS、监控、Ingress Controller 所在 NS 常需额外放行，否则「策略一加全挂」。
  3. Namespace 不是网络隔离；要隔离靠 NetworkPolicy（或网格，本篇不做）。

15. 弹性与稳定性

是什么： 副本数随负载变化（HPA）；驱逐/发布时保证最少可服务副本（PDB）；与 readiness、资源请求一起构成稳定性三角。

15.1 HPA（HorizontalPodAutoscaler）

机制要点： 按 CPU/内存利用率或自定义指标，调节 Deployment/STS 等的 replicas。依赖 metrics-server（或其它指标管道）；没有指标 → HPA 无法工作。

示例：

注意点：

  1. 必须设合理 requests，否则利用率分子分母失真。
  2. 扩得快、缩得慢是常见稳态；抖动指标会导致震荡——可调稳定窗口（实现细节点到）。
  3. VPA（垂直扩资源）与 HPA 叠加需策略，面试认名即可，生产慎同时乱配。

15.2 PDB（PodDisruptionBudget）

是什么： 限制 自愿中断（drain、滚动升级部分场景）时最多不可用的 Pod 数，避免一次抽干。

注意点：

  1. PDB 挡不住节点突然宕机（非自愿中断）——仍需多副本 + 跨故障域。
  2. minAvailable / maxUnavailable 与副本数矛盾时，drain 会卡住——改 PDB 或先扩容。
  3. 单副本业务设 minAvailable: 1 时，自愿驱逐几乎无法进行——要接受中断或改多副本。

16. 生产操作与变更

是什么： 生产不是「会写 YAML」，而是 可回放、可回滚、可观察、可维护节点 的操作习惯。

16.1 变更与发布

习惯 做法
声明式 Git 存清单；kubectl apply / GitOps（Argo CD、Flux 认名）
先看差 kubectl diff -f 或 apply --server-side --dry-run=server
镜像不可变 用 tag+digest 或仅 digest；禁依赖漂浮 latest
观察发布 rollout status；看 readiness、错误率、饱和度
回滚 rollout undo；有状态变更另按应用剧本（备份→迁移→切换）
配额 ResourceQuota / LimitRange 防单 NS 打爆集群

发布检查清单（口述级）：

  1. 镜像可拉、配置/密钥已更新且知否需滚动。
  2. readiness 正确；HPA 上下限合理；PDB 不挡本次滚动。
  3. 迁移 Job（若有）先于或编排进发布流水线。
  4. 回滚路径演练过；有状态先备份。

16.2 节点与集群维护

注意点：

  1. drain 会驱逐 Pod；遵守 PDB；DaemonSet 通常保留。
  2. emptyDir 数据在 drain 时可能丢（按参数）——勿把重要状态放 emptyDir。
  3. 控制面 / etcd：生产要备份与高可用（云托管或自建剧本）；本篇不展开搭集群，但面试需能说出「etcd 丢 ≈ 集群失忆」。
  4. 污点/容忍（taint/toleration）、亲和性：把负载放到合适节点；系统组件常容忍控制面污点。

16.3 可观测与安全（生产认名）

层面 认名
日志 标准输出 → 节点采集 / 旁路 Agent（DaemonSet）→ 集中检索
指标 metrics-server；Prometheus + 告警（认名）
追踪 OpenTelemetry 等（点到）
运行时 非 root、readOnlyRootFilesystem、drop capabilities、seccomp（回链 Docker §9）
供应 镜像签名/扫描、最小 RBAC、Secret 静态加密、NetworkPolicy

生产排障顺序（扩展 §10）：
get/describe Events → logs（含 -p 看上次崩溃）→ 探针与资源 → Endpoints/NetworkPolicy → 节点 cordon/磁盘/运行时。

总结

先抓住调谐与声明式，跑通 Deployment + Service + ConfigMap + 探针；再生产向补齐：有状态身份与盘、Ingress/NetworkPolicy、HPA/PDB，以及 diff/drain/不可变镜像与备份演练。下一篇自检与面经收口。
