1. RabbitMQ

是什么： 基于 AMQP 思想的消息中间件，擅长 灵活路由 与较完备的确认语义；吞吐通常低于 Kafka，延迟与路由能力出色。

1.1 核心模型

组件 作用
Exchange 接收生产消息，按类型与绑定路由
Queue 存消息，供消费者拉取
Binding Exchange 与 Queue 的路由规则
Routing Key 路由匹配用的键

Exchange 类型（必记）：

类型 行为
direct routing key 精确匹配
topic 模式匹配（* / #）
fanout 广播到所有绑定队列
headers 按头信息（少用）

1.2 可靠性链路（完整一条）

环节 做法
消息持久化 消息 delivery mode 持久 + 队列 durable
生产确认 Publisher Confirm（或事务，Confirm 更常用）
消费确认 手动 ACK；处理成功后再 ACK
失败 NACK/reject + 再入队或进死信

死信（DLX）链路：

延时： 常用 TTL + DLX 模拟，或延时插件；注意版本与运维复杂度。

1.4 消费并行：prefetch（QoS）

是什么： basic.qos / prefetch 限制「未 ACK 的消息数」，避免一次把大量消息推给慢消费者导致内存与堆积假象。

设置 含义
prefetch=1 处理完再拿下一条，公平但吞吐低
prefetch=N 管道化；N 过大仍可能压垮单消费者

注意点： 自动 ACK 时 prefetch 语义不同；手动 ACK 场景务必设合理 prefetch。

1.5 无法路由：mandatory 与 return

是什么： 发布时 mandatory=true，若 Exchange 无法路由到任何队列，消息通过 return 回生产者，而不是默默丢弃。

注意点： 默认不 mandatory 时「发成功但无人消费」可能长期发现不了——拓扑变更后要查绑定。

1.6 高可用：镜像 vs quorum

方案 认知
经典镜像队列 老方案，运维与脑裂问题多
仲裁队列（quorum） 较新推荐方向；基于 Raft 思想，适合持久化队列 HA

生产选集群方案时读清当前大版本推荐，避免单节点当高可用；新集群优先建立 quorum 认知。

注意点：

  1. 积压在内存/磁盘策略下可能拖慢 Broker，要监控队列深度。
  2. 自动 ACK 等同于「先 ACK」风险。
  3. 路由灵活也意味着拓扑复杂——文档化 Exchange/Queue 命名。

2. RocketMQ

是什么： 阿里开源的业务向 MQ，Java 生态友好；强调 海量 Topic、事务消息、延时/顺序 等业务特性；存储上 CommitLog 顺序写。

2.1 核心架构

组件 作用
NameServer 轻量路由注册与发现（无强一致中心状态机负担）
Broker 存消息、投递
Proxy（5.x 认名） 多语言 / gRPC 等接入层；Broker 更专注存储与复制
Producer / Consumer 发送与消费（集群消费 / 广播消费）

存储（口述级）：

结构 作用
CommitLog 所有消息顺序追加的大日志
ConsumeQueue 按 Topic/队列的索引，消费时先查索引再定位 CommitLog

相对 Kafka「每分区一套日志文件」，CommitLog 集中顺序写对 大量 Topic 更友好。

2.2 发送与消费

能力 说明
同步发送 等待 Broker 结果，易做可靠
异步 / oneway 吞吐高，可靠性策略不同
集群消费 同组内分摊（类似 Kafka Group）
广播消费 组内每人一份

2.4 顺序消息与延时

类型 要点
顺序消息 同 sharding key 进同一队列 + 顺序消费；并行度受限
延时/定时 产品级支持（档位或定时，随版本）；适合超时关单等

2.5 过滤、重试与死信

能力 要点
Tag 过滤 同一 Topic 多 Tag，消费者按 Tag 订阅；简单高效
SQL92 过滤 按属性表达式过滤；灵活但要注意过滤位置与性能代价
消费重试 失败按等级间隔再投；需幂等
死信主题 超次失败进入死信，供人工/补偿（与篇 1 死信运营对齐）

注意点： 过滤条件过宽等于没过滤；过窄导致「以为发了其实下游收不到」——要监控消费量与死信。

3. 三大 MQ 选型总表

维度 Kafka RabbitMQ RocketMQ
典型吞吐 极高 相对较低 高
延迟 低～毫秒级 通常更低延迟（常见宣传到亚毫秒，以实测为准） 毫秒级
路由 分区键 Exchange 极灵活 Topic/Tag 过滤
顺序 分区内 队列内 顺序消息（队列内）
事务/本地一致 事务 Producer 认名 较弱/另做 事务半消息强项
延时 常靠外部/业务 TTL+DLX/插件 原生友好
Topic 规模 过多分区文件压力大 队列多有成本 海量 Topic 更友好
生态 大数据/流最强 传统企业集成多 国内业务/电商多
运维复杂度 中高 中 中高
典型场景 日志、流、大数据管道 复杂路由、中小异步 订单交易、业务事件

4. 同一题三套答法

4.1 如何尽量不丢？

产品 要点
Kafka acks=all + min.insync.replicas；消费手动提交
RabbitMQ 持久化 + Publisher Confirm；手动 ACK
RocketMQ 同步发送成功；消费成功再确认；刷盘/HA 配置

4.2 如何应对重复？

三者都以 业务幂等 为主；Kafka 幂等 Producer / 事务降低生产重复；Rabbit/Rocket 重试与 Rebalance/再投递同样靠唯一键。

4.3 积压怎么办？

产品 要点
Kafka 看 lag；扩分区再扩消费者；优化处理
RabbitMQ 看队列深度；扩消费者；调 prefetch；警惕内存告警
RocketMQ 扩消费并行（队列数/线程）；临时 Topic 分流；优化业务

4.4 消费并行控制怎么抓？

产品 抓手
Kafka 分区数 上限决定同 Group 有效消费者数；max.poll.records 控制单次批量
RabbitMQ prefetch + 消费者实例数
RocketMQ Topic 队列数 × 消费线程；过滤减少无效拉取

5. 选型决策树与托管

自建 云托管
控制力 参数与版本全控 少运维
责任 HA/扩容/盘自己扛 读 SLA 与限流
适用 有平台团队 多数中小默认评估

6. 生产检查清单（跨 MQ）

  1. 明确语义目标：至少一次 + 幂等（唯一键/状态机）
  2. 生产确认与 Broker 耐久配置已按关键等级收紧
  3. 消费：先处理再 ACK/提交；禁止盲目自动 ACK
  4. 死信/重试有退避与人工处理剧本
  5. 积压（lag/队列深度）告警；分区或队列数支持目标并行度
  6. 顺序需求已落到分区键/sharding key，而非口头「全局有序」
  7. 鉴权、网络隔离、磁盘与保留策略
  8. 选型理由可口述（对照 §3 表）

总结

Rabbit 赢在路由与确认模型清晰；Rocket 赢在业务消息能力（事务/延时/Topic 规模）；Kafka 赢在吞吐与流生态。用决策树选型，用四问题验收设计。下一篇自检与面经收口。
