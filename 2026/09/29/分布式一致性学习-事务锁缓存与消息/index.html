分布式一致性学习-事务锁缓存与消息

发表于 2026-08-07 更新于 2026-08-20 分类于 计算机
收口单机事务、缓存与 DB、分布式锁、Outbox/Saga 与 Agent 写工具一致性；一张决策总表对齐 MySQL/Redis/MQ/Agent。

本篇是 一致性决策收口：把已学的 MySQL 事务、Redis 缓存、MQ Outbox、Agent 写工具放到同一张取舍表上。不新开产品巡览，只回答「多步副作用怎么选强一致还是最终一致」。

0. 本篇位置与边界

做 不做
口述隔离级别与丢更；缓存+DB 窗口 云厂商分布式事务产品手册
锁边界；Outbox/Saga；少用 2PC 共识算法（Paxos/Raft）精读
Agent 写工具与业务同口径 新框架 / Pulsar / Flink

回链：

  • 单机事务与锁：MySQL 手册（三）

  • Outbox / 至少一次：消息队列基础
  • Agent 写工具：Agent 工程化（三）

1. 单机事务与隔离口述

是什么： 同一库内多语句的原子性与隔离；强一致首先落在 本地事务，不是锁服务或 MQ。

机制（口述要点）：

现象 含义 默认 RR 下
脏读 读到未提交 InnoDB 默认避免
不可重复读 同事务两次读行内容变 MVCC 快照缓解
幻读 同条件多出行 间隙锁 / Next-Key 部分抑制
丢失更新 读-改-写互相覆盖 隔离级别不自动解决 → FOR UPDATE / 乐观版本

注意点： 事务内禁止远程 RPC；长事务拖锁与 undo。跨库「一次 COMMIT」不是单机事务能给的。

2. 缓存与 DB

是什么： Cache-Aside 下 DB 为权威，缓存可短暂脏；目标多为 最终一致。

推荐： 先写 DB，再删缓存；读未命中回源回填（带 TTL）。并发回填旧值窗口见 Redis 缓存一致性。

注意点： 「更新缓存而非删除」更难；读从库 + 删缓存窗口更大；Redis 不承诺跨系统强一致。

3. 分布式锁边界

是什么： 多实例互斥；不替代 事务与幂等。

能做 不能做
防并发双扣「尽力而为」 替代 DB 唯一约束 / 行锁
临界区串行化 保证持锁方崩溃后业务已提交且仅一次
配合短临界区 当分布式事务协调器

锁过期续期失败 → 双持锁可能；解锁必须比对 token（Lua）。库存真相仍在 DB 约束。

4. Outbox / Saga / 少用 2PC

跨服务最终一致主路径：本地事务 + Outbox + 幂等消费。

模式 适用 代价
Outbox 一服务内「改状态 + 发事件」同成败 Relay/堆积；下游仍幂等
Saga 多服务长流程；可补偿 补偿难写；中间态可见
2PC / XA 极少：强一致且参与方少、同运维域 阻塞、运维重；默认不选

4.1 Saga 补偿时序（认名）

点 口径
中间态 用户可能短暂看到「预订中」——产品需接受
与 Outbox 每步完成发事件驱动下一步，或编排器推进
何时不用 单库能搞定的别拆 Saga

注意点： Outbox 仍会重复投递；Saga 不是「自动强一致」；2PC 卡住会拖死资源；补偿失败要人工/对账队列。

5. Agent 写工具一致性

Agent 重试、interrupt 重放、队列至少一次 → 与业务写路径同口径：

  1. 写工具带 invocation_id / 业务幂等键
  2. 高风险写 → HITL；确认后再落库
  3. 「落库 + 入队」用 Outbox，勿只在内存发 MQ
  4. 审计表与副作用表可对账

详见 Agent 工程化（三）§6.1 · 工程化（四）Worker。

6. 决策总表与反模式

6.1 场景：「下单扣库存 + 发积分 + 更新缓存」

步骤 一致强度 理由
扣库存 + 订单 强（本地事务） 钱货同源，不可漏扣
发积分 最终 可延迟；幂等 + 对账
更新缓存 最终 TTL/删缓存托底

6.2 决策总表

需求 首选
同库多表原子 本地事务 + 合适隔离/锁
防丢更 FOR UPDATE / 乐观版本 / 原子 SQL
缓存与 DB 先 DB 后删缓存；认最终一致
跨服务通知 Outbox + 至少一次 + 幂等
长流程可回滚 Saga + 补偿
多实例临界区 Redis 锁（辅助）+ DB 约束（权威）
Agent 写副作用 幂等键 + 审计 + 同 Outbox

6.3 反模式

  1. 事务里调 HTTP/发邮件再 COMMIT
  2. 靠分布式锁当库存真相
  3. 无幂等假设恰好一次
  4. 先改缓存再写 DB 当强一致
  5. Agent Prompt「不要重复下单」替代幂等键
  6. 处处 2PC

7. 自检与面试（短）

S1. 脏读 / 不可重复读 / 幻读 / 丢失更新各靠什么治？

推荐回答： 前三者主要靠隔离 + MVCC/锁；丢失更新靠悲观锁、乐观版本或原子更新，不是「调高隔离」 alone。

S2. 为何推荐先写 DB 再删缓存？

推荐回答： DB 为权威；删失败可补偿；更新缓存并发更易脏。窗口用延迟双删/锁缩小，TTL 托底。

S3. Outbox 解决什么、不解决什么？

推荐回答： 解决「业务提交与发事件尽量同成败」；不解决下游重复消费（仍要幂等）与跨服务即时强一致。

S4. Saga 补偿失败怎么办？

推荐回答： 补偿也须幂等；失败进对账/人工队列；产品接受中间态。能单库事务解决的不要上 Saga。见 §4.1。

I1. 口述「下单扣库存 + 积分 + 缓存」方案与取舍。

推荐回答： 库存与订单本地事务强一致；积分与缓存走 Outbox 最终一致；锁只辅助；Agent 若触发写单须幂等与审计。对照 §6.1。

I2. 分布式锁能保证扣库存只一次吗？

推荐回答： 不能单独保证。锁过期、进程暂停可双持；权威用 DB 条件更新/唯一约束；锁降低冲突概率。

总结

强一致优先落本地事务；跨服务默认最终一致（Outbox + 幂等）。

缓存与锁是加速与协调，不是第二真相源。

Agent 写工具与 MQ/DB 同口径，不另造一套。
