消息队列学习-自检面试与对照

发表于 2026-08-06 更新于 2026-08-20 分类于 计算机
消息队列阶段自检与面试导向问答；覆盖丢/重/乱/积压、Kafka 与三大选型，含 checklist 与面经参考。

完成 基础模型、Kafka 与 对照选型 后，重点能讲清为何用 MQ、四问题怎么解、Kafka 参数与三大选型。本篇用自检验收，再用公开面经高频点训练表达。

0. 使用说明

建议先遮住「推荐回答」，在 60～120 秒内口述：

  1. 先给结论（要不要 MQ、选哪个、语义目标）。
  2. 讲机制（分区/ISR、Confirm、半消息）。
  3. 点风险（自动提交丢消息、无幂等、积压重试风暴）。
  4. 落到工程措施（手动 ACK、唯一键、lag 告警、决策树）。

1. 学习自检

1.1 通用模型

S1. 为什么要用消息队列？什么时候不该用？

推荐回答： 解耦、异步、削峰、最终一致。强同步强一致主路径、流量极小、或把 MQ 当 DB 查历史时不该硬上。

S2. 至少一次与恰好一次在工程上怎么落？

推荐回答： 默认追求至少一次（生产确认+副本+先处理再 ACK）。恰好一次需产品事务/幂等链路且成本高；业务幂等仍不可省。

S3. 丢消息可能发生在哪三段？各怎么防？

推荐回答： 生产未等确认；Broker 无耐久/副本不足；消费先 ACK 后处理失败。对策：Confirm/acks、持久化与 ISR、手动提交且成功后 ACK。

S4. 为何说「先幂等，再调 MQ 参数」？

推荐回答： 至少一次必然可能重复；参数只降概率。用唯一键、状态机、去重表消灭重复危害。

S5. 全局有序和分区内有序差别？如何保证同订单有序？

推荐回答： 全局有序吞吐差。同业务 key 进同一分区/队列且串行消费。跨分区不保证。

S6. 消息积压怎么发现和处理？临时分流是什么？

推荐回答： 看 lag/队列深度。扩消费者（匹配分区）、优化逻辑、扩分区、降级丢弃+补偿。临时分流：新 Topic/新消费者救急止血。

S7. 重试风暴有什么危害？死信队列作用？

推荐回答： 下游故障时疯狂重试会打得更死；要退避熔断。死信承接超次失败供人工/补偿，需有处理剧本。

S8. 本地消息表 / Outbox 解决什么？

推荐回答： 业务事务与发消息尽量同成败：同事务写 Outbox，异步 relay 发 MQ；下游仍幂等。

1.2 Kafka

S9. Topic、Partition、Consumer Group 关系？

推荐回答： Topic 分多分区并行；同 Group 分摊分区且一分区至多一活跃消费者；不同 Group 独立进度，实现多下游。

S10. Kafka 为什么快？举三点。

推荐回答： 顺序写、批量、分区并行；零拷贝/页缓存等认名。

S11. acks=0/1/all 与丢消息关系？为何还要 min.insync.replicas？

推荐回答： 0 最易丢；1 Leader 挂可能丢；all 等 ISR。min.insync 防止 ISR 过少时假成功。

S12. 自动提交 offset 有什么风险？推荐怎么做？

推荐回答： 可能未处理完已提交→丢。手动：业务成功（幂等写）后再 commit。

S13. Rebalance 会带来什么？如何减轻？

推荐回答： 停消费、易重复。合理超时心跳、避免频繁扩缩、处理勿过长；业务幂等。

S14. 如何保证 Kafka 分区内顺序？热点分区怎么办？

推荐回答： 固定业务 key 分区；同分区串行消费。热点则打散 key 或拆分业务。

S15. Kafka 积压时只加消费者不够用是为什么？

推荐回答： 并行度受分区数限制；需先扩分区再扩消费者（有序主题慎扩）。

1.3 Rabbit / Rocket / 选型

S16. RabbitMQ Exchange 四种类型一句话？

推荐回答： direct 精确；topic 模式；fanout 广播；headers 按头。

S17. Rabbit 如何做生产与消费确认？死信链路？

推荐回答： Publisher Confirm；手动 ACK。拒绝/过期等进 DLX 再到死信队列。

S18. RocketMQ CommitLog 与 ConsumeQueue？事务半消息步骤？

推荐回答： CommitLog 顺序存全量消息；ConsumeQueue 索引。半消息→本地事务→Commit/Rollback，超时回查。

S19. 日志采集、订单交易、复杂路由各倾向哪个 MQ？

推荐回答： 日志/流→Kafka；交易事务延时海量 Topic→RocketMQ；复杂路由轻量→RabbitMQ。可组合。

S20. 口述选型决策树一句版。

推荐回答： 吞吐流生态选 Kafka；业务事务/延时选 Rocket；灵活路由选 Rabbit；都要则可能多个 MQ。见对照篇 §5。

S21. Redis List/Stream 与专业 MQ 边界？

推荐回答： Redis 可简易队列/流，缺完整可靠投递与积压运维产品力；可靠异步以本系列 MQ 为主。回链 Redis 篇。

S22. 生产上线 MQ 前你会检查哪五件事？

推荐回答： 语义与幂等；生产确认/耐久；消费 ACK 时机；lag/死信告警与剧本；鉴权隔离与选型理由。见对照篇 §6。

S23. Rabbit prefetch 与 Kafka 分区数在「消费并行」上各管什么？

推荐回答： Rabbit prefetch 限制未 ACK 在途条数，防单消费者被冲垮。Kafka 同 Group 有效并行度受 分区数 限制，再配合 max.poll.records。Rocket 看队列数与消费线程。见对照篇 §4.4。

S24. Kafka 保留时间将尽而 lag 仍很高意味着什么？Rocket Tag 过滤要注意什么？

推荐回答： 旧段可能被删，业务视角「像丢」，要 lag+保留一起告警。Tag/SQL 过滤过窄会导致下游收不到；要监控消费量与死信。5.x 另有 Proxy 接入认名。

2. 面试真题

以下题目按主题归纳、改写自公开面经与题库，用于训练表达，并非逐题对应某一场真实面试；综合参考来源见文末「参考面经与题库」。

I1. 为什么系统里要引入消息队列？有什么缺点？

推荐回答： 解耦异步削峰。缺点：排障链路变长、一致性变最终、运维与重复消费问题。要评估值不值得。

I2. 如何保证消息不丢失？

推荐回答： 按生产/Broker/消费三段答，并落到 Kafka acks 或 Rabbit Confirm 或 Rocket 同步发送之一作例子。

I3. 如何保证消息不被重复消费？

推荐回答： 承认至少一次；业务幂等（唯一键/状态机）；再提 Kafka 幂等 Producer 等辅助。

I4. 如何保证消息顺序？

推荐回答： 同 key 同分区/队列 + 单线程消费；不追求全局有序。

I5. 消息积压了怎么办？

推荐回答： 先看 lag 与原因；扩容匹配分区、优化消费、临时分流、降级补偿；忌重试风暴。

I6. Kafka 架构怎么讲？ISR 是什么？

推荐回答： Topic 分区副本，Leader 读写，Follower 同步；ISR 为同步副本集；与 acks=all 相关。

I7. Kafka Consumer Group 与 Rebalance？

推荐回答： 组分摊分区；成员变化触发再均衡；期间停消费且易重复，需幂等与合理超时。

I8. Kafka 如何实现高吞吐？

推荐回答： 顺序写、批量、分区并行、零拷贝/页缓存等。

I9. RabbitMQ 与 Kafka 怎么对比选型？

推荐回答： Rabbit 路由灵活、延迟好、吞吐较弱；Kafka 吞吐与流生态强、路由模型简单。场景决定。

I10. RocketMQ 事务消息怎么实现的？

推荐回答： 半消息→本地事务→提交/回滚；超时回查生产者。下游仍幂等。

I11. RocketMQ 和 Kafka 存储模型差异？

推荐回答： Kafka 按分区日志；Rocket CommitLog 集中顺序写 + ConsumeQueue 索引，利于海量 Topic。

I12. 延时消息各怎么做？

推荐回答： Rocket 原生友好；Rabbit TTL+DLX/插件；Kafka 常业务延迟或外部调度。

I13. 如果让你设计「订单创建后通知多个下游」，怎么用 MQ？

推荐回答： 发订单事件 Topic；多 Consumer Group（库存、积分、搜索）；生产耐久+消费幂等；关键可用 Outbox。

I14. 自动提交 offset 为什么危险？

推荐回答： 可能丢；应处理成功后手动提交，并接受重复+幂等。

I15. 三大 MQ 如何一分钟选型？

推荐回答： 按决策树：流/日志 Kafka；交易事务 Rocket；复杂路由 Rabbit；表维度吞吐/事务/Topic 规模。

I16. 消息队列会带来分布式事务问题吗？怎么处理？

推荐回答： 会变成最终一致。手段：本地消息表/Outbox、Rocket 事务消息、下游幂等与对账补偿；避免处处 2PC。

I17. 订单支付成功后要通知库存、积分、搜索，你怎么设计？

推荐回答： Outbox 发 OrderPaid（eventId+orderId）；Kafka 多 Consumer Group 各幂等处理；key=orderId 保顺序；失败进死信可重放。见基础篇 §10。

I18. 为什么生产常关闭 unclean leader election？Schema 契约解决什么？

推荐回答： unclean 允许非 ISR 当 Leader，可能丢已确认数据；关掉则 ISR 不足时拒绝写。Schema/版本字段解决多下游结构兼容，不替代业务幂等。见 Kafka 篇 §1/§9.2。
