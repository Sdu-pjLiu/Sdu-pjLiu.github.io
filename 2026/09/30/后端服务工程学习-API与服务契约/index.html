1. REST 资源与错误模型

是什么： 客户端靠 稳定的状态码 + 结构化错误体 分支，而不是解析自然语言 message。

HTTP 典型语义
400 参数/契约错误（可改请求）
401 / 403 未认证 / 无权限
404 资源不存在（或故意统一 404 防枚举）
409 冲突（版本/状态机）
429 限流
5xx 服务端；可重试类需配合幂等

错误体最小字段： code（稳定枚举）、message（人读）、request_id（对齐 Trace）、可选 details[]。

注意点： 业务失败不要全打 200 + {ok:false}（除非历史包袱且文档写死）；4xx/5xx 与「是否可重试」写进契约。

2. 幂等键

是什么： 客户端生成的 Idempotency-Key（或业务单号），服务端对同一键的写请求只生效一次。

适用 说明
支付、下单、发券 网络重试高发
Agent 写工具 与 invocation_id 同口径

机制： 唯一索引 / 幂等表；键带 tenant_id；TTL 后可归档但须防超长窗口双写策略写清。

注意点： GET 天然幂等不必强行加键；键冲突但 body 不同 → 明确 422/409，勿静默执行第二种写法。

2.1 幂等表最小机制

列 作用
tenant_id + idem_key 唯一约束（复合主键）
request_hash 同键不同 body → 409
status processing / completed / failed
response_code / response_body 重放时原样返回
created_at / expires_at TTL 与清理

反模式： 只把键放 Redis 无持久化 → 重启后双写；键不带 tenant → 跨租户碰撞。

3. 超时、重试与退避

注意点： 超时后不知成败 → 必须靠幂等键查询，不能再盲 POST。与 一致性篇、MQ 至少一次 同思路。

3.1 超时后决策表

客户端所见 下一步
明确 4xx（非 429） 改请求，勿重试同 body 硬撞
429 / 503 + Retry-After 退避后同幂等键重试
超时 / 连接断开 同 Idempotency-Key 再 POST，或先 GET 业务单号查询
2xx 成功；勿换键再写

入口限流与 429 策略展开见 网关与限流。

4. 分页

方式 适用 坑
offset/limit 管理后台、小数据 深翻页慢；写入导致跳行
cursor / keyset 时间线、大表 需稳定排序键；不支持随意跳页

契约写清：默认 page size 上限、排序字段、空页语义。导出类走异步任务，勿巨型同步分页。

5. gRPC 认名

点 口径
定位 服务间强类型 RPC；HTTP/2、Protobuf
错误 status code + details；映射到 REST 时勿丢语义
流 unary / server/client/bidi streaming 认名即可
与 REST 对外常 REST/JSON；对内可 gRPC；契约仍要超时与鉴权

本系列不展开 stub 生成；要求能口述「何时内网 gRPC、对外仍 REST」。

6. 同步 API vs MQ 异步

选同步 API 选 MQ/异步
调用方必须立刻知成败 可最终一致；削峰
短事务、低扇出 多下游、易积压隔离
查询与简单命令 长链路、可重试消费

Agent 长任务：HTTP 提交 job + 队列执行——见 Agent 工程化（四）。

7. API 版本与契约演进

是什么： 已发布契约只能 兼容扩展 或 显式新版本，不能静默改语义。

策略 做法
URL 版本 /v1/orders → /v2/orders；旧版日落有时间表
Header 版本 Accept: application/vnd.api+json;version=2
兼容变更 只加可选字段；枚举只增不改义
破坏变更 新版本；双跑 + 监控旧版流量归零再下线

注意点： 错误 code 一旦对外即稳定；改 message 可以，改 code 语义等于破坏契约。OpenAPI/Protobuf 作为真相源，生成物进 CI 契约测试。

总结

错误可机器分支；写路径有幂等键与幂等表；超时层层收紧；分页有上限；跨服务通知走异步；版本只兼容扩展或显式 bump。
