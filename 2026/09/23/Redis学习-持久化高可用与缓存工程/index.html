各节结构：是什么 → 机制 → 示例 → 注意点。

1. 持久化总览

是什么： 内存数据进程退出即消失；持久化把状态落到磁盘，以便重启恢复或备份。

方式 特点 典型取舍
RDB 某时刻快照，文件紧凑，恢复快 两次快照间可能丢数据；fork 有开销
AOF 追加写命令，可更高耐久 文件更大；重放恢复可能更慢
混合（4.0+） AOF 重写时用 RDB 作前缀再追加增量 兼顾恢复速度与增量安全

决策口径：

  • 可丢一段时间缓存 → 偏 RDB 或甚至关持久化（纯缓存 + 可重建）。
  • 要当「内存数据库」少丢 → AOF everysec 或混合，并做备份。
  • 生产常见：RDB 作定期备份 + AOF/everysec（或混合）作耐久，按业务容忍度调。

2. RDB

是什么： 按规则把内存数据生成二进制快照（如 dump.rdb）。

机制要点：

  1. BGSAVE：主进程 fork 子进程写盘；利用写时复制（COW），共享页在被修改时才拷贝。
  2. 配置如 save 900 1 表示 900 秒内至少 1 次写则触发（具体以配置为准）。
  3. 恢复：启动时加载 RDB，通常快于重放庞大 AOF。

注意点：

  1. 丢数据窗口：崩溃点距上次成功快照之间的写入会丢。
  2. fork 与延迟：大数据集 fork 瞬间可能卡住/延迟升高；COW 导致内存短暂上涨。
  3. 大 Key 使快照与加载更重（回链第 1 篇治理）。
  4. 只开 RDB 当「绝对不丢」是错的。

3. AOF 与混合持久化

是什么： 将写命令追加到 AOF 文件；重启时重放恢复。

fsync 策略：

策略 含义 丢数据上界（大致）
always 每命令刷盘 最安全，最慢
everysec 每秒刷盘 常见生产折中，约 1 秒
no 交给 OS 更快，丢更多

AOF 重写： 文件膨胀后后台重写为更短等价命令序列，降低体积与重放时间。

混合持久化： 重写时文件前半为 RDB 格式快照，后半为增量 AOF；恢复时先载快照再重放增量。由 aof-use-rdb-preamble 等配置控制（以你版本文档为准）。

注意点：

  1. AOF 损坏需 redis-check-aof 等工具修复意识。
  2. 重写同样涉及 fork，注意高峰窗口。
  3. 纯缓存可关 AOF；会话/库存等「丢了很痛」则不要省这点磁盘。

4. 主从复制

是什么： 主（master）接收写，从（replica）异步复制数据；用于读扩展、数据冗余、故障时人工或自动提升。

全量同步时序（口述）：

部分同步时序：

机制要点：

  1. 复制默认 异步：主写成功不代表从已追上 → 读写分离有延迟，读从可能旧数据。
  2. repl-backlog-size 过小 → 短暂抖动也反复全量 → 主库与网络压力陡增。
  3. 可用 INFO replication 看 master_repl_offset 与从的 lag。

写安全认名： min-replicas-to-write / min-replicas-max-lag 可在从不足或延迟过大时拒绝写入，降低「主写了但从都没跟上就挂」的风险——以丢失容忍度权衡可用性。

注意点：

  1. 全量窗口对大内存实例很重；换机、加从尽量避开业务高峰。
  2. 从库只读；过期语义与版本配置有关，联调验证。
  3. 复制 ≠ 水平写扩展；单主写入上限仍在主。
  4. 网络分区下可能出现旧主「假活」（脑裂相关，哨兵/Cluster 用法定人数缓解，仍需理解风险）。

5. 哨兵（Sentinel）

是什么： 一组哨兵进程监控主从；主客观判定主故障后 自动故障转移，选出新主并通知相关方。适合 单分片（一组主从） 的高可用。

机制要点：

概念 含义
主观下线（SDOWN） 单个哨兵认为主不可达
客观下线（ODOWN） 足够多哨兵同意后确认（法定人数）
领导者哨兵 协调选主与 failover
客户端 经哨兵发现当前主地址（需哨兵感知客户端/SDK）

故障转移口述步骤：

  1. 哨兵探测主失败 → 达法定人数标 ODOWN。
  2. 选举领导者哨兵 → 按规则挑选从库晋升（复制偏移、优先级等）。
  3. 让其他从指向新主 → 发布新主信息（+switch-master 等）。
  4. 旧主若回转，降为从，追数据。

客户端感知： 应用配置哨兵地址列表而非写死主 IP；failover 后通过哨兵查询新主再重连。切换窗口内可能短暂写失败，需重试与幂等。

注意点：

  1. 哨兵本身要多实例（建议奇数、跨故障域）；哨兵挂光则无人自动切。
  2. 转移期间有短暂不可写/连接切换窗口。
  3. 不解决单机内存写满：数据仍在一个主的内存模型里。
  4. 脑裂极端场景：网络分区可能导致「旧主仍被部分客户端写入」——结合 min-replicas-to-write、客户端只信哨兵、以及业务幂等降低伤害。

6. Cluster 与架构选型

是什么： Redis Cluster 将数据按 16384 个哈希槽 分布到多个主节点；每个主可带从，节点级故障可转移。解决 数据量与写吞吐水平扩展。

机制要点：

概念 含义
槽 CRC16(key) mod 16384 定位；{hash tag} 可让相关 key 同槽
MOVED 槽已固定在它节点，客户端应改道并 缓存槽映射
ASK 迁移中的临时重定向（一次有效，勿当永久映射）
跨槽限制 多 key 事务/Lua 要求 key 同槽，否则失败

客户端路由流程：

因此必须使用 支持 Cluster 的客户端；把 Cluster 当单机连只会频踩重定向。

扩缩容认名： 迁移槽位把 key 从甲挪到乙；期间读写作 ASK；运维控流量、盯迁移进度与延迟。

故障转移口述： 某主挂掉 → 其从被选为新主接管槽 → 客户端经重定向更新视图。与哨兵不同：这里是 多主分片 各自 HA。

hash tag 示例： order:{1001}:data 与 order:{1001}:lock 因 {} 内相同而同槽，便于同事务/Lua；滥用会导致槽倾斜。

选型表（生产决策核心）：

形态 解决什么 代价 / 限制 何时用
单机 开发、小流量 无 HA 本地/演示
主从 读扩展、备份 主挂需人工或外挂切换 过渡
主从 + 哨兵 单分片自动 failover 不分片；运维哨兵拓扑 数据单机装得下、要 HA
Cluster 分片扩展 + 分片 HA 跨槽限制；客户端要支持；运维更复杂 容量/写并发超出单主
云托管 少运维、规格化 HA/分片 厂商锁定与费用；能力以文档为准 多数中小团队默认优选

历史 Codis 等：理解「曾用代理分片」即可，新系统优先官方 Cluster 或托管。

7. 缓存架构模式

是什么： 应用、缓存、数据库如何分工。

Cache-Aside（旁路，主推）

为何常见： 缓存失败时可回源 DB；逻辑在应用侧清晰。

其它认名

模式 要点
Read/Write Through 缓存层负责回源/回写 DB，应用只打缓存
Write Behind 先写缓存异步落 DB——吞吐高，丢风险与一致性更难

注意点： 选模式先定「缓存可不可以丢、能否接受短暂不一致」。Pub/Sub 可作失效通知，但不保证每个消费者收到。

8. 穿透、击穿、雪崩

问题 现象 常见手段
穿透 查 不存在 的数据，缓存不中，每次打 DB 参数校验；缓存空值（短 TTL）；布隆过滤器拦不存在 ID
击穿 热点 key 过期瞬间并发打爆 DB 互斥锁重建；逻辑过期（异步更新）；热点永不过期+后台刷新
雪崩 大量 key 同时过期或 Redis 整挂 TTL 加随机抖动；多级缓存；限流降级；Redis HA（哨兵/Cluster/托管）

手段展开：

  1. 空值缓存： SET id:999 "" EX 60——防穿透，TTL 宜短，避免长期占坑。
  2. 布隆： 有 误判（可能判存在实际不存在）——只能作前置拦截；容量与误差率按基数规划；数据删除后布隆难删，需重建或接受假阳。
  3. 互斥重建： 未命中时用短锁，只有持锁者读 DB 回填，其他人稍候再读缓存。
  4. 逻辑过期： value 内带过期时间戳，物理 key 不过期；发现逻辑过期则异步刷新，请求先返回旧值（接受短暂脏读）。
  5. TTL 抖动： 基础 TTL + 随机秒数，避免整点集体失效。

注意点： 三者勿混：穿透是「没有这份数据」，击穿是「有但刚好失效的热点」，雪崩是「大面积同时失效或缓存层挂」。

9. 缓存与数据库一致性

是什么： 双写下缓存与 DB 谁新谁旧。本系列主推 最终一致 的 Cache-Aside。

推荐路径：先更新 DB，再删除缓存

并发脏读窗口（为何还会脏）：

延迟双删、加短锁串行化重建、或消息总线删缓存，都是 缩小窗口，不是消灭不一致。TTL 是最后托底。

延迟双删认名： 写 DB → 删缓存 → 业务稍候再删一次，缓解「回填旧值」窗口；仍是最终一致增强。

注意点：

  1. Redis 不能单独承诺跨系统强一致；要强一致用 DB 约束、单写模型、分布式事务等别套路。
  2. 读从库 + 删缓存时序更易脏读，架构上要承认延迟。
  3. 「更新缓存而非删除」在并发下更难正确，一般不如删。
  4. 预热与降级见 §12。

与 Outbox、本地事务、锁边界的统一决策表，详见 分布式一致性学习。

10. 分布式锁

是什么： 多实例互斥进入临界区。Redis 锁是 尽力而为的协调，不是数据库事务。

最小正确示例：

进阶认名：

能力 说明
续期（看门狗） 业务未完成则延长 TTL——Redisson 等客户端常见
可重入 同线程二次加锁——需客户端约定
红锁 多独立实例上锁定——争议多，面试知概念与批评即可

Pipeline vs 锁： Pipeline 不提供互斥；锁解决互斥，不解决业务多 key 原子（多 key 仍要同槽或外部事务）。

反模式：

  1. SETNX 无过期 → 进程崩溃死锁。
  2. 解锁不校验 token → 误删他人锁。
  3. 持锁时间 ≪ 业务耗时且无续期 → 并发进入。
  4. 用锁「保证库存绝对正确」却不做 DB 约束/对账。
  5. Cluster 下锁 key 与业务 key 跨槽导致脚本失败——用 hash tag。

11. 生产运维清单

领域 要点
容量 maxmemory + 淘汰策略；预留 fork/COW 与碎片余量
磁盘 RDB/AOF 目录空间、写速；备份拷离机
备份恢复 定期拷贝 RDB/AOF；做恢复演练，别等灾难才第一次试
大 Key 监控 MEMORY USAGE；拆分；UNLINK；禁止高峰 KEYS
热 Key 本地缓存、拆 key、读写分离、业务限流
安全 绑定私网、ACL、强密码、rename 危险命令、最小权限
监控认名 命中率、连接数、ops、P99 延迟、used_memory、碎片率、复制偏移/积压、慢日志、拒绝/驱逐数

上线前检查清单：

  1. maxmemory 与 policy 已设；告警接内存、延迟、拒绝连接
  2. 持久化策略与业务丢失容忍度一致；备份任务与恢复演练有记录
  3. 危险命令已禁用/重命名；非公网；ACL 分账
  4. 客户端超时、池大小、Cluster/哨兵地址配置正确
  5. 缓存键均有 TTL 或明确永久理由；TTL 有抖动
  6. 大 Key/热 Key 巡检纳入例行；failover 演练过至少一次

变更习惯： 参数与拓扑变更走变更单；客户端熔断与 Redis HA 一起设计。

12. 预热、降级与开关

是什么： 把「缓存层出问题」当成常态设计，而不是事后救火。

手段 用途
预热 发布/大促前把热点 key 灌进缓存，降低冷启动击穿
降级开关 Redis 超时升高时短路缓存、只读 DB 或返回兜底；配合限流
多级缓存 本地 Caffeine 等 + Redis，削热 Key 与跨机房延迟
空窗保护 互斥重建 + 短空值，避免击穿与穿透叠加

注意点： 降级会增加 DB 压力，必须有限流与熔断；预热名单要可更新，避免灌入过期活动数据。

13. 典型架构口述

  1. 开发单机： 一个 redis-server，可关持久化或开 RDB；无 HA。
  2. 主从 + 哨兵： 单主多从，哨兵自动切主；适合内存单机够用、要自动恢复。
  3. Cluster： 多主分片 + 每主有从；适合容量与写扩展；客户端支持槽路由与 MOVED/ASK。
  4. 云托管： 选规格与架构模板；确认备份、多 AZ、参数白名单与限流。

口述模板：「数据量约 X，QPS 约 Y，丢失容忍约 Z 秒；选形态 A；Cache-Aside + TTL 抖动；穿透用空值/布隆；击穿用互斥；Redis 挂了走降级限流回源。」

总结

持久化决定「挂了丢多少」；哨兵/Cluster/托管决定「挂了谁接手、能否分片」；缓存三大问题与删缓存策略决定「会不会打爆 DB」；锁只解决互斥；预热/降级决定「坏了业务是否还活」。下一篇用自检与面经题收口。
