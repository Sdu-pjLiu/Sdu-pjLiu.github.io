测试框架学习-软件测试基础与工程实践

发表于 2026-07-29 更新于 2026-08-20 分类于 计算机
测试概念三维对照、分层与类型、用例设计（含边界测试）、替身、可测设计；AB 实验认名。

本系列入口。先建立 与具体框架无关 的测试口径：测什么、怎么设计用例、怎么隔离、怎样才算好测试；再进入 Python 测试工具链 与 Go 测试工具链。

0. 本篇位置与边界

本文 后续工具链
概念、方法、工程判断 pytest / Go testing 等「怎么写」

不做： ISTQB 全文背诵、测试管理平台操作、浏览器 E2E、性能/安全专项工具链、AB 实验平台与统计深挖。

下一步： Python 测试工具链

1. 概念三维对照（防混淆）

口语里常把「单元测试、边界测试、AB Test」并列，其实它们 不在同一轴：

轴 回答的问题 例子
分层 测多深、依赖多少 单元、组件、集成、E2E
类型 测什么目的 功能、回归、冒烟、性能、验收
设计方法 用例输入怎么选 等价类、边界值（边界测试）、判定表
（相关）可见性 是否看实现 黑盒、白盒、灰盒
（相关）替身 怎么隔离依赖 stub / mock / fake
（相关）产品实验 线上哪个方案更好 AB Test（非质量单测主线）

组合示例（正确说法）：

  • 「在 单元层 用 边界值 做 功能回归」——三轴都清楚。
  • 「做个边界测试」——通常指设计方法，常落在单元/接口层执行。
  • 「做个 AB」——产品分流实验，不是 pytest/go test 那类自动化质量测试。

单元测试 ≠ 测试的全部：单元只是分层中的一层；本系列以单元/组件为主，是因为反馈快、成本低，不是因为其它层不存在。

2. 测试目的与质量观

概念 含义
验证（Verification） 是否按规格做对（做对了没有）
确认（Validation） 是否做了该做的事（做对了事情没有）

测试能提高发现缺陷的置信度，不能证明无缺陷。覆盖率、用例数都是信号，不是质量证书——与工具链中「覆盖率≠质量」同一口径。

缺陷越早发现成本通常越低：单元层便宜，生产上才发现最贵。

3. 测试分层

层级 典型对象 速度/稳定性 本系列
单元 函数、类、小模块 快、稳 主线
组件 / Handler HTTP Handler、无真端口 较快 Go httptest 主线
集成 真 DB、真消息、多模块接线 较慢、较脆 点到为止
契约 服务间 API 合同 中 认名
E2E 浏览器/全链路 慢、贵 不做

测试金字塔： 底层多、上层少。若团队大量依赖 UI E2E（「冰淇淋」反模式），反馈会慢且脆——应把断言下沉到单元/组件。

同一套 边界值用例，可以写在单元层，也可以写在接口/集成层；变的是分层，不是「边界」本身。

4. 测试类型（认名）

类型 一句话 备注
功能测试 行为是否符合需求 日常主量
回归测试 改动后旧行为是否仍成立 自动化单测多属此类
冒烟测试 主路径能否快速通 子集；比全量回归更短
验收测试 是否达到可交付标准 常含业务验收口径
探索性测试 不预设脚本、边学边测 补自动化盲区；本系列不深挖
性能 / 安全 / 兼容 专项质量属性 只认名

冒烟 vs 回归： 冒烟问「能不能开机」；回归问「改完旧能力还在不在」。冒烟失败通常应挡住更深测试。

研发日常主业通常是 功能 + 回归 的自动化（落在单元/组件层最多）。

4.1 AB Test（产品实验，认名）

维度 说明
是什么 用户分流到 A/B 方案，比转化、留存等 业务指标，用统计决策
解决什么 「哪个产品方案更好」，不是「这段代码有没有 bug」
典型链路 分流 → 埋点 → 指标 → 显著性
与本系列 非主线；质量保障仍靠分层测试与用例设计

不要把 AB 与单元/边界并列成「三种测试方法」。需要实验平台、样本量、功效分析时另开专题。

5. 用例设计方法（框架之前）

框架（parametrize、table-driven）只是 把已设计好的用例跑起来；设计本身在前。

方法 要点 落到工具
等价类 同类输入期望同类行为，每类取代表 表的一行
边界值（边界测试） 边界及其内侧外侧易错；口语常称边界测试 0、空、max±1
判定表 多条件组合 → 动作 多列表格
状态迁移 合法/非法迁移 按状态列用例
错误猜测 经验：空针、超时、重复提交 错误路径行
配对/两两 多因子时降组合爆炸 控制 parametrize 规模

口诀：先等价类与边界，再谈穷举；错误路径与 happy path 同权重。

5.1 黑盒 / 白盒 / 灰盒（可见性，认名）

叫法 含义 与设计方法
黑盒 不看实现，按规格与接口选输入 等价类、边界值常用黑盒视角
白盒 看分支/路径，按结构补测 常与分支覆盖、条件覆盖配合
灰盒 知部分结构（如状态、错误码） 接口测常见

边界值 既可以 黑盒推出（规格上下限），也可以 白盒加强（某分支临界条件）。轴是「可见性」，不是「分层」。

6. 测试替身谱系

类型 行为 典型用途
Dummy 占位，几乎不用 凑参数
Stub 固定返回，不关心如何被调 简单下游
Spy 记录调用供事后断言 校验是否通知过
Mock 预设期望，交互不符则失败 严格交互
Fake 可用的简化实现（内存库） 可读、少生成代码

对照本系列：

  • Python：MagicMock / mocker 常充当 stub+spy+mock；手写对象可当 fake。
  • Go：优先手写 fake；需要严格交互再用 GoMock。

术语混用很常见；面试时能按上表澄清即可。

7. 好测试的属性

FIRST（常用口径）：

字母 含义
Fast 快，默认可频繁跑
Independent 独立，不靠顺序
Repeatable 可重复，同环境同结果
Self-validating 自验证，成败由断言决定
Timely 及时，与代码一起演进

结构：AAA / Given-When-Then

  1. Arrange / Given：准备
  2. Act / When：执行
  3. Assert / Then：断言

一个用例优先验证 一个行为；失败信息应能定位原因。

8. 可测设计

测试难，往往是设计难测，而不只是「不会用框架」。

手段 作用
依赖注入 测试可塞替身
纯函数 无 IO，最好测
副作用外置 IO 在边界，核心可单测
面向接口（Go） 替换实现成本低

反模式：巨石函数、隐藏全局单例、构造时就连外网。

9. 脆性与偶发失败（Flaky）

常见根因 处理方向
共享可变状态 / 顺序依赖 fixture/Cleanup、独立数据
真实时间、随机 注入时钟/种子
外网、真第三方 mock/fake；集成另跑
异步竞态 显式等待或同步化；Go 加 -race
盲目重试变绿 慎用；优先修根因

偶发红会腐蚀信任：人们开始忽略失败。

10. 断言与预言机

问题 说明
弱断言 只断言「不抛异常」→ 假绿
过强断言 绑死无关字段/调用次序 → 脆
预言机 如何知道期望值：规格、对照实现、不变量、差分

属性测试（Hypothesis / Go fuzz）本质是用 不变量 当预言机的一种。

11. 度量与流程（不绑 CI 产品）

度量 口径
行覆盖 行是否执行过
分支覆盖 if/else 等分支是否走过
变更覆盖 diff 是否被测到（团队可选）

流程建议：PR 默认跑快测（单元）；夜间/主分支可加集成；覆盖率作 防回退，不作唯一 KPI。

12. TDD / BDD（认名）

方法 一句话
TDD 红 → 绿 → 重构；用失败测试驱动实现
BDD 用业务可读场景（Given-When-Then）表达行为

本系列不强制宗教式流程；需要时借用其结构即可。Go 侧 Ginkgo 等 BDD 框架仅在工具链中点到。
