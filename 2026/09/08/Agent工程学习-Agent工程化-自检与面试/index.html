AI-Agent工程学习-Agent工程化(自检与面试)

发表于 2026-07-23 更新于 2026-08-20 分类于 计算机
Agent 工程化（一）～（四）学习自检与面试导向问答；覆盖 Runtime、观测、韧性与部署。

本文是 Agent 工程化（一）～（四）的阶段验收。目标不是背组件名，而是能把 State/会话/生命周期、观测、韧性、部署 串成可上线口径，并与已学框架回链对齐。

0. 使用说明

建议先遮住「推荐回答」，在 60～120 秒内口述。面试题侧重故障分类与架构边界。

回答时重点检查四件事：

  1. 是否区分运行态与持久态、thread 与 Run。
  2. 是否区分 Trace 排障与 Dataset 回归。
  3. 是否先做错误分类再谈重试，写路径是否幂等。
  4. 是否分清图内事件与跨服务 MQ。

1. 分篇自检

1.1（一）Runtime

S1. 运行态与持久态如何分工？

推荐回答： 运行态是当前步可见的 messages/中间结果，可被摘要策略触及；持久态是 Checkpointer/@persist/外存快照，跨请求可恢复。治理字段（Contract、预算、open[]、副作用）必须进结构化持久 State，不能当普通消息交给摘要改写。

S2. 为何不宜把 Session 当框架一等概念硬套？

推荐回答： LangGraph 等以 thread_id 标识 checkpointer 线程；口语 Session 易与产品会话混淆。生产用 thread_id + 租户前缀表达会话边界与隔离，resume 须校验所有权。

S3. Lifecycle 中 interrupted 与 budget_exceeded 各禁止什么？

推荐回答： interrupted 禁止把暂停当成功；budget_exceeded/partial 禁止标 Success，应 Checkpoint + handoff note + 部分结果边界说明。

S4. Run ID 与 Invocation ID 分别解决什么？

推荐回答： Run ID 关联一次用户目标的日志、Trace、成本；Invocation ID 标识单次模型/工具调用，作幂等键与副作用对账。API 应回传 run_id。

S5. 优雅收尾最低交付物？

推荐回答： Checkpoint（合同、计划、open/done、关键 Observation、预算、副作用）、handoff note（原因、策略、缺口、建议下一步）、面向用户的带边界部分结果。续跑只处理 open[] 并分配新显式预算。

1.2（二）Observability

S6. Logging 三条硬要求？

推荐回答： 结构化字段含 run_id/thread_id/tenant_id；脱敏禁密钥与完整 Prompt/PII；每条可关联 Trace。

S7. Trace 与 Experiment 分工？

推荐回答： Trace 看「这一次为什么错」；Dataset+Experiment 看「这一版是否整体退化」。发版标准仍以 Agent（四）§6 Checklist 为 canonical，平台只承载。

S8. 多 Agent Trace 如何过滤子 Agent？

推荐回答： 用 metadata（如 lc_agent_name）过滤 subagent span，避免只看最终回答或把子 Trace 全文灌回主窗。

S9. 生产 Metrics 最小集？

推荐回答： Task Success、假完成率、P95、重试率、HITL 等待、Gate 拦截率；告警挂预算、错误率、下游故障。

S10. LangSmith 与 OpenTelemetry 如何并存？

推荐回答： 本路径以 LangSmith 为主做 Agent Trace/Eval；OTel 用于跨微服务导出与关联。要求 run_id 等属性可打通，不强制自建完整 Collector 教程。

1.3（三）Reliability

S11. 429 与 403 重试策略差异？

推荐回答： 429 可重试，尊 Retry-After，指数退避+抖动+总时限；403 通常权限/策略拒绝，原样重试无意义，应停止或改权限路径。

S12. Fallback 层级从高到低？

推荐回答： 换模型 → 缩 scope → 只读降级 → HITL → 明确失败（partial+handoff）。路径须进 Trace 并计成本。

S13. Timeout 为何要分层？

推荐回答： 单工具/单模型/墙钟总超时/步数 Token 硬顶各管一类挂死；仅总超时无法提前挡住单步风暴。超时后收尾而非假完成。

S14. 熔断 open 状态做什么？

推荐回答： 短时拒绝下游调用，直接走 Fallback，避免打爆故障依赖；half-open 探测后决定关闭或再开。

S14b. 口述 5xx → open → half-open 时序。

推荐回答： 连续失败达阈值 → open（新请求 Fallback）→ 冷却后 half-open 少量探测 → 成功则 closed，失败再 open。限制探测并发防惊群。见工程化（三）§5.1。

S15. 写工具重试前三件套？

推荐回答： 幂等键、状态查询是否已成功、必要时补偿。Reducer 不保护图外副作用。

S15b. 写工具带 invocation_id 重试如何防双写？

推荐回答： 先查业务表是否已有该幂等键；无则插入并 UNIQUE 约束挡并发；超时后同键重试只补状态。跨服务落库+入队走 Outbox。见工程化（三）§6.2。

S16. 流式中断为何不能盲目完整重试？

推荐回答： 用户可能已看到部分输出；完整重试会导致重复拼接。应记录已发送边界，续传或声明截断。

1.4（四）Deployment

S17. /invoke /stream /resume 各解决什么？

推荐回答： invoke 同步或短任务；stream 流式体验；resume 从 interrupt/HITL 带 thread_id 与决策继续。均需鉴权与租户上下文，回传 run_id。

S18. 何时必须上 Worker Queue？

推荐回答： 长任务、批处理、等人审后续跑不宜堵死 HTTP 进程；API 入队返回 job_id，Worker 执行并写 Checkpoint/回调。

S19. Checkpoint 生产存储如何选型？

推荐回答： 开发可用 SQLite/内存；生产优先 PostgreSQL 等权威持久后端。Redis 适合作 broker/缓存，不宜作为唯一长期会话库（除非明确短 TTL）。

S20. 图内 Event Bus 与跨服务 MQ 边界？

推荐回答： Flow @listen/图边是单应用内编排；跨服务须显式 Redis/Celery/Kafka 等，并做幂等、顺序与 DLQ。Flow 事件不等于生产总线。

S21～S28. 速查

题 要点
S21 Serverless 长跑 时限与冷启动；状态外置；重活改常驻 Worker
S22 Batch 限速、逐条 run_id、DLQ、断点续跑
S23 readiness DB/Redis/凭据就绪再接流量
S24 Celery 角色 异步执行与重试钩子
S25 Docker 可复现运行时；密钥环境注入
S26 取消 协作式取消 + 冻结新写副作用
S27 背压 队列深度告警；拒绝或降级
S28 密钥 仅环境/密钥管理；正文不写真实值

S29. 记忆/Session 如何选型与隔离？过期怎么做？

推荐回答： 权威会话用 PG Checkpointer；热缓存用 Redis；语义记忆用向量且检索前 tenant filter。resume 校验 thread 所有权。TTL/归档/用户删除须级联向量与业务表。见工程化（一）§2.1。

S30. 日/次预算熔断如何与 Metrics、路由配合？

推荐回答： 简单任务小模型、复杂任务大模型；run 与租户日硬顶；触顶停写并打 budget_exceeded；告警与熔断联动。见工程化（二）§4.1。

S31. Agent 长任务为何上队列？如何防丢防重？

推荐回答： 避免堵 HTTP、支持崩溃恢复与 HITL。至少一次 → 幂等；Outbox 保证「落库+入队」；失败进 DLQ。对照 消息队列基础。见工程化（四）§2.1。

S32. 写工具审计最少记什么？

推荐回答： tenant/user、工具名、参数摘要、invocation_id、结果码、时间；权限分级 + HITL；与一致性篇/Outbox 同口径。见工程化（三）§6.1、MCP（四）§2.1。

2. 面试题

I1. 设计一个可 HITL 的 Agent API，说明 ID 与状态机。

推荐回答： 鉴权后创建 run_id 与 thread_id；invoke/stream 进入 running；高风险工具 interrupt 并 persist；客户端 resume 带决策；取消走 cancel 冻结写。状态含 interrupted/partial/failed；日志 Trace 全链路带 run_id。持久态用 PG Checkpointer。

I2. 线上假完成率上升，你如何用观测定位？

推荐回答： Experiment 对比发版前后 Task Success/假完成；抽样 Trace 看 Gate 是否被绕过、预算撞顶是否标 Success、子 Agent 是否假摘要。对照 Agent（四）§6，修 Gate 与收尾，而非只加 Prompt。

I3. 模型商连续 5xx，如何保护系统？

推荐回答： 熔断 open → Fallback（备用模型/缩 scope/只读）；Metrics 告警；半开探测。队列任务进有限重试后 DLQ。避免无限重试打爆对方与自身线程池。

I4. Multi-Agent Voting N=5 成本暴涨，工程侧控什么？

推荐回答： 预算硬顶、按角色 Token 账单、动态降 N、超预算 Fallback；Trace 按角色汇总。协作层减 N 或改 Role-Based——回链 Multi-Agent 成本模型。

I5. 为何 interrupt 恢复要求节点前半段幂等？

推荐回答： 恢复可能使节点从函数开头重跑；若前半段已写库/发消息，无幂等会双写。副作用用 invocation_id 或移到确认后执行。

I6. 自托管与 LangSmith Deployment 如何分工口述？

推荐回答： 自托管掌控 VPC、队列、自定义 MQ；托管减少运维换平台约束。无论哪种，Checklist、Gate、幂等与租户隔离不因托管而省略。

I7. 事件驱动 Flow 上线前检查什么？

推荐回答： 消费者幂等、重复投递、顺序键、DLQ、与图内事件边界文档化；跨服务不误用 @listen 当总线。

I8. 如何向评审说明「可观测已达标」？

推荐回答： 任意失败 run 可在 5 分钟内用 run_id 打开 Trace；发版有 Dataset 对比；成本/Token 按 run 可查；告警覆盖错误率与预算；日志无密钥泄漏。

I9. 设计可 HITL 恢复的 Agent API，并说明长任务队列如何防丢防重。

推荐回答： /invoke/stream/resume + run_id/thread_id；高风险工具 interrupt；状态 PG Checkpointer。长任务 API 入队：Outbox、至少一次消费、幂等键、DLQ；取消冻结写副作用。见（一）（四）与 MQ 基础篇。

I10. 「用户要求忘记我」时记忆层要删哪些？

推荐回答： Checkpointer/会话表、业务偏好表、向量记忆（tenant+user 过滤删除）、对象存储附件；审计可留脱敏痕迹按合规。漏删向量 = 仍可被语义检索。
