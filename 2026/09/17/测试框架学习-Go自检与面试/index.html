测试框架学习-Go自检与面试

发表于 2026-08-02 更新于 2026-08-20 分类于 计算机
Go 测试工具链自检与面试导向问答；覆盖 table-driven、Testify、GoMock 与 httptest。

完成 软件测试基础 与 Go 测试工具链 后，重点是能按业务约束选择 table-driven、断言风格、接口 mock 与 HTTP 测法。本篇用自检题验收，并用公开实践文/题库中的高频点训练表达。

0. 使用说明

建议先遮住「推荐回答」，在 60～120 秒内口述：

  1. 先给结论（用标准库还是加 Testify/GoMock）。
  2. 说明机制（t.Run、require、EXPECT、Recorder）。
  3. 点出风险（脆 mock、假高覆盖、泄漏 Server）。
  4. 落到工程措施（-race、cover、Cleanup、接口注入）。

1. 学习自检

1.1 testing 与 table-driven

S1. 为什么 Go 社区默认推荐 table-driven + t.Run？

推荐回答： 把输入/期望收成表，一套逻辑跑多行，便于加边界；t.Run(name) 让失败定位到具体用例，并支持 -run 单跑子测试。相比复制多个 TestXxx，表驱动更易维护，也是代码评审的常见期待。

S2. t.Errorf 与 t.Fatalf 如何选？

推荐回答： 后续断言仍有意义时用 Error；前置失败（err、nil）用 Fatal 立即结束当前（子）测试，避免空指针连锁。表驱动里常对 wantErr 分支 Fatal/提前 return。

S3. -race 与 -cover 各回答什么问题？

推荐回答： -race 检测数据竞争；-cover 看执行痕迹。二者都不能证明逻辑正确。并发包应常规跑 race；覆盖率用于找未测分支与防回退，而非 KPI 刷到 100%。

1.2 Testify

S4. assert 与 require 的本质差别？

推荐回答： assert 失败继续，适合收集多个字段差异；require 失败即停，适合前置条件。典型写法：require.NoError 后再 assert.Equal。

S5. 小项目是否必须引入 Testify？

推荐回答： 不必。标准库足够；断言变啰嗦或团队统一风格时再引入。引入后仍应保持 table-driven，而不是用 suite 包办一切纯函数测试。

1.3 GoMock 与可测设计

S6. 为什么说「先接口，后 mock 框架」？

推荐回答： Go 通过接口替换依赖。没有接口就很难干净 mock。业务 struct 依赖 UserRepo 接口，测试注入 fake/mock。框架只是生成与校验期望的加速器。

S7. 何时手写 fake，何时 GoMock？

推荐回答： 接口方法少、行为简单 → 手写 fake，可读且重构靠编译器。方法多、要断言次数/参数/次序 → GoMock/mockgen。不要默认上重型 mock。

S8. EXPECT 写太死有什么后果？

推荐回答： 与实现细节绑死，无关重构也红。应对无关键参数用 Any()，只断言影响行为的交互；行为测试优先于交互测试。

1.4 httptest

S9. NewRecorder 与 NewServer 如何分工？

推荐回答： Recorder 不启端口，直接 ServeHTTP，适合单测 handler/中间件链。NewServer 给真实 URL，适合测自研 client 或轻量端到端。都要用 Cleanup 关闭 Server。

S10. Handler 依赖 DB/下游时，httptest 够不够？

推荐回答： httptest 只解决 HTTP 进出边；依赖仍需注入 fake 或 GoMock。三者组合：Recorder 调 handler，handler 内 service 用假 repo。

S11. 单元测试与集成测试在 Go HTTP 场景怎么划？

推荐回答： 单元：Recorder + fake，快、无外网。集成：测试容器/真 DB 或契约测试，少而精。不要把外网调用塞进默认 go test ./...。

S12. 与 Ginkgo 等 BDD 框架比，本系列为何以标准库为主？

推荐回答： 标准库 + table-driven 是 Go 主流与面试默认语境；BDD 适合团队统一风格的大型套件。本系列点到即可，不深挖。

1.5 基础概念与工具细节

S13. 内部测试包与外部测试包如何选？

推荐回答： package foo 可测未导出符号，适合白盒；package foo_test 只测公开 API，更接近用户、强迫可测设计。关键逻辑优先能通过外部包测通。

S14. TestMain 适合放什么？不适合放什么？

推荐回答： 适合包级一次性资源（测试库、共享进程）。不适合把每个用例的业务数据准备塞进 TestMain，否则耦合与泄漏风险高；用例级用 t.Cleanup 或 suite。

S15. Eventually 解决什么？滥用有何风险？

推荐回答： 异步条件在超时内变为真时轮询断言。滥用会掩盖竞态、拖慢套件；能同步化或注入通道时优先确定性等待，并配合 -race。

S16. Recorder 上 Code 为 0 是什么情况？

推荐回答： Handler 未调用 WriteHeader 且未触发隐式写入时，Recorder 的 Code 可能仍为 0；用 Result() 可得到带默认状态的响应。断言前应理解这一差异。

S17. InOrder 何时用、何时不用？

推荐回答： 业务确实要求调用次序时用。无关次序绑死会导致重构脆失败；多数场景 EXPECT + Times + 行为断言即可。

2. 面试真题

以下题目按主题归纳、改写自公开实践文与题库，用于训练表达，并非逐题对应某一场真实面试；综合参考来源见文末「参考面经与题库」。

I1. 你们 Go 项目单测的基本范式是什么？

推荐回答： *_test.go + TestXxx，默认 table-driven 与子测试命名；纯逻辑少依赖标准库断言或 Testify；外部依赖面向接口，必要时 GoMock/手写 fake；HTTP 用 httptest。PR 跑 go test ./...，关键包加 -race，覆盖率作防回退而非唯一门禁。

I2. 请现场说一段 table-driven 的结构该长什么样。

推荐回答： 切片元素含 name、输入字段、want / wantErr；for + t.Run(tt.name, ...)；错误路径与边界行数不少于 happy path。强调可单独 -run 子测试。

I3. assert 和 require 怎么讲给同事听？

推荐回答： 用「失败后还能否继续」区分：require 管门槛，assert 管核对。err 与非空用 require，多字段相等用 assert。避免 err 后继续解引用造成噪音失败。

I4. 有外部 API 调用时单元测试怎么做？

推荐回答： 优先把调用收在接口后，测业务时 mock 接口；测 HTTP client 本身可用 httptest.NewServer 固定响应。避免单测打真实外网。若历史代码难抽接口，再评估传输层拦截类库，但设计上仍应推动可注入。

I5. gomock 和 testify 如何搭配？

推荐回答： gomock 负责依赖行为期望；testify 负责结果断言。Controller 绑定 t，结束时校验 EXPECT。接口小可不用 gomock。二者都只出现在 _test.go。

I6. 如何测试 HTTP Handler 且不监听业务端口？

推荐回答： httptest.NewRequest + NewRecorder，调用 handler.ServeHTTP；断言 Code、Header、Body。需要完整路由/中间件时组装与生产一致的 Handler，仍用 Recorder；需要真实 URL 再 NewServer。

I7. 覆盖率很高但线上仍出 bug，可能因为什么？

推荐回答： 只测正常路径、断言弱、mock 掉了真实分支、未跑 race、集成路径未覆盖。应用 table 补边界、审查缺失行、对关键接线做少量集成测试。

I8. 什么时候不该用 mock？

推荐回答： 被测就是算法/纯函数时直接测；mock 成本高于收益的小接口用手写 fake；为了覆盖率去 mock 被测函数本身是反模式。mock 服务隔离，不服务虚荣指标。

I9. t.Parallel 使用时要注意什么？

推荐回答： 用例必须无共享可变状态；表驱动子测试并行时注意循环变量与共享 fixture。与 -race 联用更能暴露问题。不理解隔离时宁可不并行。

I10. 请对比 Recorder 测 handler 与启动真服务器测的差异。

推荐回答： Recorder 快、无端口、测合同清晰；真服务器更接近部署但慢、脆、要清理。默认单测用 Recorder/NewServer（测试用），预发/冒烟再用真部署环境。

I11. 如何向面试官证明你写过「能拦 bug」的测试？

推荐回答： 讲一个真实缺陷：先补失败用例（表中一行或 httptest 场景），再修代码变绿；说明边界与错误码断言，而不是只报覆盖率数字。能讲清 Fatal/require 避免假绿连锁。

I12. Go 1.18+ fuzz 与本系列 Hypothesis 有何概念对应？

推荐回答： 都属生成式/模糊寻找反例的思路。Go 用 FuzzXxx 内建；Python 常用 Hypothesis。本系列 Go 主线仍是 table-driven + httptest，fuzz 可作为加分项一句带过。

I13. 「单元测试、边界测试、AB Test」分别属于什么？

推荐回答： 单元是分层；边界值是用例设计（可落在单元层执行）；AB 是线上产品实验，比业务指标而非代码正确性。质量保障主线仍是分层 + 设计方法 + 自动化，AB 另册。见基础篇 §1/§4.1。

I14. -short 与 build tag 如何分工跑集成测？

推荐回答： -short 让用例内 testing.Short() 跳过慢路径，适合同一包内区分。build tag / 独立目录把集成测彻底隔离出默认 go test ./...，避免 CI 默认变慢。二者可组合：默认短测，夜间加 tag。

I15. 请区分 fake 与 GoMock，并说明你会怎么选。

推荐回答： fake 是简化可用实现，可读、重构靠编译器；GoMock 生成替身并校验 EXPECT，适合方法多、要断言交互。接口小优先 fake；交互合同复杂再 GoMock。对应基础篇替身谱系。
