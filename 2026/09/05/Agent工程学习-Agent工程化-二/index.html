AI-Agent工程学习-Agent工程化(二)

发表于 2026-07-22 更新于 2026-08-20 分类于 计算机
Agent 工程化观测层：Logging / Tracing / Metrics / Cost / Token；LangSmith 与 OpenTelemetry 生产口径。

接 Agent 工程化（一）：Runtime 身份与生命周期已定；本篇讲 如何看见系统在做什么——Log、Trace、Metrics、Cost/Token，以及 LangSmith / OpenTelemetry。

系列导航： （一） · （二）本篇 · （三） · （四） · 自检

0. 本篇位置

观测回答三个问题：这一次为何错（Trace）、整体是否退化（Eval/Metrics）、钱与延迟花在哪（Cost/Token）。

回链：LangChain（六）§4 LangSmith（轻量） · Agent（四）§6 发版 Checklist。本篇升为 生产口径，不重复平台点选教程。

1. Logging

要求 说明
结构化 JSON 字段：run_id、thread_id、tenant_id、level、event
脱敏 禁止落密钥、完整 Prompt、用户 PII 原文；必要时哈希或截断
关联 每条日志可跳到对应 Trace span
级别 业务异常与 Gate 拦截用 warning/error；调试细节可采样

反模式： print 调试残留、把 Tool 全量返回值写入 INFO、无 run_id 的散落日志。

2. Tracing

Span 层级 典型内容
run 用户目标、起止、最终状态（success / partial / failed）
node / step 图节点或 Flow 步骤 Input/Output 摘要
model 模型名、token、延迟、finish_reason
tool 工具名、参数摘要、错误码、invocation_id
subagent 子 Agent 边界；主窗不灌全文 Trace

多 Agent 过滤： LangChain / Deep Agents 可用 lc_agent_name 等 metadata 只看子 Agent span——回链 Deep Agents（四）、Deep Agents（五）§4。

原则： 排障看轨迹；发版看 Dataset——二者互补，不做第二套互相矛盾的标准。

3. Metrics

生产最小集：

指标 含义
Task Success 对齐 Contract / LE Gate，非「模型说完成」
假完成率 标成功但 Gate/人工判缺口
P95 延迟 端到端与关键节点
重试率 模型/工具可恢复重试占比
HITL 等待 排队时长、超时放弃率
Gate 拦截率 输入/输出/工具护栏触发

告警建议挂在：预算耗尽突增、错误率、Gate 拦截异常、下游 5xx——与（三）熔断联动。

4. Cost Tracking / Token Tracking

维度 拆什么
Token prompt / completion / cache hit；按 run、角色、工具汇总
Cost 按模型单价折算；含重试与 Voting×N 放大
预算 软顶告警 + 硬顶停写；对齐 Runtime 预算字段

Multi-Agent 成本 ≈ 角色数 × 轮次 ×（可选 Voting N）——回链见 Multi-Agent（三） 成本模型。

4.1 模型路由、预算熔断与 Metrics 联动

是什么： 成本控制 = 路由（用对模型）+ 预算（硬顶）+ 观测（能看见谁在烧钱）。

机制 做法
模型路由 简单分类/改写 → 小模型；复杂推理/写工具前决策 → 大模型；失败可 Fallback 升档
次/日预算 每 run 硬顶（token/¥）；每租户日顶；超顶 → 停写工具 + partial + handoff
与 Metrics cost_per_run、budget_exceeded_rate、按模型拆分；突增告警联动熔断（三）

注意点： 只告警不硬顶 → 账单爆炸；路由只按「感觉」不按任务类型 → 浪费；日预算不清零窗口 → 误杀正常流量。

5. LangSmith（生产口径）

能力 用途
Trace 单次 run 排障：tool_calls、Middleware、token、节点 state
Graph 可视化 LangGraph 走错边、卡点定位
Dataset + Experiment 固定 Scenario 集回归；对齐 Agent（四）§6
Engine（认名） 监控与异常检测；细节属平台篇

分工：

CrewAI 侧用 AMP / tracing=True 看 Task timeline；与 LangSmith 生态对照见 实现框架对比 §10。

6. OpenTelemetry

项 口径
定位 跨服务 Trace/Metrics 导出标准；Agent 平台可对接
做法 Run/span 属性带 run_id、thread_id；导出到现有 APM
边界 本路径以 LangSmith 为主战场；OTel 解决「多微服务一条链路」

不要求本系列实现完整 Collector 配置；要求清楚：Agent Trace 与业务 HTTP Trace 可关联。

6.1 run_id 与 Trace 同现（对账约定）

层 约定
入口 HTTP span 属性写入 run_id、tenant_id（鉴权后可知）
Agent run span 同一 run_id；子 span（model/tool）继承或显式挂上
传播 跨服务用 W3C traceparent；业务日志仍打 run_id，避免只能靠 hex trace_id 人工对账
不做 本系列不配 Collector/Exporter 教程

业务服务侧日志 / Metrics / Trace / CI 门禁的完整口径，见 后端服务工程 · 可观测与 CI/CD（本篇专注 Agent Run）。

总结

Log： 结构化、脱敏、可关联 Trace。

Trace： run→node→model/tool/subagent；多 Agent 用 metadata 过滤。

Metrics / Cost / Token： 成功率与假完成、P95、预算；按角色放大成本可见。

LangSmith： Trace 排障 + Experiment 回归；Checklist 不换标准。

OTel： 跨栈导出认名到可对接。
