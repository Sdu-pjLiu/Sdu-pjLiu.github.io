消息队列学习-基础模型与通用工程问题

发表于 2026-08-06 更新于 2026-08-20 分类于 计算机
消息队列一篇打底：为何用 MQ、投递语义、丢消息/重复/顺序/积压四大工程问题，以及重试死信与 Outbox 认名。

本系列入口。先建立 与具体产品无关的可靠性心智：解耦与削峰、至少一次与幂等、顺序与积压；再进入 Kafka 核心与生产实践 把主路径写透，并在对照篇完成三大 MQ 选型。

0. 本篇位置与边界

做 不做
通用模型与丢/重/乱/积压 某一云厂商控制台逐步截图
与 RPC/本地消息表关系 Broker 源码逐函数精读
为 Kafka / Rabbit / Rocket 打底 Pulsar / ActiveMQ 深挖

与 Redis 边界： Redis 的 List / PubSub / Stream 可作简易队列或通知，但 可靠投递、长期积压、多消费者运维、跨服务契约 以本系列专业 MQ 为准。Stream 能力边界见 Redis 篇，不在此重复产品化。

各节结构：是什么 → 机制 → 示例/时序 → 注意点。

1. 为何用消息队列

是什么： 消息队列（MQ）在服务之间传递异步消息，使调用方不必同步等待下游完成。

典型收益：

收益 说明
解耦 上游只发事件，下游可独立演进、增减消费者
异步 耗时工作（发邮件、算分、通知）移出请求路径
削峰 流量尖刺先进队列，消费者按能力消化
最终一致 用「事件 + 补偿」替代处处分布式事务

何时不该用：

  1. 强同步、强一致、必须立刻知道成败的路径（下单扣款本身仍常走 DB 事务）。
  2. 流量很小、调用链简单——引入 MQ 增加运维与排障成本。
  3. 把 MQ 当数据库：长期查历史、复杂查询不该压在 Topic 上。

注意点： MQ 解决的是 异步协作与缓冲，不是自动保证业务正确；正确性靠幂等、对账与补偿。

2. 核心抽象

是什么： 各产品名词不同，心智可统一为三类角色。

角色 职责
Producer 发送消息
Broker（集群） 接收、存储、转发
Consumer 拉取/推送并处理

Topic vs Queue（认名）：

  • 发布订阅 / Topic： 一条消息可被多个订阅组各自消费（Kafka Topic + Consumer Group；Rocket Topic）。
  • 点对点 / Queue： 一条消息通常只被一个消费者拿走（Rabbit 队列语义更贴近）。

选型时先问：要广播给多种下游，还是任务只处理一次。

3. 投递语义（工程现实）

语义 含义 工程现实
最多一次 at-most-once 可能丢，不重 吞吐优先、可丢日志
至少一次 at-least-once 不丢，可能重 最常见默认目标
恰好一次 exactly-once 不丢不重 需 Broker + 客户端事务/幂等链路；业务仍建议幂等

结论： 面试与生产都优先做到「至少一次 + 业务幂等」。迷信「开了 exactly-once 就万事大吉」会在重试、多系统、人工补单处翻车。

4. 丢消息（三段链路）

是什么： 消息在「生产确认 → Broker 落盘/副本 → 消费 ACK」任一环失败且未正确处理，即表现为业务侧「没发生」。

阶段 典型丢法 通用对策方向
生产 发完不等确认就当成功；超时当失败却未重试策略 等待 Broker ACK/Confirm；失败重试+本地记录
Broker 只写单机内存；副本不足仍报成功；磁盘坏 持久化 + 多副本；写成功条件收紧
消费 未处理完就 ACK；进程崩溃在 ACK 后业务未落库 先业务成功再 ACK；失败重试/死信

时序（至少一次心智）：

注意点 / 反模式：

  1. 客户端超时重试但无幂等 → 变重复而非「只丢」。
  2. 自动提交 offset 开太大 → 未处理完已提交 → 真丢。
  3. 只保证其中一段，其它两段裸奔。

5. 重复消费与幂等

是什么： 至少一次必然可能重复；网络重试、Rebalance、ACK 超时都会再投递。

幂等手段（由易到难）：

手段 做法
业务唯一键 订单号/消息 ID 唯一索引，插入冲突则跳过
状态机 仅允许「待支付→已支付」等合法迁移
去重表 处理前查「已处理消息 ID」
天然幂等 按最终状态覆盖写（set 成某值）

口诀：先幂等，再调 MQ 参数。 参数降低重复概率，幂等消灭重复危害。

5.1 消息 ID 与幂等规范

项 建议
eventId / messageId 生产侧生成 UUID（或业务流水号），放入 header 或 body 固定字段
业务键 如 orderId；扣库存用「订单维度唯一」而非仅 messageId
落库 processed_event(event_id UNIQUE) 或业务表唯一约束；冲突即跳过
日志 打印 eventId + 业务键，便于跨服务追踪

注意点：

  1. 幂等粒度要覆盖「副作用」（扣款、发券），不只覆盖「写一行日志」。
  2. 仅用自增 DB id 当幂等键在多生产者下会撞车；重试必须带同一 eventId。

6. 顺序消息

是什么： 业务要求消息按某键顺序处理（同一订单的创建→支付→发货）。

级别 含义 代价
全局有序 整个 Topic 单通道 吞吐崩、难扩展
分区/队列内有序 同 key 进同一分区且单线程消费 常见可落地方案

机制要点： 生产端用业务 key 做分区键；消费端同分区串行。跨分区无法靠 Broker 保证全局顺序。

注意点：

  1. 分区数变更、错误的 key 策略会打乱顺序假设。
  2. 消费失败重试时勿并发打乱同 key。
  3. 能接受最终一致时，不要强上全局有序。

7. 消息积压

是什么： 生产速率持续大于消费，lag 升高，延迟暴涨甚至磁盘写满。

发现： 消费滞后（lag）、队列深度、端到端延迟告警。

处理策略：

策略 适用
扩消费者（与分区/队列数匹配） 消费 CPU 不够、分区有空闲
优化消费逻辑（批量、异步、减远程调用） 单条过慢
扩分区后再扩消费者 并行度顶格（注意顺序与再均衡）
临时分流 topic 紧急：新服务消费积压副本/新流量，旧逻辑止血
降级 / 丢弃非关键 + 事后补偿 保核心链路
限流生产 保护下游不被冲垮

反模式： 积压时无限加大重试并发 → 雪上加霜；不查根因只加机器。

8. 重试、死信、延时

机制 是什么 注意
重试 失败后再次投递 要退避，避免重试风暴；与幂等绑定
死信（DLQ） 超过次数进死信队列人工/补偿 要有处理剧本，别只进不管
延时消息 到期才可消费 实现因产品而异（Rocket 原生、Rabbit 插件/TTL+DLX、Kafka 常靠业务或外部）

重试风暴反模式： 下游 500 时所有消费者疯狂重试 → 把下游打得更死。应熔断、限流、指数退避、隔离线程池。

8.1 死信运营与可观测

项 要求
告警 死信队列/主题深度 > 0 告警
责任人 指定值班处理，禁止「只进不管」
关联 日志带 eventId，能反查生产与业务单
剧本 重放 / 人工修数 / 丢弃+补偿 三选一写进 runbook

9. RPC、本地消息表与 Outbox

模式 要点
同步 RPC 强依赖下游可用；简单但峰值脆弱
发消息后直接改状态 进程崩溃可能「DB 已改消息未发」或相反
本地消息表 与业务同事务写「待发送」表，异步任务扫表发 MQ
Outbox 同思路的标准化：业务事务提交 Outbox，relay 发消息

用于需要「业务提交与发事件尽量同成败」的场景；再配合下游幂等达到最终一致。

注意点： Outbox 也有堆积与重复发送；仍要幂等。不要用分布式事务硬扛所有链路。

与缓存/锁/本地事务的取舍总表，详见 分布式一致性学习。

10. 端到端案例：订单已支付

场景： 用户支付成功后，需要通知 库存、积分、搜索 三个下游；允许最终一致，不允许漏扣库存。

设计要点对照：

问题 本例做法
丢 Outbox + 生产确认/acks；先业务再 ACK
重 eventId / orderId 唯一约束
乱 key=orderId，同订单同分区
积压 分 Group 独立扩容；搜索可降级

注意点： 库存与积分不要塞进同一消费者硬编码串行——用多 Group 解耦失败域。完整 Kafka 参数见 Kafka 篇。

四大问题速查表

问题 一句话 优先动作
丢 三段任一未确认 生产确认 + 副本 + 先处理再 ACK
重 至少一次常态 业务幂等
乱 缺分区键或并发消费同 key 同 key 同分区 + 串行
积压 消费跟不上 lag 告警 + 扩容/优化/分流

总结

先接受「至少一次 + 幂等」为默认工程语义；丢看三段，乱看分区键，积压看 lag 与并行度。下一篇把这套心智落到 Kafka 参数与运行机制上。
