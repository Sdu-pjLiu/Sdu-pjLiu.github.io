1. 定位与为何快

是什么： Redis（REmote DIctionary Server）是内存为主的键值存储，常作缓存、会话、排行榜、限流计数、分布式锁协调等。它 可以持久化，但默认心智仍是「热数据在内存、延迟极低」。

机制要点（为何快）：

因素 含义
内存读写 避免磁盘随机 IO 成为主路径
单线程执行命令 无复杂锁竞争，命令串行，逻辑简单
IO 多路复用 单线程处理大量连接就绪事件
高效编码 小对象用紧凑编码，减少指针开销

事件循环（口述级）：

Redis 6.0+ IO 线程认名： 可将网络读写交给 IO 线程加速；命令执行仍在主线程串行。因此「单线程」说的是执行模型，不是「绝对不会卡」——慢命令仍会堵住后续所有请求。

字典与渐进式 rehash（认名）： 全局哈希表扩容时，为避免一次搬迁卡住，采用 渐进式 rehash：新旧两表并存，读写顺带搬迁，后台逐步完成。面试答到「避免一次性阻塞」即可。

典型场景：

  • 读多写少的热点缓存（商品详情、配置）
  • 会话 / Token、验证码短 TTL
  • 计数器、排行榜（ZSet）、简易限流（§11）
  • 分布式锁（见第 2 篇）

注意点：

  1. Redis 不是万能数据库：复杂事务、强一致多表业务仍归 RDBMS。
  2. 内存有价：要设 maxmemory 与淘汰策略，并治理大 Key。
  3. 发布订阅（Pub/Sub）消息不持久、不保证送达——适合通知，不适合可靠队列（可靠向见 Stream 边界 §7）。

2. 键设计与治理

是什么： 键是全局命名空间中的字符串；好的键设计决定可运维性与碰撞风险。

机制要点：

习惯 做法
命名 业务:实体:id:字段，如 user:1001:profile
TTL 缓存键几乎都应有过期；永久键要有容量理由
体积 单 value / 单集合元素量设上限；大对象拆分或外置
环境 前缀区分 prod: / stg:，避免串环境

示例：

注意点 / 反模式：

  1. 无规范键名 → 无法按前缀扫描治理，易误删。
  2. 把整库业务状态塞进一个巨型 Hash/String → 大 Key。
  3. 生产禁用 KEYS *；用 SCAN 游标迭代。
  4. 敏感数据进 Redis 仍要权限、网络隔离与脱敏意识（点到）。

3. String

是什么： 最通用类型：字符串、整数（可 INCR）、二进制安全值。常缓存序列化对象或简单计数。

机制要点（编码认名）：

编码（概念名） 何时 意义
int 可解析为整数的短值 省内存
embstr / raw 短/长字符串 长大后转更重编码
（实现细节随版本演进） — 面试强调 有编码转换，勿死记阈值

可用 OBJECT ENCODING key 观察（调试用，勿当生产热路径）。

示例：

注意点：

  1. 大 JSON 整包缓存：更新局部仍要整 key 替换，或改用 Hash。
  2. INCR 适合计数/限流桶；不要用它当分布式唯一 ID 的唯一方案而不谈时钟/分段（业务另议）。
  3. GET 不存在返回 nil——与「缓存空值防穿透」策略相关（第 2 篇）。

4. Hash

是什么： 字段-值映射，适合对象多字段读写、不必每次反序列化整包。

示例：

注意点：

  1. HGETALL 在超大 Hash 上昂贵——字段极多时分页字段设计或拆 key。
  2. Hash 整体过期，不能给单个 field 独立 TTL（需业务拆 key 或版本字段）。
  3. 对象字段少且总是整读整写时，String 存 JSON 也可能更简单——按访问模式选。

5. List

是什么： 有序列表，两端推弹；可作简易队列、最新动态时间线。

示例：

注意点：

  1. List 作队列：无消费确认、无重试语义，进程崩溃可能丢或重复——可靠队列优先专业 MQ 或认真评估 Stream。
  2. LRANGE 0 -1 拉全量在长列表上危险。
  3. 阻塞命令（BRPOP）会占用连接，连接池要按阻塞场景单独规划。

6. Set 与 ZSet

6.1 Set

是什么： 无序去重集合；交并差适合共同好友、标签等。

注意点： 超大集合上的交并差与全量 SMEMBERS 成本高；注意基数。

6.2 ZSet（Sorted Set）

是什么： 成员 + score 排序；排行榜、延时边界（按时间 score）常用。

机制要点（口述）： 常用 字典（成员→score）+ 跳表（按 score 有序） 组合，使按成员查与按排名/区间查都高效；小体积时可能用更紧凑编码，长大后转换。

注意点：

  1. score 为浮点语义，业务要用整数时间戳时注意精度。
  2. 排行榜要定期裁剪（ZREMRANGEBYRANK），防无限增长。
  3. 延时任务用 ZSet 可行但要处理并发抢单与时钟；生产常有现成组件。

7. 特殊类型认名

类型 用途 能力边界
Bitmap 签到、布尔状态压缩 位运算灵活；偏移极大时注意内存
HyperLogLog 海量 UV 近似去重 有误差；不能取成员列表
Geo 附近的人/店 基于 ZSet；精度与业务坐标体系要匹配
Stream 消息流、消费组 比 List 强，仍非「完整 MQ」：持久化/堆积/多消费者运维要自行设计；跨机房可靠投递勿神话

注意点： 选型先问「要精确还是近似、要可靠投递还是尽力通知」；答不清就别用特殊类型装酷。

8. 过期与淘汰

是什么：

  • 过期（expire）：键到点删除（对业务可见为不存在）。
  • 淘汰（eviction）：内存触及 maxmemory 时按策略删键腾空间。

机制要点（过期）：

策略 行为
惰性删除 访问时发现过期再删
定期删除 后台抽样清理一部分过期键

因此「已过期」键可能仍短暂占内存，直到被抽到或访问到——监控内存时要心里有数。

过期键在复制中（认名）： 主从场景下过期如何传播随版本与配置而异；读写分离时「从库读到已过期语义」要在联调中验证，勿想当然。

淘汰策略（常见）：

策略 含义 生产常见
noeviction 写满报错 要严格失败可见时
allkeys-lru 所有键 LRU 纯缓存很常见
volatile-lru 仅带 TTL 的键 LRU 混合永久+缓存
allkeys-lfu / volatile-lfu 按访问频率 热点更稳的场景
volatile-ttl 优先短 TTL 特定语义
*-random 随机 少用作默认

示例：

注意点：

  1. 缓存实例通常设 maxmemory + allkeys-lru（或 LFU）；勿默认无上限吃光机器。
  2. 永久键 + volatile-* 策略 → 永不过期键永不被淘汰，可能把内存钉死。
  3. 淘汰与过期是两套机制，面试勿混为一谈。
  4. 设 maxmemory 时预留 fork/COW 与碎片余量（见第 2 篇持久化）。

9. 事务 / Pipeline / Lua

能力 是什么 注意
MULTI/EXEC 队列命令一次执行 不是关系库事务：无回滚；中间某命令失败不撤销已成功命令；WATCH 乐观锁
Pipeline 客户端批量送命令，降 RTT 不原子；网络一次往返多命令
Lua（EVAL） 脚本在服务端原子执行 脚本勿做重计算/慢逻辑；版本与复制注意

示例：

Pipeline vs 事务（加厚）： Pipeline 优化延迟；MULTI 保证「连续执行不被插队」。需要「读比较写」原子性时优先 Lua 或正确锁，而不是误以为 MULTI 等于 ACID。

注意点：

  1. 集群模式下，事务/Lua 涉及的 key 常需同一 hash slot（第 2 篇）。
  2. 长 Lua 与慢命令一样会阻塞主线程。

10. 阻塞、大 Key、惰性释放（单线程 ≠ 不会卡）

是什么： 主线程在执行一条慢命令时，其它客户端请求排队等待——表现为延迟尖刺、超时、雪崩式重试。

常见阻塞来源：

来源 说明
大 Key 一次序列化/删除/迁移巨量数据
热 Key 单 key 打满带宽/CPU，或成热点
危险命令 KEYS、无界 SORT、对超大集合不当操作
持久化 fork RDB/AOF 重写时 fork 与 COW 内存压力（第 2 篇展开）
主从全量同步 大数据集复制窗口

大 Key 经验阈值（口述级，非硬标准）： String 数 MB 级、集合元素数万～十万级就要警惕；以本机 MEMORY USAGE、慢日志与业务 SLA 为准。

惰性释放（lazy free）认名： UNLINK、以及部分配置下的异步释放，把释放内存的工作挪到后台，减轻主线程在「删大 Key」上的卡顿。仍应 拆分大 Key，不能只靠 UNLINK 掩盖设计问题。

观测与替代：

内存碎片认名： 分配与释放模式可能导致 used_memory 与 RSS 差距；观察 mem_fragmentation_ratio。碎片率长期偏高再考虑版本能力内的整理；勿在高峰盲目激进整理。

注意点 / 反模式：

  1. 线上用 KEYS 排查。
  2. 发现超时就加大客户端重试 → 放大打满。
  3. 不设监控：无历史延迟与慢日志，只能事后猜。
  4. 用 DEL 同步删超大结构导致超时尖刺——优先拆分 + UNLINK。

11. 客户端、ACL 与限流认名

是什么： 应用通过 TCP 连接执行命令；生产几乎总用 连接池，并设合理超时、重试上限与权限。

机制要点：

项 建议
池大小 按并发与实例规格，避免过大打满 maxclients
超时 connect / command 超时分开；阻塞命令用专用连接
序列化 统一 JSON/MessagePack 等，注意版本兼容
Cluster 客户端需处理 MOVED/ASK 重定向（第 2 篇展开路由流程）
重试 有上限 + 抖动；配合熔断，避免故障放大

安全基线：

手段 作用
私网 / 安全组 不把 6379 暴露公网
密码 / ACL（6+） 按用户最小权限，禁 FLUSHALL 等
rename-command 重命名或禁用危险命令
TLS 跨网络加密（按部署需要）

限流认名（应用侧常见套路）：

套路 思路
固定窗口计数 INCR + 首次数 EXPIRE；简单，窗口边界可能突刺
滑动/令牌等 用 ZSet 存时间戳或 Lua 维护；更平滑也更复杂
集群注意 限流 key 与业务同槽或接受近似全局

限流是 业务保护，不能替代容量规划与 HA。入口网关侧配额与 429 契约见 网关限流学习。

注意点：

  1. 连接泄漏（借出不还）会耗尽池与 Redis 连接。
  2. 无限重试 + 熔断缺失 = 故障放大。
  3. 勿全服务共用一个超级用户；按服务拆 ACL。

类型选型总表

类型 典型场景 反模式
String 整对象缓存、计数、NX 锁 超大 blob；无 TTL 缓存
Hash 对象多字段局部更新 HGETALL 扫巨型 Hash
List 时间线、简易队列 当可靠 MQ；LRANGE 全量
Set 去重、交并差 超大集盲目 SMEMBERS
ZSet 排行榜、按分排序 只增不裁剪
Bitmap/HLL/Geo/Stream 签到、近似 UV、附近、流 边界不清硬上

总结

先选对类型与 TTL，设好内存与淘汰，避开大 Key 与慢命令；理解「单线程执行」下的阻塞模型。下一篇进入持久化、主从/哨兵/Cluster 与缓存工程（穿透击穿雪崩、一致性、分布式锁与生产运维）。
