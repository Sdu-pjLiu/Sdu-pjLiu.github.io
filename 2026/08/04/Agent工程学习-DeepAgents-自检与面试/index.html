AI-Agent工程学习-DeepAgents(自检与面试)

发表于 2026-07-20 分类于 计算机
Deep Agents 五篇正文的学习自检与面试导向问答；覆盖四层能力、Middleware、Backends、Subagent 与 HITL。

本文是 Deep Agents（一）～（五）的阶段性验收。目标不是背 API 名称，而是能从长任务约束出发，选用 Deep Agents 四层能力、解释 Middleware 栈与 Subagent 隔离，并说明何时退回 LangGraph 自建。

0. 使用说明

建议先遮住「推荐回答」，在 60～120 秒内口述答案。自检题用于逐篇查漏补缺；面试题要求先给结论，再说明机制、风险与工程措施。

回答时重点检查四件事：

  1. 是否区分 Harness 预装能力 与 LangGraph Runtime 能力。
  2. 是否说清 messages / todos / files 各自生命周期。
  3. 是否覆盖 Subagent 隔离、offloading、HITL 三类长任务风险。
  4. 是否能把概念落到 create_deep_agent 参数 + Middleware 名。

1. 学习自检

1.1 定位与 Harness 架构

S1. Deep Agents 在 Agent 技术栈中解决什么问题？它与 LangChain、LangGraph 如何分工？

推荐回答： Harness 完整定义见 Agent（三）§6。LangChain 提供可定制的 Model + 薄 Harness（create_agent + Middleware）；LangGraph 是 Orchestration Runtime，负责显式拓扑、持久化、Interrupt 与 Multi-Agent 图；Deep Agents 是在二者之上预装 Planning、虚拟 FS、Skills、Memory、Subagent、Summarization 等的 厚 Harness，入口为 create_deep_agent。标准短环单 Agent 用 LangChain；需精细确定性拓扑用 LangGraph；长任务且需要开箱 context 治理与委托时用 Deep Agents。Deep Agents 底层仍编译为 LangGraph Runnable，不是新 Runtime。

S2. 请说明 Deep Agents 官方「四层能力模型」各解决什么。

推荐回答： Execution environment 解决 Agent 在哪行动——Tools、MCP、虚拟 FS、Backends、Sandbox/Interpreter；Context management 解决知道什么、能跑多久——Skills、Memory、Summarization、offloading、Prompt caching；Delegation 解决如何拆任务——write_todos 与 task Subagent；Steering 解决人如何管控——HITL、permissions、Profiles。四层是阅读文档与配置参数的主索引。

S3. create_deep_agent 返回什么类型？与 create_agent 的相似与不同？

推荐回答： 返回 CompiledStateGraph，即 LangGraph 编译图，支持 invoke、stream、stream_events 等 Runnable 接口。与 create_agent 相似：都是 Model + Harness 编译产物。不同：Deep Agents 默认挂载 TodoList、Filesystem、Summarization、Patch 等 Middleware，并在有 subagents 时挂 SubAgentMiddleware；参数面含 memory、skills、backend、permissions、subagents 等厚 harness 专用项。

S4. 主 Agent 默认 Middleware 栈中，Skills、Memory、Prompt caching 的相对顺序有什么工程含义？

推荐回答： 主栈大致为 TodoList → Skills（若有）→ Filesystem → SubAgent（若有）→ Summarization → Patch → 用户 middleware → profile extras → Prompt caching → Memory（若有）→ HITL（若有）。Skills 在 Filesystem 前以便文件工具运行前已有 skill 元数据；Memory 在 Prompt caching 之后是为减少 memory 更新 invalidate 缓存前缀。理解顺序才能正确覆盖默认 Middleware 而不破坏 caching 或 FS 脚手架。

1.2 Execution / Backends

S5. 默认虚拟文件系统数据存在哪里？StateBackend 与 StoreBackend 如何选型？

推荐回答： 默认 StateBackend：文件内容在 graph state 的 files 等字段，经 checkpointer 在 同一 thread 内持久，不跨 thread 共享。StoreBackend 配合 store= 与 namespace，适合跨 thread 的用户级长期数据。常见模式是 CompositeBackend：工作区走 State， /memories/ 等路径走 Store，避免 agent 内部 offload 数据与项目目录混写。

S6. 内置文件工具有哪些？execute 何时出现？

推荐回答： 包括 ls、read_file、write_file、edit_file、delete、glob、grep，以及 Sandbox 后端的 execute。execute 仅在 Backend 实现 SandboxBackendProtocolV2 时由 harness 自动加入；StateBackend 或纯 FilesystemBackend 无 shell 执行。Interpreter 路径则提供 QuickJS eval，不是 execute。

S7. Filesystem permissions 如何工作？与 Sandbox execute 的关系？

推荐回答： permissions 是声明式规则列表，含 operations（read/write）、paths（glob）、mode（allow/deny），按声明顺序 first-match-wins，未匹配则默认允许。仅约束 built-in FS 工具。Sandbox 的 execute 可跑任意 shell，不受 permissions 约束；生产环境需 Sandbox 策略或限制 Backend 类型。Subagent 可设独立 permissions 列表，完全替换父规则。

S8. 如何配置只读 Deep Agent？错误做法是什么？

推荐回答： 正确：传 FilesystemMiddleware(tools=["read_file", "ls", "glob", "grep"], backend=...) 替换默认实例，且 read_file 必须在 allowlist 中。或用 HarnessProfile 的 excluded_tools 隐藏写工具。错误：用 excluded_middleware 删除 FilesystemMiddleware——会被拒绝；FilesystemMiddleware 是必需脚手架，只能限制模型可见工具面。

1.3 Context / Skills / Memory

S9. Skills、Memory、Tools 三者分工是什么？

推荐回答： Tools 是可调用能力，始终在 tool list。Skills 是按需加载的领域流程与知识（SKILL.md + progressive disclosure：启动读 frontmatter，用时读全文）。Memory 是 AGENTS.md 等持久偏好与规范，启动全量注入，且 Agent 可更新。Tools 做动作，Skills 教怎么做，Memory 定长期约束与风格。

S10. Summarization 与 Context offloading 各解决什么？能否互相替代？

推荐回答： Summarization 压缩 对话历史，在 token 接近上限时触发，由 SummarizationMiddleware 管理 trigger/keep。Offloading 把 单次过大 tool 结果或中间产物 写入虚拟 FS，messages 只留引用或短摘要。二者互补：offloading 防单次撑爆，summarization 防多轮累积撑爆。都不能替代 Memory 的全量偏好注入，也不能替代 Subagent 对整段子任务轨迹的隔离。

S11. Memory 与「上下文压缩」为何不能混为一谈？

推荐回答： Memory 是 AGENTS.md 等文件的 主动加载，属于 Input context，跨会话传递规范。压缩是对已有 messages 或超大结果的 被动缩减。把 Memory 当成压缩会导致误以为偏好应只在对话长了才加载——实际上 Memory 每次启动都要在 scope 内，且更新会影响 Prompt caching 行为。

S12. context_schema 与 Context management 中的压缩有何区别？

推荐回答： context_schema 定义运行时业务上下文（user_id、tenant、feature flags），通过 invoke(..., context=Context(...)) 注入，并自动传播到 Subagent 及其 Tools（ToolRuntime）。它是 每次调用的外部输入，不参与 token 压缩。Context management 的压缩/offloading 是 对话与工具输出体积 治理。二者名称都含 context，但一层是身份与配置，一层是窗口 economics。

1.4 Delegation / Subagent

S13. write_todos 在 Deep Agents 里扮演什么角色？它是独立 Planner 吗？

推荐回答： 它是内置工具，让 Agent 维护 pending/in_progress/completed 任务列表，状态持久在 agent state。它是 轻量跟踪，不是独立 Plan-Execute-Verify 引擎；拆重活主要靠 task Subagent，检查与修正靠模型推理和可选 HITL，不是 todos 系统自动 replan。

S14. Subagent 的 single handoff 是什么意思？对主 Agent context 有什么影响？

推荐回答： 同步 Subagent 运行结束后 只向主 Agent 回传一份 final report（ToolMessage），不能多轮 message 回父 Agent。中间所有 tool calls 留在子 context。主 Agent 因此不收十几次 search 详情，只收摘要，这是 context quarantine 的核心。若需要结构化结果，可设 response_format 让父 Agent 收到 JSON。

S15. 主 Agent 如何选择委托给哪个 Subagent？是否存在独立 Routing 框架？

推荐回答： 不存在独立 Router API。主 Agent 读各 Subagent 的 description（应 action-oriented、互斥清晰），通过 task(subagent_type=...) 选择。选错 Subagent 时应优化 description 与主 Agent system_prompt（明确要求 delegate），而非寻找 routing 配置表。

S16. general-purpose Subagent 默认行为是什么？如何禁用？

推荐回答： 若无同名同步 Subagent，自动添加 general-purpose：默认 FS 工具、继承主 Agent skills、可用 profile 覆盖 prompt/model。用 subagents=[{"name": "general-purpose", ...}] 可整体替换。完全禁用：profile 设 GeneralPurposeSubagentProfile(enabled=False) 且 subagents= 不传同步 subagent——此时无 task 工具。不可用 excluded_middleware 删 SubAgentMiddleware。

S17. Deep Agents Subagent 与 LangGraph Supervisor 何时互换？

推荐回答： Deep Agents 适合快速委托、context 卫生、开箱 FS 的重 research/编码子任务。LangGraph Supervisor 适合需 显式图拓扑、每步图级 LE、复杂 handoff 合同、确定性分支与 Store 映射的 Multi-Agent。组合方案：外层 Deep Agents + CompiledSubAgent（内层 LangGraph/create_agent 图）。需要每步 interrupt 插节点时偏 LangGraph。

1.5 Steering / 选型 / 阶梯

S18. interrupt_on 为什么必须配置 checkpointer？

推荐回答： HITL 依赖 LangGraph interrupt 在 tool 执行前暂停并持久化图状态；resume 时需同一 thread 的 checkpoint 恢复 messages 与 pending tool call。无 checkpointer 则无法 pause/resume，interrupt 无意义。这与 LangGraph（五）Interrupt 模型一致，Deep Agents 只是通过 interrupt_on 封装。

S19. 覆盖默认 SummarizationMiddleware 时要注意什么？

推荐回答： 按 .name 匹配则 整体替换 默认实例，不会 merge 默认配置。自定义实例须自带 model、backend、trigger、keep 或 summary_prompt 等完整参数。若同时覆盖 FilesystemMiddleware，须自行传入 backend（及 permissions），不会继承 create_deep_agent 的 backend=。Declarative subagent 不继承主 Agent 的 middleware 覆盖，需在 subagent 的 middleware 字段单独配置。

S20. L0、L1、L2 实践阶梯分别应证明什么？

推荐回答： L0：create_deep_agent + harness 工具 + LangSmith trace，证明最小厚 harness 跑通。L1：memory + skills + subagent，对比主 Agent messages 体积，证明委托与知识加载价值。L2：interrupt_on + permissions + streaming +（可选）Sandbox，证明长任务可治理、可观测。只有确实需要 FS/Skills/Subagent 开箱能力且接受抽象成本时才上 Deep Agents。

S21. 线上「主 Agent 从不委托 Subagent、context 仍爆炸」如何排查？

推荐回答： 先看 description 是否模糊、主 prompt 是否未要求 task()；再看 Subagent system_prompt 是否要求 concise output；若主 Agent 自己做重 tool 链，应强制 delegate 或禁用其直接访问重 tools。若已委托仍膨胀，检查子 Agent 是否返回 raw data——应要求写 FS + 摘要。LangSmith 用 lc_agent_name 确认是否产生 subagent span。

S22. 什么情况下应从 Deep Agents 退回 LangGraph 或 LangChain？

推荐回答： 退回 LangChain：只需少量 Tool、短环、无需 FS/Skills/Subagent。退回 LangGraph：需确定性多节点编排、复杂条件路由、每步验证节点、精细 Store/checkpoint 策略，或 Deep Agents 默认栈难以满足且 CompiledSubAgent 仍不够。Deep Agents 适合长任务厚 harness，不是一切 Agent 的默认选项。

2. 系列总结

Deep Agents 系列应掌握：

  • 四层能力作为阅读与配置索引
  • 默认 Middleware 栈及覆盖规则
  • Backends + permissions + Sandbox/Interpreter 构成 Execution 层
  • Skills / Memory / Summarization / offloading 分工明确的 Context 层
  • write_todos + task Subagent 的 Delegation 层与 single handoff
  • interrupt_on + Profiles 的 Steering 层
