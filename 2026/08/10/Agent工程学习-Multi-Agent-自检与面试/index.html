AI-Agent工程学习-Multi-Agent(自检与面试)

发表于 2026-07-18 更新于 2026-08-20 分类于 计算机
Multi-Agent（一）～（五）学习自检与面试导向问答；覆盖角色、协作、通信、拓扑映射与退回条件。

本文是 Multi-Agent（一）～（五）的阶段验收。目标不是背名词，而是能根据业务约束 设计角色与协作拓扑、选择通信机制、映射到 LangGraph / Deep Agents / CrewAI，并判断何时应退回单 Agent。

0. 使用说明

建议先遮住「推荐回答」，在 60～120 秒内口述。自检题按篇覆盖；（五）映射表与拓扑设计为重点。面试题侧重架构取舍与生产边界。

回答时重点检查四件事：

  1. 是否区分 角色职责 与 协作模式、通信机制。
  2. 是否说明 Handoff 合同与 Context 隔离。
  3. 是否能把概念映射到至少一个已学框架。
  4. 是否给出 退回单 Agent 或简化拓扑的条件。

1. 分篇自检

1.1（一）定位与分水岭

S1. Multi-Agent 系列与 LangGraph（六）的分工是什么？

推荐回答： LangGraph（六）讲图级实现——Subgraph、Router、Supervisor、代码拓扑；Multi-Agent 系列讲与框架无关的理论 canonical——五角色、五协作、四通信、治理与映射表。先有过（六）的实现体验，再用本系列命名和系统化；Deep Agents 与 CrewAI 是不同实现线，回链（五）映射表。

S2. 列出三个「需要 Multi-Agent」的有效信号。

推荐回答： 角色异质（工具集与验收不同）、Context 隔离（子任务 Trace 会挤爆主窗）、并行独立子任务或需辩论/投票消解冲突。反例：同一 Tool 环加 Skill 切换、固定三步 ETL、单模型 Reflection 可解决的，不必拆。

S3. 过早拆角色的四个典型代价是什么？

推荐回答： Context 丢失（Handoff 不完整）、Token 膨胀（多环各带完整 System）、责任模糊（只有角色名无独立工具/验收）、图维护成本超过收益。默认应先单 Agent + 分层规划 + Skill。

S4. 五角色各用一句话概括。

推荐回答： Supervisor 分派验收；Worker 执行原子子任务；Coordinator 管流程时钟与依赖；Router 分类分流；Peer 对等自治。Coordinator 不做内容推理，Router 通常不做多轮协调。

1.2（二）五角色深讲

S5. Supervisor 与 Coordinator 的核心区别？

推荐回答： Supervisor 负责任务分解、选 Worker、验收子结果与是否结束；Coordinator 负责步骤依赖、并行门禁、超时重试路由，不负责内容质量推理。CrewAI Flow 的 @listen 偏 Coordinator；hierarchical Manager 偏 Supervisor。

S6. Worker 必须返回结构化错误态的原因？

推荐回答： Supervisor 需区分无结果、限流、权限、致命错误以决定改 query、换 Worker、降级或 Interrupt。非结构化「失败了」会导致盲目重试或假完成。生产应返回 status、summary、evidence_refs。

S7. Router 与 Supervisor 的选型分水岭？

推荐回答： 一次或少数几次分类、分支彼此独立无多轮协调用 Router；需根据进展反复分派、验收、handoff 用 Supervisor。误把长期协作塞进 Router 会缺验收；简单 FAQ 分流不必上 Supervisor。

S8. 可靠 Handoff 至少包含哪些字段？

推荐回答： Goal 摘要、done[]/open[]、硬规则引用、证据指针（非全文）、Worker 错误态（如适用）、剩余预算提示。不要把完整 Trace 灌给下一角色。

S9. Peer / Swarm 何时才值得考虑？

推荐回答： 中心 Supervisor 已成瓶颈、各 Agent 能自治、冲突有收敛协议（max_rounds、Voting 聚合）时。多数业务从 Router 或单 Supervisor 起步；无收敛协议的 Peer 易重复劳动与争论不止。

1.3（三）五协作模式

S10. Role-Based 与 Hierarchical 的区别？

推荐回答： Role-Based 是固定角色流水线（Researcher→Writer），顺序通常预定义；Hierarchical 是多层 Supervisor 再分派，顶层目标逐级分解到叶子 Worker。可组合：Hierarchical 顶层 + 每层内 Role-Based。

S11. Debate 模式必须有的两个治理项？

推荐回答： max_rounds 硬上限与仲裁节点（Supervisor 或规则聚合）。否则 Token 爆炸且争论不收敛。辩论摘要后再进下游，不全文灌窗。

S12. Voting 模式的成本与适用？

推荐回答： 成本约 × N 路 Worker；适用分类、评分、冗余校验降幻觉。LangGraph 用 Send 并行 + 聚合 Node；须定义聚合规则（多数、加权、judge）与无一致时的 HITL 或降级。

S13. 何时用 Role-Based 而非 Debate？

推荐回答： 流水线步骤与验收标准清晰、不需多视角争论时用 Role-Based（CrewAI sequential）。策略取舍、方案评审、风险辩驳才用 Debate。把 Debate 塞进简单写作流水线通常浪费 Token。

S14. CrewAI sequential 主要对应哪种协作模式？

推荐回答： Role-Based Collaboration。Researcher + Writer + Editor 流水线是典型场景；hierarchical Process 对应 Hierarchical Agent System。

1.4（四）四通信机制

S15. Message Passing 与 Shared Memory 如何选型？

推荐回答： 子任务隔离、Handoff 清晰、易审计用 Message Passing（默认首选）。多 Agent 需低延迟读写同一任务事实、并行写不同键或 Reducer 合并用 Shared Memory。长材料永不全文传递，用指针与外存。

S16. Event Bus 与 Coordinator 的关系？

推荐回答： Event Bus 常是 Coordinator 的实现手段——Flow 用 @listen 订阅 research_done 等事件驱动下一步。Event Bus 解耦发布订阅，但须幂等与顺序策略；Coordinator 不替代 Supervisor 的内容验收。

S17. Blackboard 的主要风险与防护？

推荐回答： 写污染（猜测当事实）、脏读、黑板过大。防护：字段级来源标注、权限（谁可写 claims）、只读事实层用 RAG、读取侧版本与时效过滤。与通用 Shared Memory 比更强调多专家贡献演化知识结构。

S18. Deep Agents Subagent 返回摘要是哪种通信机制？

推荐回答： Message Passing。子 Agent 独立 Context，只 Handoff 摘要与证据指针到主 Agent，避免完整 Trace 挤占主窗——与（二）Worker 隔离一致。

S19. 并行 Worker 写同一 State 键要注意什么？

推荐回答： 声明 Reducer（append/merge）或由 Coordinator 串行化写；否则非确定性合并。租户数据须 namespace 隔离。Reducer 不保护图外副作用，写库仍需幂等。

1.5（五）拓扑与映射

S20. 拓扑设计四步是什么？

推荐回答： 定角色 → 定协作 → 定通信 → 定治理（Handoff、Budget、LE Gate、HITL）。每步有产出物与验收问题，并对齐 Agent（四）§6。

S21. 理论→三框架映射表中，Supervisor 在三框架的落点？

推荐回答： LangGraph Supervisor 节点；Deep Agents 主 Agent 委派；CrewAI hierarchical Manager。完整表见（五）§4 canonical，他处只回链。

S22. 「快速委托重 research、主 context 要干净」选哪条实现线？

推荐回答： Deep Agents task() Subagent——厚 Harness 内 context quarantine。若还需每步图级门禁与复杂 handoff 合同，用 LangGraph 外层 + Subagent 节点组合。

S23. L0/L1/L2 实践阶梯各验收什么？

推荐回答： L0：Router→2 Worker→聚合，Handoff 含证据指针；L1：Supervisor+Checkpointer+Store，子任务失败可局部重试、interrupt 可恢复；L2：混合拓扑+LE Gate+成本记录，Agent（四）§6 相关项全绿。

S24. 何时应退回单 Agent？

推荐回答： 仅增加角色名无独立工具/状态/验收；Token 升而成功率不变；Supervisor 与 Worker 职责重叠；拓扑复杂度超过业务收益。应用单 Agent + 分层规划 + Skill 或 LangGraph 单节点 Agent。

2. 面试题

I1. 设计「竞品调研 + 报告」Multi-Agent 拓扑，说明角色、协作、通信与框架选型。

推荐回答： Router 可选分流行业；Supervisor 分派 Research Worker 并行（Send）；Message Passing 摘要与 evidence_refs 进 Store；聚合验收覆盖率后 Writer Worker；Final LE Gate。长材料隔离用 Deep Agents Subagent 或 LangGraph 子图。角色团队产品化可选 CrewAI sequential。须 Handoff 合同、Budget、节点级 Trace。

I2. Supervisor、Coordinator、Router 在一个 Flow+Crew 系统里如何划分？

推荐回答： Flow 层 Coordinator：@listen 管步骤时钟与事件；Crew 内 hierarchical Manager 作 Supervisor 分派 Researcher/Writer；入口 @router 作 Router 分流意图。避免一个节点既协调又写正文。持久化用 Flow @persist 与图级 Checkpointer 按层选型。

I3. 多 Agent 上线前最容易遗漏的工程边界？

推荐回答： 子 Context 未隔离、Store 串租户、handoff 丢硬规则、并行写同键无 Reducer、失败子任务无结构化错误、Supervisor 无预算、只记最终回答无节点 Trace、Voting 无聚合规则。价值须由 Task Success 证明，非角色数量。

I4. Message Passing 与 Shared Memory 能否混用？

推荐回答： 常见混用：Worker 间 Handoff 用 Message Passing；跨步骤共享事实用 Store（Shared Memory）。例如 Research 写 evidence[] 到 Store，Writer 读指针；同时 Supervisor 用 state 传 Goal 与 open[]。须分清哪些字段谁可写、Reducer 规则。

I5. Debate 与 Voting 都「多路产出」，如何区分选型？

推荐回答： Debate 是序列或多轮交互求综合观点，有过程；Voting 是独立并行产出后聚合决策，强调冗余与一致性检验。策略评审用 Debate；分类/评分/降幻觉用 Voting。二者都可设上限与仲裁。

I6. 为何 Multi-Agent 理论放在 Deep Agents 与 CrewAI 之前？

推荐回答： LangGraph（六）已给实现体验；理论系列命名五角色五协作四通信，避免 CrewAI 承担理论课。Deep Agents Subagent 是 Worker+Message Passing；CrewAI 是 Role-Based/Hierarchical 产品化。先理论后实现，选型有词汇表。

I7. Swarm 与 Peer 在 LangGraph 里如何实现？

推荐回答： LangGraph 核心无内建 Swarm 一等 API；可用 companion 包（如 langgraph-swarm）或自建多 Peer 节点 + Store 共享黑板 + 路由/轮次上限。须收敛协议，否则难审计。多数场景 Router 或 Supervisor 更可控。

I8. Multi-Agent 成本如何治理？

推荐回答： 限制角色数与轮次、Supervisor 预算、Voting 的 N、Debate max_rounds；Trace 记录每角色 Token；超预算降级（换小模型、减 Worker 数、缩 scope）。对齐 Agent（四）§6 成本项。

I9. 子 Worker 限流时 Supervisor 应如何处理？

推荐回答： 读结构化 status=rate_limited；有限退避重试；仍失败则换备用检索源、降 scope 为证据不足、或 Interrupt 用户。禁止 Writer 用模型常识填补空白。

I10. 实现框架对比 §5 与 Multi-Agent（五）§4 关系？

推荐回答： （五）§4 是理论→主三框架完整 canonical 映射（含巡览占位列）；实现框架对比是八框架产品/工程层全体选型（主四+外四），§5 多 Agent 摘要回链（五）§4 不重写理论全表。发版标准仍以 Agent（四）§6 universal。

I11. Event Bus 在生产环境落地注意什么？

推荐回答： 幂等消费、重复投递、顺序（分区键）、死信队列；与 Celery/Redis 集成见 Agent工程化（四）。Flow 层事件不等于跨服务总线，跨服务须显式 MQ。

I12. 什么情况下 CrewAI 不如 LangGraph 做 Multi-Agent？

推荐回答： 控制流极复杂、需精细 CompiledSubAgent 级拓扑、每步图级 interrupt/checkpoint、Send 并行聚合复杂时 LangGraph 更强。CrewAI 强项是角色团队产品化与 Flow 事件，图级可视化与节点门禁弱于 LangGraph。
