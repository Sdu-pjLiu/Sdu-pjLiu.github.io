Linux性能学习-观测排查与基础调优

发表于 2026-08-07 更新于 2026-08-20 分类于 计算机
Linux 性能观测路径：CPU/内存/IO/网络机制、工具阶梯、运维命令详解、容器叠层、案例与自检。

有 MySQL/Redis/K8s/业务 Metrics 之后，排障常落到 机器与内核视角。本篇给 可复述的观测与排查路径：先分清「算不过来」还是「在等」，再落到进程/设备；不写成发行版手册或 sysctl 百科。

0. 本篇位置与边界

做 不做
CPU/内存/IO/网络瓶颈机制与读数 内核源码、每条 sysctl 精读
工具阶梯与决策顺序 某云主机控制台逐步截图
与容器、应用 Metrics 对照 汇编级优化、调优参数「万能表」

回链： 可观测与 CI/CD · K8s · MySQL 监控 · Redis 运维 · 网关限流

节 主题
§1 问题分层与 USE 心智

各节结构：是什么 → 机制 → 示例/读数 → 注意点。命令详解见 §7。

1. 先定问题类型

表象 先怀疑 勿先做
CPU 高、延迟升 计算忙、自旋、正则/压缩/序列化 盲目加机器却不看火焰图
CPU 低但延迟高 等锁、等 IO、等网络、线程/连接池不够 加 CPU 核
内存持续涨 泄漏、缓存过大、堆/缓冲设置 只看 free 的 available 当「没事」
磁盘 util 高 随机写、刷脏、日志、缺索引扫盘 只扩盘不查谁在写
网络重传/带宽满 跨 AZ、大包、连接泄漏、限流误伤 先改 TCP 参数碰运气

USE 心智（资源侧，认名）： 对每类资源问 Utilization（利用率）、Saturation（饱和/排队）、Errors（错误）。业务侧仍用 RED（可观测篇）；本篇补机器侧。

2. CPU

2.1 是什么

CPU 时间花在：用户态算、内核态（系统调用/驱动）、软中断、硬中断、iowait（空等 IO）、idle。

2.2 机制

读数 含义
us（user） 应用代码在算
sy（system） 内核路径重（过多 syscall、拷贝、网络栈）
wa（iowait） 有可运行任务在等 IO → 不是算力不够
si / hi 软/硬中断；网络 PPS 高时常抬升 softirq
load average 可运行+不可中断睡眠队列长度；不等于 CPU 利用率
上下文切换 过高 → 线程过多、锁竞争、IO 碎

2.3 示例读数

2.4 注意点

  1. 单核打满、其它核空闲 → 看是否单线程瓶颈，不是「机器还有余量」。
  2. 容器里 %CPU 相对 cgroup 配额；节点 idle 高也可能被 throttle。
  3. 负载与核数对比：load ≈ 核数尚可；长期 ≫ 核数要查排队。

3. 内存

3.1 是什么

物理内存被：应用匿名页（堆/栈）、文件页缓存（Cache）、Buffers、内核、可选 Swap 瓜分。Linux 倾向把空闲内存用作 Cache——Cache 高往往正常。

3.2 机制

概念 口径
RSS 进程常驻物理内存
可用内存 available（含可回收 Cache）比裸 free 更有用
回收 内存紧时回收页缓存；再紧可能换页/OOM
OOM Killer 节点或 cgroup 内存顶时杀进程
Swap 换出换入 → 延迟毛刺；生产常尽量避免依赖 Swap 顶业务

3.3 示例读数

3.4 注意点

  1. 把 Cache 当「内存泄漏」去清缓存，常是自伤（下次读盘更慢）。
  2. JVM/Go 堆上限 + 容器 limit：堆过大 → cgroup OOM，节点 free 仍可能好看。
  3. 对齐业务 Metrics：连接池、队列深度、本地缓存大小。

4. 磁盘 IO

4.1 是什么

瓶颈在 IOPS（小随机）或 吞吐 MB/s（大顺序），或在 排队等待（await）。数据库 WAL、刷脏页、容器日志、本地盘上的对象落地都是常见源。

4.2 机制

读数 含义
%util 设备忙的时间比例（近似；多队列盘解读宜谨慎）
await / await 读写 平均等待；升高 ≈ 排队或介质慢
r/s w/s IOPS
rkB/s wkB/s 吞吐
队列长度 饱和信号（与 await 一起看）

4.3 示例读数

4.4 注意点

  1. util≈100% 且 await 高 → 真饱和；util 低但应用慢 → 可能在等锁/网络，不是盘。
  2. 云盘有 突发积分；积分耗尽后延迟陡增——要认名，勿只怪 SQL。
  3. 深分页、全表扫、缺索引 → 表现为 IO 与 CPU 双高。
  4. 对象存储走网络，慢在 网 不在本地盘——见 对象存储。

5. 网络

5.1 是什么

延迟与吞吐受：带宽、PPS、重传、连接状态机、文件描述符、conntrack、跨 AZ/网格跳数 影响。

5.2 机制

信号 含义
带宽打满 大包、备份、误扫全量
重传升高 丢包、拥塞、路径质量差
TIME_WAIT 多 短连接爆发；未必致命，但占端口
FD 耗尽 ulimit/进程打开过多连接或文件
accept 队列满 监听 backlog；表现为连接失败/超时
conntrack 满 NAT/防火墙连接跟踪表溢出

5.3 示例读数

5.4 注意点

  1. 服务网格、跨可用区使 P99 叠加——先 Trace 再怪内核。
  2. 限流 429 与连接耗尽表象不同：见 网关限流。
  3. 生产慎用 tcp_tw_recycle 一类「江湖参数」；优先减短连接、连池、扩 backlog 与 FD。

6. 工具阶梯与读数要点

原则：先宽后窄——总览确认哪类资源红 → 进程/设备 → 应用 profiling；禁止一上来 strace 打满生产。各命令的功能与参数见 §7。

阶 目的 工具
L0 总览 哪类资源红 uptime、top/htop、vmstat 1、free -h、w
L1 CPU 谁在算、us/sy/wa mpstat -P ALL 1、pidstat -u 1、sar -u
L1 内存 RSS 谁大、OOM ps、smem、dmesg/journalctl、cgroup
L1 IO 哪块盘、谁写、空间 iostat -xz 1、iotop、df/du、lsblk
L1 网络 连接与队列 ss、ip、sar -n、nstat、mtr（认名）
L2 追踪 系统调用/热点 perf、lsof、应用 pprof；strace/tcpdump 慎生产
L2 eBPF 低开销观测 bcc/bpftrace（认名）

注意点： 采样间隔太短易噪声；变更窗口前后要有 基线（同命令、同负载时段）。

7. 运维命令详解（功能与作用）

本节按场景收录排障常用命令：做什么、关键参数、看哪些列、注意点。包名因发行版而异（如 sysstat 提供 iostat/mpstat/pidstat/sar）；容器内可能缺权限或看不到宿主机设备。

7.1 总览与主机信息

uptime

功能： 显示系统已运行时长、当前登录用户数、1/5/15 分钟 load average。

作用： 30 秒判断「是否整体过载」；load 相对 CPU 核数偏高时进入 CPU/IO 分流。

w / who

功能： w 列出谁登录、来自哪、空闲多久、当前在跑什么；who 更精简的登录列表。

作用： 排查「是否有人在节点上跑重任务/手工操作」；多人运维时确认变更责任人。

uname -a / hostnamectl

功能： uname 输出内核版本、架构等；hostnamectl（systemd）看主机名、OS、虚拟化类型。

作用： 确认内核/OS 版本是否与文档一致；区分物理机/KVM/云主机，避免用错排障假设。

date / timedatectl

功能： 查看/核对系统时间与时区；timedatectl 可看 NTP 同步状态（视权限）。

作用： 日志与 Trace 对不上时间时先查时钟；分布式排障时钟漂移会导致「假先后」。

top / htop

功能： 交互式进程监视器。默认按 CPU 排序，展示整体 us/sy/wa/mem 与各进程 %CPU/%MEM/TIME+。

作用： 现场找「谁最忙」；htop 更易读（树状、着色），能力同族。

常用交互（top） 作用
P / M 按 CPU / 内存排序
1 展开每核 CPU
H 按线程显示（看线程暴增）
c 显示完整命令行

注意点： 瞬时采样有噪声；容器内 %CPU 相对可见配额，需结合 §8。

vmstat 间隔 [次数]

功能： 报告进程队列、内存、swap、IO、CPU 的汇总快照（可连续刷新）。

作用： 一张表同时看 r（可运行队列）、b（不可中断睡眠，常等 IO）、si/so（换入换出）、wa。

7.2 CPU 相关

nproc / lscpu

功能： nproc 打印可用 CPU 个数；lscpu 详述型号、核、线程、NUMA 等。

作用： 解释 load（相对核数）、判断是否单核瓶颈、是否 NUMA 相关（进阶认名）。

mpstat -P ALL 间隔

功能：（sysstat）按 每个逻辑 CPU 输出 %usr/%sys/%iowait/%irq/%soft/%idle 等。

作用： 发现「一核打满、其它空闲」或 softirq（%soft）过高；比 top 汇总更适合看均衡性。

pidstat -u 间隔 / pidstat -t

功能：（sysstat）按进程（或 -t 按线程）输出 CPU 占用，可带进程名。

作用： 比 top 更适合脚本化采样与对齐 PID；定位吃 CPU 的具体进程/线程。

sar -u 间隔 次数 / sar -q

功能：（sysstat）系统活动报告；-u 为 CPU，-q 为队列与 load；还可读历史（若启用了 sadc 采集）。

作用： 事后复盘「昨天 15:00 CPU 怎样」；现场也可用。是值班回看基线的主力之一。

perf top / perf record + perf report（认名）

功能： 基于性能计数器的采样剖析，看热点函数/符号（需符号表与权限）。

作用： 确认 us 高时「代码哪段在烧」；与应用自带 pprof/异步剖析互补。生产采集要评估开销与权限。

7.3 内存相关

free -h

功能： 汇总物理内存与 Swap 的 total/used/free/available、buffers/cache。

作用： 快速判断是否内存吃紧；优先看 available，不要把 Cache 当成泄漏。

cat /proc/meminfo

功能： 内核导出的细粒度内存计数（MemAvailable、Cached、Dirty、SReclaimable 等）。

作用： free 不够细时下钻（脏页过多、回收困难等进阶线索）。

ps（内存视角）

功能： 报告进程状态、CPU、内存、命令行等。

作用： 找出 RSS 最大的进程；配合排序做 Top-N。

smem（若已安装）

功能： 按进程报告 USS/PSS/RSS，比 RSS 更能反映「真实独占」与共享库分摊。

作用： 多进程共库时避免把 RSS 简单相加高估内存；查真泄漏更靠谱。

swapon --show / cat /proc/swaps

功能： 列出 Swap 设备与使用量。

作用： 确认是否启用 Swap、用了多少；与 vmstat 的 si/so 对照。

dmesg -T / journalctl -k

功能： 读内核环形缓冲区 / systemd 内核日志。

作用： 查 OOM Killer 杀了谁、硬件/驱动报错、软锁等；OOM 后第一现场。

7.4 磁盘与文件系统

df -h / df -i

功能： 按挂载点显示磁盘空间（-h）或 inode（-i）使用率。

作用： 空间满会导致写失败、日志停、DB 崩溃；inode 满（大量小文件）时 df -h 仍可能显示有空间。

du -h --max-depth=1 / du -sh *

功能： 统计目录实际占用。

作用： 在已满或暴增的挂载点上找「哪个目录吃空间」（日志、容器层、备份、核心转储）。

lsblk / mount / findmnt

功能： lsblk 列块设备树；mount/findmnt 看挂载选项与类型。

作用： 确认数据盘是否挂上、是否只读、是否用了网络盘/本地盘；PVC 落在哪块设备。

iostat -xz 间隔

功能：（sysstat）按设备输出 IOPS、吞吐、%util、await、队列等（-x 扩展，-z 省略空闲设备）。

作用： 判断盘是否饱和、延迟是否升高；性能篇 §4 的主读数来源。

iotop / iotop -o

功能： 类似 top 的 IO 版，按进程显示读写带宽（通常需 root；-o 只显示有 IO 的进程）。

作用： 回答「util 高时到底是谁在写盘」。

lsof / lsof +D 目录（慎）

功能： List Open Files——谁打开了哪些文件/套接字。

作用： 找删了但未关闭导致空间不释放的日志；查进程打开的端口与文件过多。

注意点： lsof +D 递归大目录极慢，生产慎用。

fuser -m 挂载点

功能： 显示占用某文件系统的进程。

作用： umount 失败时找「谁还占着盘」。

7.5 网络相关

ss

功能： 现代套接字统计（替代多数 netstat 场景），可列监听、连接、状态、队列。

作用： 看监听端口、连接数、Recv-Q/Send-Q 是否堆积、TIME_WAIT 规模。

参数 作用
-l 仅监听
-t / -u TCP / UDP
-n 不反解域名（更快）
-p 显示进程（常需权限）
-a 所有连接

ip（ip addr / ip route / ip neigh）

功能： 现代网络配置查看（替代多数 ifconfig/route）。

作用： 确认网卡 IP、路由是否指向预期网关、邻居表是否异常——「机器是否根本出不去」。

ping / mtr / traceroute

功能： ping 测连通与 RTT；traceroute 看路径跳点；mtr 结合二者持续统计（认名）。

作用： 区分「应用超时」与「网络路径差/丢包」；跨 AZ 延迟基线。

dig / nslookup

功能： 查询 DNS 解析结果与耗时（dig 更适合脚本）。

作用： 排除「偶发慢」其实是 DNS 卡住或解析到错误 IP。

curl -w / curl -o /dev/null -s -w

功能： HTTP(S) 客户端；-w 可打印各阶段耗时。

作用： 从节点测依赖连通与 TLS/首字节时间，辅助对照 Trace。

sar -n DEV|TCP|ETCP 间隔 / nstat

功能： sar -n 报网卡吞吐与部分 TCP 统计；nstat 打印内核网络计数器（重传等）。

作用： 看带宽是否打满、重传是否升高（与 §5 对照）。

ethtool <网卡> / ethtool -S <网卡>

功能： 查询网卡速率/双工；-S 驱动级统计（丢包、错误，字段因驱动而异）。

作用： 排除协商成百兆、硬件/驱动丢包；云主机上权限与可见性可能受限。

tcpdump（慎用）

功能： 抓取网卡数据包。

作用： 确认是否真收到请求、重传、错误 Reset；生产必须限 BPF 过滤、短时、小包量，避免打满盘与 CPU。

7.6 进程、文件与限制

pstree -p

功能： 以树形显示进程父子关系。

作用： 看清主进程与 worker/子进程结构（如 Nginx master/worker、多进程模型）。

kill / kill -9 / kill -15

功能： 向进程发信号；默认多为 TERM(15)；KILL(9) 强制、不可被应用清理。

作用： 停掉失控进程；优先 15 给优雅退出，9 仅作最后手段（可能留下残留锁/临时文件）。

nice / renice

功能： 调整进程调度优先级（nice 值）。

作用： 让批处理少抢在线流量 CPU；非根因修复，只是权宜。

ulimit -a / ulimit -n

功能： 显示（及在当前 shell 设置）资源限制；-n 为最大打开文件数。

作用： 「Too many open files」、连接上不去时查 FD 上限；真正持久改法在 systemd/unit 或镜像配置。

ls -l /proc/<PID>/fd | wc -l

功能： 统计某进程打开的 FD 数量。

作用： 对照 ulimit -n，验证是否逼近上限。

strace -p PID（慎用）

功能： 跟踪进程的系统调用与信号。

作用： 看进程卡在 read/futex/poll 还是疯狂 write；生产短时、单 PID、可加 -e 过滤，避免全量跟踪拖垮服务。

7.7 日志与内核线索

journalctl

功能： systemd 日志查询。

作用： 查服务崩溃、OOM、单元重启原因；可按 unit、boot、优先级过滤。

tail -f / less + 应用日志

功能： 跟踪或翻阅文本日志。

作用： 与 request_id / Trace 对齐的最后一公里；轮转后注意 journald vs 文件路径。

sysctl <名>（只读排查）

功能： 读内核参数当前值（如 net.core.somaxconn）。

作用： 对照文档确认 backlog 等是否过小；本篇不鼓励无基线乱改；改动需变更流程与回滚。

9. 案例决策表与反模式

9.1 案例

场景 路径
API P95 升高，CPU/盘都低 Trace → 下游超时/锁/连池；查是否 cgroup throttle
MySQL 延迟升，iowait+util 高 慢查询与锁 → 缺索引/刷盘 → PVC/云盘积分 → 同节点噪声
Redis 偶发毛刺 大 Key/慢日志 → fork/AOF（Redis 篇）→ 节点 IO/CPU → 网络重传
仅某 Pod 慢 同节点邻居 CPU/IO；该 Pod limit；副本是否不均
发布后变慢 金丝雀回滚；对比 Trace；再看是否新增大包/同步日志

9.2 反模式

  1. 无 Trace/基线，直接调 sysctl
  2. 把 Cache 当泄漏清掉
  3. iowait 高却加 CPU
  4. 只看容器内 top，忽略 throttle 与节点邻居
  5. 生产长时间 strace -p 全量附着
  6. 用节点「看起来空」否定应用层问题（或反过来）

10. 自检与面试

S1. iowait 高说明 CPU 不够用吗？

推荐回答： 不说明。表示 CPU 在等 IO；应查磁盘/网络阻塞与谁在产生 IO，而非先加 CPU 核数。

S2. 机器很空但接口很慢，先看哪？

推荐回答： 应用 Trace 与依赖；锁/下游/GC/连池；再确认是否 cgroup 限额导致「节点看起来空」。

S3. load 很高但 CPU idle 也高，可能是什么？

推荐回答： 不可中断睡眠（等磁盘等）推高 load；用 wa、iostat、进程状态核对，不是简单「缺核」。

S4. free 里 Cache 很大要不要紧？

推荐回答： 通常正常，Linux 用空闲内存做页缓存；看 available 与进程 RSS 趋势。业务泄漏看 RSS 单调涨或 cgroup OOM。

S5. 急救包 60 秒先跑哪些命令？

推荐回答： uptime、free -h、mpstat、iostat -xz、ss -s，再按红项下钻。功能细节见 §7。

S6. ss 与 iostat 各解决什么问题？

推荐回答： ss 看套接字/监听/连接队列与状态；iostat 看块设备 IOPS、吞吐、util、await。见 §7.4、§7.5。

S7. 为何生产慎用 strace/tcpdump？

推荐回答： 开销大，易放大延迟甚至拖垮进程/打满盘；必须短时、过滤、限 PID/端口。优先用 Metrics/Trace/ss/pidstat。

I1. K8s 上 MySQL 延迟升高，如何分层排？

推荐回答： 业务慢查询与锁 → iostat/wa → 节点与 PVC/云盘 → 同节点噪声 → 再考虑参数。对齐 MySQL 与本篇。

I2. 如何向评审说明「性能排查达标」？

推荐回答： 任意慢请求能用 Trace 定位到跨度；节点侧有 USE 读数习惯与基线；会用 §7 命令分层下钻；容器限额与 OOM 可查；不靠盲目改内核参数。

总结

先应用 Trace，再资源饱和；分清 us 忙与 wa 等 IO；Cache≠泄漏；容器限额与节点现实一起看。

工具：先宽后窄（§6）；命令功能见 §7；有基线再调优。
