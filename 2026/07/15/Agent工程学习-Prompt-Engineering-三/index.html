AI-Agent工程学习-Prompt Engineering(三)

发表于 2026-07-15 分类于 计算机
Prompt 工程化：Versioning 与 Registry、Evaluation、Optimization、A/B Testing，以及从编写到发布的闭环。

接Prompt Engineering（二）：把 Prompt 当成可版本、可评测、可优化的产品资产，而不是聊天草稿。

1. Versioning 与 Registry

1.1 Prompt Versioning（版本管理）

每次上线变更应有 可回滚的版本号，并记录改了什么。

常见变更类型：

类型 例子
文案 改措辞、补禁止事项
结构 调整四积木顺序、增减区块
示例 增删 Few-shot
输出契约 字段增删、与 Schema 对齐

建议：

  1. 语义化版本或单调 build 号（如 planner@3、tool_fill@2026.07.15.1），团队内统一一种即可。
  2. 绑定依赖：该版本对应的 模型名/版本、Tool Schema 版本、相关业务配置。模型升级导致行为漂移时，才能判断是 Prompt 问题还是模型问题。
  3. 变更日志：为什么改、预期改善什么、回滚点是哪一版。
  4. 灰度与回滚：先小流量，再全量；出问题立刻切回上一 version。

1.2 Prompt Registry（注册与治理）

Registry 是 Prompt 的 目录与仓库：按名称取用「当前环境该用的那一版」。

至少应有的元数据：

  1. 名称与用途（如 agent.plan、agent.tool_args、agent.summarize）
  2. 输入变量列表（Template 槽位）
  3. 输出契约（自然语言说明或 Schema id）
  4. 依赖模型 / 工具
  5. 环境：dev / staging / prod 各自指针
  6. 负责人与变更权限：谁能改 prod

没有 Registry 时，Prompt 散落在代码常量与临时实验里，A/B 与回滚都会失控。

2. Prompt Evaluation（评测）

2.1 评什么

维度 含义
正确性 答案 / 决策是否对
格式合规 能否通过 Schema / 规则解析
指令遵循 是否遵守 Role/Instruction（第三篇）
安全与拒答 越权、注入、违规请求是否处理得当
成本与延迟 Token 数、轮次、TTFT / 端到端耗时

Agent 场景额外关注：工具参数是否可执行、是否在无工具结果时 幻觉「已完成」。

2.2 怎么评

  1. 黄金集（Golden Set）：固定输入 + 期望输出（或期望属性）；回归时必跑。
  2. 规则校验：JSON Schema、必填字段、枚举、正则——与Schema Validation同一思路，评测流水线里应自动化。
  3. LLM-as-Judge：用另一 Prompt/模型按量表打分；要固定裁判 Prompt 版本，并抽检防偏。
  4. 人工抽检：开放生成、安全边界、产品口吻；比例可小但不可省。

用例设计提示：

  1. 正常路径 + 边界（空 Context、冲突材料、超长输入）
  2. 幻觉高发：要求引用不存在的 id、诱导跳过工具
  3. 格式破坏：要求「顺便聊两句」看是否仍守契约

2.3 离线评测 vs 线上监控

离线 线上
数据 黄金集 / 仿真 真实流量抽样
目的 发版门禁 漂移与劣化告警
指标 准确率、合规率 成功率、重试率、人工差评、P95 延迟

发版前过离线门禁；上线后盯线上指标。二者互补，不能只靠其中一个。

3. Prompt Optimization（优化）

3.1 人工迭代循环

归因时先分清：改 Prompt 是否够用。

现象 更可能动哪里
格式偶发失败 Format / Schema / 低温
事实错误但材料里有答案 Context 排序与引用指令
事实错误且材料没有 RAG / 工具，而不是加形容词
某类题系统性不会 换更强模型或拆解任务（见第二篇）
工具参数类型错 Tool Schema + 执行侧校验

3.2 自动 / 半自动优化（认名即可）

方向包括：生成多份候选 Prompt → 用黄金集打分 → 保留优胜者。工程上仍建议 人审后入 Registry，避免自动优化写出不安全或不可读的指令。本系列不展开具体算法。

4. Prompt A/B Testing

4.1 基本要素

  1. 假设：改哪一版、预期提升哪一指标（如工具一次成功率 +X%）
  2. 分流：按用户 / 会话稳定哈希，避免同用户来回跳版本
  3. 主指标与 护栏指标：主指标变好时，延迟、投诉率、安全拒答误伤不得明显变差
  4. 样本量与时长：未达置信度不盲目全量

4.2 与 Registry / Version 挂接

A/B 比较的是 明确的 version id（如 summarize@7 vs summarize@8），而不是「线上随手改的那份字符串」。实验结束：胜出者成为 prod 指针，失败者归档。

4.3 何时先离线即可

  1. 纯格式合规、字段抽取：离线黄金集足够。
  2. 强依赖真实用户分布、口吻偏好、长链路 Agent 成功率：需要线上 A/B 或影子流量。
  3. 安全相关改动：先离线红队集，再小流量，慎用「只看业务主指标」。

5. 工程闭环

对 Agent 的门禁建议：规划、工具参数、用户可见总结等关键节点，各自有独立 Template 名与 version；未过评测的版本不得指向 prod。

与前两篇的关系：

  1. （一） 解决「写什么结构」
  2. （二） 解决「用什么推理/编排技巧」
  3. 本篇解决「如何当成资产长期演进」

总结

Versioning + Registry：有版本、有目录、有环境指针、与模型/工具 Schema 绑定。

Evaluation：正确性、格式、遵循、安全、成本；黄金集 + 规则 +（可选）裁判模型 + 人工；离线门禁与线上监控并用。

Optimization：失败归因后改 Prompt 或改系统其它层；回归后再发版。

A/B：比较明确 version；设主指标与护栏；简单格式问题可先离线。

闭环：编写 → 入库 → 版本 → 评测 →（可选）A/B → 优化 → 发布。
