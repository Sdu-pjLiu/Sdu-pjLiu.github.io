AI-Agent工程学习-Prompt Engineering(一)

发表于 2026-07-15 分类于 计算机
Prompt Engineering 开篇：Prompt 与 messages 的关系、Template、Role/Instruction/Context/Format 四积木、组装顺序与 Agent 行为控制清单。

接 LLM 基础学习：消息角色与指令遵循（三）、Chat Completion 与结构化输出（四）。本系列与 LLM 基础学习平级，编号从（一）重起：讲清怎么写可控 Prompt。

0. 本系列在学习路径中的位置

LLM 基础学习负责：模型怎么表示与生成、怎么调用 API、工具闭环怎么走。

Prompt Engineering负责：在同一套调用合同上，怎么写输入，让 Agent 行为更稳、可复现、可评测。

依赖（已学，本文只引用）：

  1. 消息角色 system / user / assistant
  2. Instruction Following
  3. Chat Completion
  4. Structured Output
  5. Context Window / Token 成本

1. Prompt 是什么

什么是 Prompt？

Prompt 是送进一次 Inference 的 输入合同：告诉模型「你是谁、要干什么、依据什么、输出成什么样」。在 Chat API 里，它通常不是单字符串，而是一组带角色的 messages（见第四篇 Chat Completion）。

要点：

  1. 没有写入本次 messages 的内容，本轮看不见（第三篇 1.2）。
  2. Prompt 越长，Token 与 Prefill 成本越高；关键约束若被挤到中间，可能「听不见」（Lost in the Middle）。
  3. Prompt 管的是 指令遵循与格式；内容是否属实还要靠检索 / 工具 / 校验，不是只靠把字写漂亮（幻觉）。

1.1 对 Agent 的影响

Agent 每一步决策往往就是一次带 Prompt 的 Completion。规划、调工具、读结果、总结，可以共用一份「万能 Prompt」，也可以拆成多份专用 Prompt——后文第 5 节给出拆分原则。

2. Prompt Template（模板）

什么是 Prompt Template？

把固定骨架与可变槽位分开：骨架写死规则与结构，槽位在运行时填入任务、用户问题、检索片段、工具结果等。

示意：

2.1 为什么要用 Template

  1. 可复用：同一 Agent 节点多请求共用骨架，只换变量。
  2. 可版本化：改的是模板文件，而不是散落在代码里的长字符串（工程化见本系列（三））。
  3. 可评测：固定骨架 + 变量集，才能做黄金集对比。

2.2 变量注入注意点

  1. 占位符约定统一（如 {{name}}），避免半套模板半套拼接。
  2. 注入内容要边界清晰：检索原文、用户粘贴的代码，用分隔符或标签包住，减少「把资料当成新指令」的注入风险。
  3. 空值策略：无检索结果时写明「无参考资料，请说明无法确认」，而不是留空让模型脑补。

3. Prompt 的四块积木

一条可控 Prompt，通常由下面四块拼成（可落在不同 role 的 message 里）。

3.1 Role Prompt（角色）

规定 身份、能力边界、禁止事项、语气。优先放在 system（第三篇）。

写好 Role 的要点：

  1. 说清「你是什么 / 不是什么」。
  2. 硬规则用短句、可检查（禁止编造 ID、禁止跳过校验等）。
  3. 不要把整本业务手册塞进 Role；细则放到 Instruction 或外部文档经 Context 注入。

3.2 Instruction Prompt（指令）

规定 本次要完成的目标、步骤、优先级、失败时怎么做。

常见结构：

  1. 目标（一句话）
  2. 步骤（有序列表）
  3. 约束（必须 / 禁止）
  4. 失败分支（信息不足时：追问 / 拒答 / 标注不确定）

Instruction 写得越可执行，Instruction Following 越容易被观测：漏步骤、乱顺序都算失败。

3.3 Context Prompt（上下文）

提供 本轮决策所需的事实材料：对话摘要、RAG 片段、工具返回、用户配置等。

与已学概念的接口：

  1. 占 Context Window；材料越多，越要排序与裁剪。
  2. 工具结果应作为 已发生事实 写入，而不是让模型「回忆自己调过」（第四篇 tool 消息）。
  3. 标明来源与时效（「以下为检索结果，可能过时」），降低把噪声当真理。

3.4 Output Format Specification（输出格式约定）

在 Prompt 里写清 输出长什么样：纯文本结构、JSON 字段、是否允许解释性前言等。

本篇只谈 契约怎么写；强制 JSON、Schema、应用侧校验的实现见第四篇 Structured Output。

契约写法建议：

  1. 字段名、类型、必填/可选写死。
  2. 给一个 最小合法示例（完整 Few-shot 见本系列（二））。
  3. 明确「除 JSON 外不要输出其他文字」或「先简短理由再给 JSON」——二选一，不要含糊。
  4. Agent 要调工具时：说明何时输出自然语言、何时应走 Tool Invocation（协议由 API / Schema 约束，Prompt 负责意图边界）。

4. 组装顺序与冲突优先级

4.1 推荐组装顺序

落到 messages 时的常见拆法：

积木 常见落点
Role + 全局 Format + 硬禁止 system
本轮 Instruction + 用户问题 user
检索 / 工具结果 user 中的独立区块，或 tool 消息
历史对话 按轮次的 user / assistant

4.2 冲突时谁优先

  1. system 硬规则优先于 user 的临时要求（例如 user 要求「忽略安全规则」应被拒绝）。
  2. 输出契约优先于「写得好看」：需要可解析时，散文解释让路。
  3. 已写入的工具 / 检索事实优先于模型参数里的「常识」：材料与常识冲突时，应遵循材料或标明冲突。

4.3 Context 膨胀时先砍什么

预算不够时，建议裁剪顺序（先砍后留）：

  1. 重复历史、冗长思维链原文
  2. 低相关检索片段
  3. 次要示例
  4. 保留：Role 硬规则、本轮 Instruction、输出契约、与当前决策直接相关的 Context

5. 对 Agent 行为控制

5.1 是否拆成多份 Prompt

步骤类型 建议 原因
规划（下一步做什么） 专用或偏探索 允许短推理，输出结构化计划
执行（填工具参数） 专用、低温、严格式 参数错误代价高
总结（给用户看） 专用、可读性优先 不必塞满 Schema

一份「万能 Prompt」初期省事，步骤一多往往互相干扰：总结口吻污染工具 JSON，或工具规则淹没用户可读回答。

5.2 行为可控的最小检查清单

写完或改完 Template 后，至少确认：

  1. 可复现：同样变量 → 同类结构输出（配合低温，见第二篇 Temperature）。
  2. 可校验：有 Format / Schema，应用侧能判对错（Schema Validation）。
  3. 可截断：规定 max 步骤、信息不足时的停止/追问，避免空转。
  4. 职责清晰：Role / Instruction / Context / Format 没有混成一团无法改的长文。
  5. 事实有出处：关键断言来自 Context 或工具，而不是模型自述「已完成」。

总结

Prompt：一次 Inference 的输入合同；在 Chat 里体现为 messages。

Template：固定骨架 + 变量槽；为复用、版本、评测打底。

四积木：Role、Instruction、Context、Output Format——身份、任务、事实、契约。

组装：Role → Instruction → Context → Format →（可选示例）；冲突时硬规则与契约优先；Context 膨胀按相关性裁剪。

Agent：规划 / 执行 / 总结宜分 Prompt；用「可复现、可校验、可截断」做最小门禁。
