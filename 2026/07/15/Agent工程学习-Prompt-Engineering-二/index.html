AI-Agent工程学习-Prompt Engineering(二)

发表于 2026-07-15 分类于 计算机
Prompt 推理与编排：Zero/Few-shot、CoT 与 Self-Consistency、Tree of Thoughts、Least-to-Most 与分解、Prompt Chaining，以及选型表。

接Prompt Engineering（一）：在会写可控 Prompt 的基础上，学习单轮推理技巧与多步编排。

1. 示例策略：Zero-shot 与 Few-shot

1.1 Zero-shot Prompting

只给指令，不给示范，直接让模型做题。

适用：任务表述清晰、模型本身已很熟（分类、简单改写、常见 JSON 形态）、或示范成本高。

失败常见表现：格式漂移、边界 case 乱猜。此时优先补 Output Format 或改用 Schema / 工具（第四篇），而不是先堆长篇说教。

1.2 Few-shot Prompting

在指令之外，提供 少量输入→输出示范，让模型对齐模式。

写好 Few-shot 的要点：

  1. 示例要像真实分布：覆盖正常路径 + 一两个边界（空输入、拒答）。
  2. 数量：通常 1～5 条；过多占 Context，且可能过拟合到示例措辞。
  3. 顺序：难例或关键约束相关的示例靠近「当前问题」一侧，往往更稳（仍要实测）。
  4. 正反例：可展示「错误示范 → 正确示范」，但反例要标明「以下为错误，勿模仿」。

1.3 何时用示例，何时改用 Schema / 工具

需求 更合适的手段
口吻、分类标签、短结构对齐 Few-shot
字段必须合法、可机读 JSON Schema / 约束解码（LLM 四）
需要外部真值 Tool / RAG，而不是在示例里编造「假事实」

示例解决的是 形态对齐；真伪与副作用仍靠工具与校验。

2. 推理链：Chain-of-Thought 与 Self-Consistency

2.1 Chain-of-Thought（CoT）

要求模型 显式写出中间步骤，再给出结论（「一步步想」或结构化步骤字段）。

适用：多步算术、逻辑、需要展示依据的分析。

代价：

  1. 输出 Token 变多 → 延迟与费用上升（第二篇 Inference）。
  2. 步骤本身也可能错，且错得「看起来很认真」。

2.2 何时不该强制 CoT

  1. 简单分类、抽取、严格短 JSON：多余推理易污染格式。
  2. 已走工具拿到结果：应基于结果总结，而不是再「空想推导」。
  3. 需要稳定 Tool 参数：优先低温 + Schema，而不是长思维链（Temperature）。

2.3 Self-Consistency（自评一致）

同一题用 多样本（略高 Temperature 或多次采样）各走一遍 CoT，再对最终答案 投票 / 聚合。

要点：

  1. 依赖「多次 Inference」，成本近似线性放大。
  2. 适合 有离散标准答案 的题；开放长文写作不适合简单投票。
  3. 与 Agent：可用于规划选项打分的离线增强，不宜默认挂在每个工具调用前。

3. Tree of Thoughts（ToT）

相对 CoT 的差别：CoT 基本是一条链；ToT 维护 多条候选思路（树），带扩展、评估、剪枝、回溯。

工程视角只需抓住：

  1. 状态：每个节点是一种部分方案或中间结论。
  2. 扩展：从节点生成若干下一步。
  3. 评估：启发式或再调模型打分，差的剪掉。
  4. 停止：找到可行解、深度上限、或预算耗尽。

成本：远高于单次 CoT；适合 搜索空间大、单步难判对错 的难题。Agent 里若已有外部搜索 / 仿真 / 测试工具，往往用工具探索比纯 Prompt ToT 更划算。

4. 问题拆解：Least-to-Most 与 Prompt Decomposition

4.1 Least-to-Most Prompting

把难题拆成 由易到难、有依赖 的子问题：先解决简单子题，再把答案喂给下一题。

适合：复合问答、多约束规划、需要先澄清定义再计算。

4.2 Prompt Decomposition

把一个大 Prompt / 大任务拆成 多个子 Prompt 或子目标，各自输入输出更窄。

与 Least-to-Most 的关系：Least-to-Most 强调 难度递进与依赖；Decomposition 强调 职责拆分（可并行的子任务不必强行串成由易到难）。

拆解时要写清：

  1. 子问题列表与依赖边
  2. 每个子问题的输入来自哪里（用户 / 上一子结果 / 工具）
  3. 失败回退：子步失败是重试、换策略，还是向用户追问

5. Prompt Chaining（提示链）

Prompt Chaining：上一步模型（或规则）的输出，经清洗 / 校验后，成为下一步 Prompt 的输入。

5.1 与 Tool Calling 多轮的区别

Prompt Chaining Tool Calling 多轮
中间步骤主要是 再调模型（或规则） 应用执行外部工具
真值来源 仍偏模型生成 工具返回的事实
协议 自管消息与字段 Schema → Invocation → Result（第四篇）

可以组合：链的某一步触发 Tool，工具结果再进入下一环 Prompt。

5.2 中间结果校验、短路、重试

  1. 校验：格式、必填字段、业务规则；失败不要盲目喂给下一步。
  2. 短路：已够回答用户则停止，避免为链式而链式。
  3. 重试：区分「可重试错误」（解析失败）与「需换策略」（任务不可解）。

6. 技术选型表

场景 优先手段 备注
形态对齐、短任务 Zero / Few-shot 格式硬需求叠加 Schema
多步推理、有标准答案 CoT；难题可加 Self-Consistency 看清 Token 预算
大搜索、多候选方案 ToT 或外部搜索工具 纯 ToT 最贵
复合题、依赖清晰 Least-to-Most / Decomposition 先画依赖再写 Prompt
多阶段流水线 Prompt Chaining 每环校验；真值步骤用 Tool

按 Agent 步骤类型：

步骤 推荐
规划 短 CoT 或结构化计划；必要时 Decomposition
执行（工具参数） Zero/Few + 严格 Format；低温；少散文推理
总结 Zero-shot + 可读约束；依据 Context/工具结果

探索（想方案）与执行（填参数）不要混在同一温度、同一松紧契约里。

总结

示例策略：Zero-shot 靠指令；Few-shot 靠示范对齐形态。

推理链：CoT 换可解释步骤；Self-Consistency 用多样本投票，成本高。

ToT：树状搜索，贵；有外部工具时优先工具探索。

拆解：Least-to-Most（由易到难）与 Decomposition（职责拆分）常一起用。

Chaining：多步 Prompt 编排；与 Tool 多轮互补，中间必须校验。

选型：按场景与 Agent 步骤选，而不是默认「越复杂越聪明」。
