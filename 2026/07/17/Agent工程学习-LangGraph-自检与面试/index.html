AI-Agent工程学习-LangGraph(自检与面试)

发表于 2026-07-17 分类于 计算机
LangGraph 六篇正文的学习自检与面试导向问答；覆盖状态、执行、持久化、HITL 与多 Agent 拓扑。

本文是 LangGraph（一）～（六）的阶段性验收。目标不是背 API 名称，而是能从业务约束出发，设计一张具备状态合并、分支循环、持久恢复、人工门禁与多 Agent 协作能力的图，并解释每项取舍。

0. 使用说明

建议先遮住“推荐回答”，在 60～120 秒内口述答案。自检题用于逐篇查漏补缺；面试题要求先给结论，再说明机制、风险与工程措施。

回答时重点检查四件事：

  1. 是否区分模型决策与 Runtime 确定性控制。
  2. 是否说明 State 字段、Reducer 与状态生命周期。
  3. 是否覆盖失败恢复、幂等、副作用和停止条件。
  4. 是否能把概念落到一张可执行、可观测的图。

1. 学习自检

1.1 定位、模块地图与图设计

S1. LangGraph 在 Agent 技术栈中解决什么问题？它与 LangChain create_agent 如何分工？

推荐回答： LangGraph 是低层编排 Runtime，负责显式拓扑、共享状态、持久化、中断恢复、流式事件与多 Agent 组织；create_agent 是预构建 Agent harness，适合标准“模型—工具”闭环及 Middleware。标准单 Agent 环能满足需求时优先 create_agent；需要确定性步骤与 Agent 步骤混合、跨故障恢复、任意点 HITL 或复杂多 Agent 拓扑时使用 LangGraph。两者并非替代关系，编译后的 create_agent 可以直接作为图节点。

S2. 请画出 LangGraph 的模块地图，并说明一次状态更新如何穿过各层。

推荐回答： 可分为定义层、拓扑层、Runtime、持久层和控制层。定义层用 State Schema 与 Reducer 规定数据及合并语义；拓扑层用 Node、Edge、Command、Send 和 Subgraph 描述计算与转移；Runtime 以 superstep 调度节点并通过 channel 传递状态；Reducer 在超步边界合并 partial update；Checkpointer 可保存快照；Streaming、Interrupt 和 Time Travel 再从执行过程投影事件、挂起或分叉。模块地图的价值是帮助定位故障属于状态、路由、调度还是持久化。

S3. 请设计一张同时包含条件分支、失败回环和明确退出条件的图，不要只背入口/出口常量。

推荐回答： 例如研究报告图可设计为：入口进入 plan，再按任务列表动态分派 research；汇合后进入 write，随后由 verify 判断。合同通过则退出；未通过且预算充足则回到 write；预算耗尽则进入 handoff 写出失败原因和人工接管信息后退出。图中需把 retry_count 或 remaining_budget 放入 State，同时配置 recursion_limit。入口和出口哨兵只是接线工具，真正重要的是分支依据、回环进展量与可解释退出。

S4. DAG 与 Loop Graph 各适合什么场景？为什么 Agent 编排不能只按 DAG 理解？

推荐回答： DAG 适合步骤和依赖固定、无需回退的流程，例如解析、检索、生成、格式化。Loop Graph 适合工具调用、验证不通过重写、规划迭代与失败换策略。Agent 的下一步常由中间 Observation 决定，并可能重复调用工具或修订结果，因此有状态回环是核心能力。回环必须同时具备业务停止条件、进展检测、预算字段和图级硬顶。

S5. Graph API 与 Functional API 应如何选型？

推荐回答： 需要显式查看节点、边、条件路由、循环和图可视化时选 Graph API；已有普通函数式任务流，只想增加持久化、流式、任务化和 HITL 时可用 @entrypoint、@task 的 Functional API。两者共享 Runtime 且可混用。选择依据是控制流是否需要成为可审查的一等结构，而不是哪种写法代码更短。

S6. compile()、invoke() 与 Runnable 语义分别意味着什么？

推荐回答： compile() 校验拓扑并注入 checkpointer、store 等运行依赖，产出可执行图；该产物是 Runnable，可使用 invoke、stream、batch 等统一接口。invoke(input, config) 提供初始状态和本次执行配置，持久化场景还需在 config 中提供 thread_id。编译成功只说明结构可运行，不代表 Reducer、幂等与业务退出条件正确。

1.2 State、Partial Update 与 Reducer

S7. State Schema 为什么是图设计的地基？可使用哪些定义方式？

推荐回答： State 是节点之间的显式合同，决定节点能读取什么、能更新什么，以及哪些信息可被 checkpoint。可使用 TypedDict、dataclass、预置 MessagesState 等；对话图常继承 MessagesState 再加入目标、预算、合同状态和交接信息。Schema 应按生命周期和职责设计，而不是把所有中间对象塞进一个巨型字典。

S8. Node 返回值与 invoke 输入的完整 State 是什么关系？

推荐回答： invoke 输入用于初始化或向已有 thread 注入状态；节点通常只返回自己负责字段的 partial update，而不是复制整份 State。Runtime 再按每个字段的 Reducer 把更新合入当前快照。这样能减少无关字段覆盖，也让并行分支的合并语义可声明。

S9. messages 为什么通常需要 add_messages，而不是默认覆盖？

推荐回答： 对话与工具环需要保留历史消息，并把新 AI、Tool 或 User 消息追加进去；默认覆盖会让前文丢失。MessagesState 已为 messages 配置 add_messages，它还可按消息 ID 处理替换等消息语义。即使使用追加 Reducer，也要做上下文裁剪或摘要，不能让 checkpoint 和模型 Context 无限增长。

S10. 预算计数应该用覆盖还是累加 Reducer？

推荐回答： 取决于节点输出合同。若字段使用 operator.add，节点必须返回增量，例如每步返回 1；若采用覆盖语义，节点应读取旧值并返回计算后的新总量。团队必须统一一种语义，不能 Reducer 要增量、节点却返回累计值，否则重放和并行合并会重复计数。剩余预算常用覆盖，事件计数可用累加。

S11. 哪些字段不应被摘要节点覆盖？

推荐回答： 当前目标、权限与硬规则引用、剩余预算、合同校验结果、待执行副作用、幂等键、错误原因和 handoff_note 等治理字段应独立保存。摘要只压缩可再表达的对话或工具长文本，不能把决定路由和恢复正确性的字段藏进自然语言摘要，否则压缩后可能丢合同、误判完成或重复执行。

S12. 并行分支写同一个键时，Reducer 应满足哪些性质？

推荐回答： 合并操作至少应可结合；业务不依赖分支完成顺序时还应可交换。列表拼接若下游依赖固定顺序，应在结果中携带稳定序号并在汇合后排序。Reducer 只解决状态合并，不自动解决外部副作用去重；写库、发消息等仍需稳定业务键、幂等记录或事务。

S13. State 中出现不可 JSON 序列化对象会造成什么问题？如何处理？

推荐回答： Checkpointer、Time Travel 和跨进程恢复依赖状态可持久化，不可序列化的连接、客户端或生成器会导致 checkpoint 失败或后端绑定。State 应保存可序列化的业务值和外部资源标识；数据库客户端、模型实例等通过闭包、依赖注入或 Runtime 提供，不进入快照。

S14. 如何避免多 thread 串台和 State 竞争？

推荐回答： 不使用模块级可变全局变量保存会话状态；线程内状态交给 checkpointer 并使用唯一 thread_id，跨线程用户数据放 Store 且以租户、用户等 namespace 隔离。并行节点尽量写不同键；确需同键时声明明确 Reducer。高并发外部写入还需依赖数据库并发控制，不能假设图内 Reducer 能保护图外资源。

1.3 Node、Edge、Command、Send 与拓扑语义

S15. Node 与 Edge 应分别承担什么职责？

推荐回答： Node 读取 State、执行单一计算或受控副作用并返回更新；Edge 决定下一跳。固定顺序用普通边，基于 State 的分流用 conditional edge。将业务计算和路由依据分清，可独立测试节点结果与转移规则；但当更新与路由构成不可分割的治理决策时，可由节点返回 Command。

S16. Conditional Edge 与 Command 有什么区别？

推荐回答： Conditional Edge 把“节点计算”和“之后如何走”分开，适合复用同一节点结果、集中展示拓扑；Command 可在一次返回中同时更新 State 并指定 goto，适合验证门、handoff 等更新与路由强绑定的逻辑。不能因 Command 方便就把所有控制流藏进节点，否则图的可读性会下降。

S17. Send 与静态 fan-out 的分水岭是什么？

推荐回答： 静态 fan-out 的分支数量和目标节点在建图时已知；Send 根据运行时 State 动态创建 N 个任务，例如对 N 篇文档或 N 个研究主题分别处理。每个 Send 可携带独立输入切片，结果写回共享字段时依赖 Reducer。若 N 可控且固定，普通并行边更简单。

S18. Fan-in 为什么不能依赖分支执行顺序？

推荐回答： 并行分支在同一 superstep 中执行，完成先后受调度和外部延迟影响，汇合节点只能依赖提交后合并的 State。若输出顺序有业务意义，应显式携带索引、来源或优先级，再确定性排序。把“先返回的就是第一项”写进业务逻辑会导致非确定性结果。

S19. 何时应把 create_agent 直接作为 Node？

推荐回答： 当子任务本质是标准模型—工具循环，且希望复用 Middleware、工具错误处理、压缩或 HITL 时，可直接嵌入编译后的 create_agent。外层 LangGraph 负责确定性预后处理、跨 Agent 路由、持久化和验证门。若必须在每次模型与工具调用之间插入审批、预算或改写节点，再考虑手画工具环。

S20. 何时应使用 ToolNode 与 tools_condition 手画工具环？

推荐回答： 需要细粒度控制模型节点和工具节点之间的每条边，或要插入参数复核、人工审批、独立预算、结果清洗和错误路由时使用。tools_condition 根据末条 AI 消息是否包含 tool calls 决定进入工具节点或退出，ToolNode 执行工具调用。若只是标准工具环，直接使用 create_agent 可减少样板和维护成本。

S21. Router 与 Supervisor 的控制粒度有什么不同？

推荐回答： Router 通常做一次或少数几次分类，把请求送到某个固定分支；Supervisor 是持续参与的中心协调者，会根据任务进展反复选择专家子图并接收 handoff。简单意图分流用 Router，跨角色迭代协作才需要 Supervisor。Supervisor 也必须受可选目标集合、预算和结束条件约束，不能让模型任意跳转。

S22. 一个可靠的 handoff 至少包含哪些信息？

推荐回答： 至少包括目标摘要、已完成与未完成事项、关键证据及来源、硬规则或合同引用、剩余预算、当前错误与期望交付格式。不要把整个消息历史无差别传给下一个 Agent；应提供最小充分上下文，并保留可追溯的原始产物指针。

1.4 Persistence：Checkpointer、Store 与 Runtime Context

S23. Checkpointer 与 Store 各解决什么？能否只使用一个？

推荐回答： Checkpointer 保存单个 thread 的图状态快照，用于多轮续跑、故障恢复、Interrupt 和 Time Travel；Store 保存跨 thread 的应用级 KV，如用户偏好与长期事实。仅需要一次性无状态任务时两者都可不用；只需线程内恢复可只用 Checkpointer；换新 thread 仍需记住用户信息则要 Store。完整会话产品通常两者都用。

S24. 为什么应使用 thread_id，而不是模糊地说 Session？

推荐回答： thread_id 是 LangGraph checkpointer 定位一条 checkpoint 链的明确配置键；Session 可能在业务中指登录会话、浏览器会话或订单流程，语义不唯一。工程上可让业务会话 ID 映射到 thread_id，但应说明映射、租户隔离、生命周期和并发策略。

S25. 多轮对话丢失历史时，首先检查什么？

推荐回答： 先确认图编译时是否注入 checkpointer、两次调用是否使用同一持久化后端和同一 thread_id，再检查 messages 是否使用正确 Reducer、输入是否误覆盖历史，以及进程重启后是否仍连接原后端。只复用变量名而没有持久化链，不能实现多轮续跑。

S26. Durable execution 与外层 while 重跑整图有什么差别？

推荐回答： Durable execution 利用已提交 checkpoint 从最近可恢复边界继续，已成功 superstep 不必全部重做；外层 while 通常从头执行，浪费模型和工具调用，并可能重复副作用。恢复并不自动保证业务 exactly-once，失败节点或 Interrupt 所在节点仍可能重放，所以幂等设计不可省略。

S27. Checkpoint 恢复要同时满足哪些条件？

推荐回答： 必须复用同一持久化 checkpointer 后端、提供同一 thread_id，并保证重放节点的外部副作用可幂等或可查询执行状态。还要确保代码与 State Schema 版本兼容；若工作流升级改变字段或节点，需要迁移、版本路由或终止旧线程，不能假设任意版本都能直接续跑。

S28. user_id、thread_id 与 Store namespace 应如何分工？

推荐回答： thread_id 标识一条执行与 checkpoint 链；user_id 是本次运行的身份上下文，可通过 context_schema 注入；Store namespace 可由租户、用户和数据类别组成，实现跨 thread 共享与隔离。不要把 user_id 当 thread_id，否则同一用户的并发任务可能互相污染。

S29. Store 与 RAG VectorStore 为什么不能直接画等号？

推荐回答： LangGraph Store 的核心职责是跨 thread 保存和检索应用级 KV，可选支持语义索引；RAG VectorStore 面向大量文档向量的相似度召回、过滤和索引运维。用户偏好可放 Store，企业知识库通常使用专门 VectorStore。二者可组合，但数据模型、访问模式和容量目标不同。

S30. context_schema 适合放什么？哪些内容仍应进入 State？

推荐回答： Context 适合本次调用的环境参数，如用户、租户、权限主体和外部服务配置引用，这些值通常不作为业务进度被 checkpoint。会影响恢复后路由与任务完成情况的目标、预算、工具结果和合同状态应进入 State。判断标准是该值属于“本次运行环境”还是“可恢复业务进度”。

1.5 Runtime、Superstep、Streaming 与重试

S31. 请解释一次 superstep 的执行与提交过程。

推荐回答： Scheduler 选出当前可运行节点；这些节点读取同一超步开始时的 State/channel 值并执行；各自产生 partial update；Reducer 在超步边界合并更新；成功后提交并可写 checkpoint；下一 superstep 再读取新状态。这个模型解释了并行、状态可见性和恢复边界。

S32. Superstep 中一个并行分支失败，其他成功分支的 State 更新会怎样？

推荐回答： 该 superstep 的更新整体不提交，体现事务感；若重试或恢复，该超步中的任务可能再次执行。此前已经成功提交的 superstep 不需要重做。注意“状态未提交”不等于外部副作用自动回滚，成功分支若已经写库仍需幂等、事务或补偿。

S33. 节点重试与 checkpoint 恢复分别适用于什么失败？

推荐回答： 节点重试适合临时网络错误、限流等局部可恢复故障，应有分类、退避和次数上限；checkpoint 恢复适合进程崩溃、部署重启或长任务中断，依靠持久状态续跑。不可恢复的参数、权限或业务错误不应原样重试。外层整图重跑通常是最后选择。

S34. values、updates、messages 与 custom 流分别适合什么前端需求？

推荐回答： values 展示每步后的完整 State，直观但数据量大；updates 只发送节点局部更新，适合工作流进度和调试；messages 提供 LLM token 与 metadata，适合聊天逐字输出；custom 由节点主动发业务进度，如“已检索 3/10 篇”。生产前端通常组合 messages 与 updates/custom，并按 thread、run、node 和事件序号去重。

S35. stream() 与 stream_events() 应如何区分？

推荐回答： stream() 按指定 stream_mode 投影图运行结果，适合消费 State、消息或自定义进度；stream_events(..., version="v2") 提供更细粒度、统一结构的 Runnable 事件，适合通用可观测与链路集成。二者不是同一个参数体系。选型取决于 UI 需要业务投影还是底层执行事件。

S36. 为什么有业务停止条件后仍要设置 recursion_limit？

推荐回答： 业务条件可能因模型输出、状态错误或路由 Bug 失效，recursion_limit 是限制 superstep 数的最后保险丝。它不能替代 State 中的软预算和优雅收尾分支；触顶应记录结构化原因并告警，而不是静默调大上限。可靠循环通常有业务 Done、无进展检测、软预算和图级硬顶四层。

S37. 如何判断一个 Agent 回环“有进展”？

推荐回答： 应定义可观测进展量，例如新增有效证据数、未解决子任务数下降、校验错误数下降、测试通过数上升，或工具调用指纹发生有意义变化。连续多轮相同工具与相同参数、结果摘要无变化或合同分数不提升可判定停滞，随后换策略、转人工或优雅退出，不能只看模型是否声称“正在继续”。

1.6 Interrupt、HITL 与 Time Travel

S38. interrupt() 为什么必须配合 checkpointer 与 thread_id？

推荐回答： Interrupt 要把挂起前的已提交状态保存下来，并在外部审批后找到同一执行链继续；checkpointer 提供快照，thread_id 提供定位。缺少任一项，进程无法可靠恢复。传给 interrupt() 的 payload 还应可序列化，便于 UI 展示和审计。

S39. Command(resume=value) 与 interrupt() 的返回值是什么关系？

推荐回答： 首次执行到 interrupt(payload) 时图挂起并把 payload 暴露给调用方；之后使用同一 thread_id 传入 Command(resume=value)，该 value 会成为节点重放时 interrupt() 调用的返回值，节点据此继续分支。Resume 是恢复协议，不是从 Python 栈的下一行原地续跑。

S40. 为什么 interrupt() 前的逻辑必须幂等？

推荐回答： 恢复时节点从开头重跑，而不是从中断行继续，因此中断前的代码会再次执行。若那里已发送邮件、扣款或写入订单，就可能产生重复副作用。应把纯计算放在 Interrupt 前，将批准后的副作用拆到独立节点，并以业务幂等键、状态查询或事务保证重放安全。

S41. HITL 与 Loop Engineering 的 Verification Gate 如何对应？

推荐回答： 确定性规则能判断时先用验证节点；高风险、语义模糊或需责任确认的动作再通过 Interrupt 交给人。人的批准、拒绝或修改进入 Resume 值或更新后的 State，再由图决定下一跳。HITL 是一种外部 Gate，不应代替所有可自动化校验。

S42. Time Travel 的查看、重放与分叉分别解决什么问题？

推荐回答： get_state 和 get_state_history 用于查看当前及历史快照；从历史 config 再次执行可重放后续过程；update_state 在旧 checkpoint 上写入修订值并产生新 checkpoint，再继续形成分叉。它适合复现失败、A/B 路由和审计假设，不是直接覆盖或回滚原历史。

S43. 为什么不建议用 try/except 包住 interrupt()，也不建议在一个节点内写 while True + interrupt()？

推荐回答： Runtime 依赖特殊控制流异常完成挂起，普通捕获可能破坏协议。节点内无限循环中断还会让校验、状态变化和重放边界难以观察。应让一次节点执行只处理一次交互，校验失败后返回状态并通过边回到节点，使每轮都经过清晰的 superstep 和 checkpoint。

1.7 Subgraph、Multi-Agent 与 Research 端到端

S44. 子图 checkpointer=None、True 与 False 的语义如何选择？

推荐回答： 默认 None 适合多数一次子任务，单次调用内可继承父图能力；True 用于子图需要在同一 thread 跨多次调用保留自身状态；False 让子图不做 checkpoint，适合纯函数式、无需 Interrupt 和 durable 的流程。父图需要配置 checkpointer，子图的中断与持久能力才有完整基础。

S45. 父图和子图如何共享数据，为什么不能无边界共享全部 State？

推荐回答： 父子 Schema 相同时可直接传递共享字段；不同时通过包装节点显式做输入输出映射；跨子图长期共享事实优先使用 Store。全量共享会扩大耦合、checkpoint 体积与字段冲突，也容易让专家 Agent 看到无关或敏感上下文。每个子图应拿到完成职责所需的最小状态切片。

S46. L2 Supervisor 拓扑与“只使用 LangChain Middleware”的分水岭是什么？

推荐回答： Middleware 主要治理单个 Agent harness 内的模型和工具调用；当系统需要多个专家子图、中心分派、跨子图 handoff、图级验证门、统一预算和持久恢复时，已经进入 LangGraph 的 L2 拓扑。若只有一个标准工具 Agent，增加 Supervisor 反而会提高 Token、延迟和故障面。

S47. 请完整解释 Research 迷你图每个阶段的职责与状态变化。

推荐回答： planner 把 query 拆成 subtasks；Send 按运行时任务数并行创建 research_worker；workers 以带来源的 notes 增量写回，由 Reducer 合并；combine 去重并形成提纲；writer 生成 draft；verify 做合同与引用检查。通过则退出；失败且可修复则回 writer，风险高或预算不足时 Interrupt 或写 handoff。外层图负责确定性编排，worker 内可嵌 create_agent 负责工具选择。

S48. Multi-Agent 上线前最容易遗漏哪些工程边界？

推荐回答： 常见遗漏包括子 Agent Context 未隔离、Store namespace 串租户、handoff 丢硬规则、并行写同键无 Reducer、失败子任务无降级、Supervisor 无预算、checkpoint 与代码版本不兼容，以及只记录最终回答而没有节点级 Trace。多 Agent 的价值必须由任务成功率证明；若只是增加角色名称却没有独立工具、状态或验收职责，应退回更简单拓扑。

2. 面试真题

以下题目按主题归纳、改写自公开面经与题库，用于训练表达，并非逐题对应某一场真实面试；综合参考来源见文末「参考面经与题库」。

I1. 什么情况下你会选 LangGraph，而不是简单 Chain 或 create_agent？

推荐回答： 我先看是否存在真实的显式控制需求：多分支或回环、长任务断点恢复、人工审批、动态并行、多个 Agent 子图和图级验证门。若只是“分类—检索—回答”或标准工具环，Chain 或 create_agent 更简单；若需要审计每个状态转移，并在故障后从 checkpoint 恢复，LangGraph 更合适。代价是团队要维护 State Schema、Reducer、边与版本兼容，所以不能为了框架标签过度设计。

I2. 你会怎样为一个多阶段 Agent 设计 State？

推荐回答： 我先按生命周期拆字段：输入与目标、节点中间产物、路由标志、预算与重试、错误与 handoff、审计标识。对每个字段写清生产者、消费者、覆盖还是追加、何时清理及是否进入 checkpoint。并行结果使用可结合 Reducer并携带稳定来源；连接和客户端不进 State；跨会话偏好进 Store。最后用失败恢复和并发写场景审查 Schema，避免一个 messages 承担全部业务语义。

I3. 多 Agent 并行执行时，如何解决 State 竞争？

推荐回答： 首选让各分支写不同键或写入带 worker ID 的独立结果；必须写同键时定义可结合、必要时可交换的 Reducer，汇合后再按稳定索引排序。图内 State 合并只在 superstep 边界完成，节点不能依赖完成先后。若竞争发生在数据库或第三方系统，还要使用乐观锁、事务、幂等键或队列串行化，不能把 Reducer 当成分布式锁。

I4. Checkpoint 恢复时，如何避免工具重复执行和业务重复副作用？

推荐回答： 我不会承诺框架自动提供 exactly-once。恢复或 Interrupt resume 都可能重放节点，因此先把纯推理、审批和副作用拆成不同节点；对写操作生成稳定业务幂等键，在执行前查状态，执行后持久化结果和外部流水号；能使用数据库唯一约束或事务时再加一层保护。超时状态不明时先查询，不盲目重试；不可幂等动作需补偿或人工接管。

I5. 如何设计 checkpoint 的 thread_id、存储后端和生命周期？

推荐回答： thread_id 是编排执行链标识，不直接复用用户 ID；我会以租户和业务任务生成唯一映射，并对并发运行制定单写或分支策略。开发可用内存后端，生产使用数据库型持久后端并做高可用、加密、TTL、备份和容量监控。State 中敏感字段需最小化或脱敏；代码发布要记录图与 Schema 版本，旧 thread 通过迁移、兼容节点或版本路由恢复。

I6. 前端使用 SSE 展示 LangGraph 执行进度时，你会怎样设计事件协议？

推荐回答： 后端组合 messages 与 updates/custom：token 用于文本展示，节点更新用于步骤状态，自定义事件用于业务进度。每个事件带 run ID、thread ID、node、event type、单调序号和时间，客户端按 ID 去重并区分展示流与控制流。重连时从最后确认事件续传；若底层无法无损续流，则读取 checkpoint 展示当前状态并明确重启策略。工具只有在完整参数校验后执行，不能由半截 token 触发。

I7. 如何防止 LangGraph 中的 Agent 死循环？

推荐回答： 我会同时设置四层控制：业务完成合同由确定性验证节点判断；State 中记录步数、时间、Token、费用和工具次数等软预算；比较工具调用指纹、证据增量或错误下降判断是否有进展；最后配置 recursion_limit 作为 superstep 硬顶。达到软预算时走 handoff 或降级节点，触顶则记录结构化原因和 Trace，不通过无限提高上限掩盖路由 Bug。

I8. 线上某个并行 superstep 有三个分支，其中一个超时，另外两个已调用外部服务成功。你如何恢复？

推荐回答： 图内该 superstep 的 partial updates 不会提交，但两个外部调用未必回滚。恢复前先用任务 ID 和幂等键查询三项外部状态：已成功项复用结果并写回，确定失败项按分类重试，状态未知项先对账。节点实现应把外部结果持久化到可查询的业务记录，避免只存在未提交的 State 中。若无法安全判定，进入人工补偿分支，而不是整超步盲目重放。

I9. Command、Conditional Edge 和 Send 如何选型？

推荐回答： 固定下一跳用普通 Edge；路由逻辑希望独立、可复用和直观看图时用 Conditional Edge；节点更新与治理路由必须原子表达时用 Command(update, goto)；分支数量由运行时数据决定时用 Send 动态展开。它们解决的是不同维度，不能互相简单替代。无论哪种路由，目标集合、State 输入和汇合 Reducer 都应明确。

I10. 请设计一个带 HITL 的高风险付款工作流。

推荐回答： 图可设计为：解析请求—读取订单与权限—确定性校验金额和收款方—生成付款意图—interrupt 展示证据与风险—人工批准或拒绝—独立执行付款节点—对账—退出。Interrupt 前不产生付款副作用；Resume 使用同一 thread_id，批准值只代表授权，不代表支付成功。执行节点使用订单号加操作类型构造幂等键，超时先查支付状态；拒绝、校验失败和状态未知均有独立分支与审计。

I11. Time Travel 能否用于生产回滚？有哪些风险？

推荐回答： 它更准确地说是从历史 checkpoint 查看、重放或创建新分支，不会撤销外部世界已经发生的副作用，也不会覆盖原历史。因此可用于复现、A/B 与修订 State 后重跑，但订单、邮件、支付等要单独做补偿或幂等检查。分叉还应记录操作者、来源 checkpoint、修改字段和新 run，避免审计上把“假设分支”误当成原执行。

I12. Router、Supervisor 和 Swarm 三种多 Agent 模式如何取舍？

推荐回答： 单次意图分类、分支彼此独立时用 Router；任务需多轮协调、专家之间存在依赖时用 Supervisor，并限制可选专家、handoff 合同与总预算；对等协作的 Swarm 只有在中心协调确实成为瓶颈、各 Agent 能自治且冲突有解决协议时才考虑。LangGraph 没有必须使用的独立 Swarm API，本质仍是节点、状态、边和 Store。多数业务从 Router 或单 Supervisor 起步更可控。

I13. 一个 Research Agent 的某个子任务返回空数据，你如何重试或降级？

推荐回答： Worker 先返回结构化状态，区分无结果、限流、权限、解析错误和不可恢复错误。限流可有限退避重试；无结果可改查询词、切备用检索源或降低为“证据不足”；权限错误直接停止该路径；关键子任务失败则 Interrupt 请求补充。Supervisor 根据子任务重要性决定局部重试、跳过还是终止，最终 verify 检查证据覆盖率，禁止 writer 用模型常识填补空白。

I14. 如果一个 LangGraph 项目效果不好，你会如何监控和归因？

推荐回答： 我会记录每个 run 的图版本、thread、节点时延、重试、输入输出摘要、State 差异、所走边、模型与工具调用、checkpoint 和 interrupt 事件。先把失败分为节点计算错误、路由错误、Reducer/State 污染、外部依赖、预算触顶和恢复重放，再针对失败簇建立回归。质量指标除最终答案外，还包括合同通过率、工具成功率、证据覆盖、人工介入率、恢复成功率、成本和 P95；监控必须能回答“哪一个状态转移导致失败”。
