AI-Agent工程学习-LangChain(自检与面试)

发表于 2026-07-17 更新于 2026-07-20 分类于 计算机
LangChain 六篇阶段自检与面试导向问答；覆盖 LCEL、RAG、create_agent、Streaming、Memory 与 Middleware。

完成 LangChain（一）～（六）后，重点不应是背诵类名，而是能根据任务判断：该走确定性 LCEL、标准 create_agent harness，还是下沉到 LangGraph 自定义编排。本篇用场景题检查组件边界、执行轨迹与治理能力，再用网易、字节 AI 应用开发面经中的高频追问训练工程表达。

0. 使用说明

建议先遮住“推荐回答”，在 60～120 秒内口述：

  1. 先给选型结论，再解释数据流或消息轨迹。
  2. 明确模型负责什么、harness 或 Runtime 负责什么。
  3. 补充失败模式、观测方式与确定性门禁。
  4. 若只能说出 API 名，却说不出何时不用它，视为尚未掌握。

1. 学习自检

1.1 定位、Harness、Messages 与 Model

S1. 一个需求同时包含固定清洗、知识检索和模型自主调用工具，你会如何用 LangChain 模块地图拆解？

推荐回答： 输入与对话用 Messages 或 Prompt 表达；固定清洗、检索和格式化用 Runnable/LCEL；生成决策使用 ChatModel；知识侧由 Loader、Splitter、Embeddings、VectorStore、Retriever 组成；需要模型自主决定是否调用检索或业务工具时，把能力封装成 Tool，交给 create_agent；重试、摘要、审批和护栏放 Middleware；跨轮状态由 checkpointer 管理，轨迹进入 LangSmith。若固定步骤、复杂分支和 Agent 节点需要组合，再下沉 LangGraph，而不是继续堆一条巨链。

S2. 为什么说 Agent = Model + Harness？只调用一次 ChatModel 缺少哪些能力？

推荐回答： Harness 完整定义见 Agent（三）§6。LangChain 提供 Model + 可定制薄 Harness。Model 只负责根据当前消息预测回复或提出 tool_calls；Harness 负责维护消息状态、执行真实工具、把 ToolMessage 写回、继续调用模型，并提供 Prompt、结构化输出、预算、重试、记忆、流式、审批与观测。单次 ChatModel 调用最多产生一次候选动作，不会自动执行工具，也不会验证业务是否完成。可靠 Agent 的关键不是模型“更自主”，而是概率性决策被可观察、可中断的执行环境包围。

S3. 同事把 LangChain、LangGraph 和 Deep Agents 都称为“Agent 框架”，你会怎样澄清边界？

推荐回答： LangChain 提供模型、Prompt、Tool、Retriever、Runnable 以及可定制的 create_agent harness；LangGraph 是更低层的有状态编排 Runtime，适合显式节点、分支、循环、持久化、中断恢复和多 Agent 拓扑；Deep Agents 则是在 LangChain/LangGraph 基础上预装压缩、虚拟文件系统、Skills 和 subagent 等厚能力。标准单 Agent 工具环优先 LangChain，复杂确定性拓扑用 LangGraph，需要开箱即用的厚 harness 才考虑 Deep Agents。

S4. 用户问天气时，一次成功工具调用在 messages 中应形成什么轨迹？

推荐回答： 先有 HumanMessage("上海天气？")；模型返回带 tool_calls=[{name, args, id}] 的 AIMessage，这只是 Action；Harness 执行工具后追加与该 ID 对齐的 ToolMessage，这是 Observation；模型再次读取完整消息列表，生成不再含 tool_calls 的最终 AIMessage。若 call ID 对不上，模型无法可靠关联调用与结果；若没有真实 ToolMessage，模型声称“已查询”也不构成执行证据。

S5. SystemMessage、HumanMessage、AIMessage、ToolMessage 应分别承载什么？为什么不能把外部工具结果升格为 system？

推荐回答： SystemMessage 放应用控制的身份、硬规则和长期指令；HumanMessage 放用户目标与输入；AIMessage 放模型回复或工具调用意图；ToolMessage 放真实执行结果或错误，并关联 tool_call_id。外部工具结果属于 Observation，可能过期、错误或含注入内容，不是新的最高优先级规则；升格为 system 会破坏指令与数据边界。权限、审批和业务校验仍必须由 Runtime 落实。

S6. 在客服 Agent 中，ChatModel 与 Embeddings 各自处于哪条链路？能否互换？

推荐回答： ChatModel 消费消息并生成自然语言、结构化结果或工具调用，是推理与决策组件；Embeddings 把查询和文档块编码成向量，服务索引与语义检索。二者训练目标、输入输出粒度和接口不同，不能用 ChatModel 的 Token Embedding 直接替代文档向量，也不能让 Embedding Model 生成回复。常见链路是 Embeddings 支撑 Retriever，Retriever 的结果再作为 Context 或 Tool Observation 交给 ChatModel。

1.2 Runnable、LCEL 与确定性工作流

S7. 订单问答需要固定执行“规范化问题 → 检索 → 组装 Prompt → 生成答案”，你选 LCEL 还是 create_agent？为什么？

推荐回答： 路径固定且每步职责明确，应优先 LCEL，把函数、Retriever、Prompt 和 Model 组合成 RunnableSequence。这样控制流确定、成本可预估，也更容易单测和重放。只有当模型需要根据中间结果决定“是否检索、调用哪个工具、是否继续”时才使用 create_agent。不能因为链路里有 LLM 就一律做 Agent；是否需要模型选路才是分界。

S8. 为什么 Runnable 的统一接口对替换组件和上线治理有价值？

推荐回答： Prompt、Model、Retriever、LCEL 链、create_agent 编译产物和 LangGraph 图都可暴露 invoke、stream、batch 等统一调用形态。调用方可以在不改整体接入协议的情况下替换某段链或编排方式，并统一叠加配置、回调、追踪和并发策略。但统一接口不代表输入输出合同天然兼容，替换前仍要核对字典键、消息类型、流式 chunk 与错误语义。

S9. 一个 RAG Prompt 同时需要原问题和检索上下文，RunnablePassthrough 解决了什么？

推荐回答： 输入问题需要扇出为两支：一支进入 Retriever 并格式化成 context，另一支通过 RunnablePassthrough 原样保留为 question；两支汇合成字典后交给 Prompt。Passthrough 不做推理，它解决的是“保留原输入供下游复用”。如果直接把问题只送入 Retriever，下游通常只剩文档列表，Prompt 会丢失用户原始问题。

S10. 业务要求“同一篇文档并行生成摘要和关键词，随后合并为报告”，请用 LCEL 串并行思维描述方案。

推荐回答： 先用 RunnableParallel 将同一文档扇出到摘要链和关键词链，并行产出 {"summary": ..., "keywords": ...}；再用 | 把合并字典串到报告 Prompt、ChatModel 和结构化输出步骤。这里应讲清 Parallel 负责同输入多支并发，Sequence/| 负责前后依赖。旧资料中的 RunnableMap 可理解为同类映射能力，新代码围绕 LCEL 的串行与并行数据流设计，不必背旧名。

S11. RunnableLambda、RunnableBranch 和 Fallbacks 各适合解决什么，不适合解决什么？

推荐回答： Lambda 将确定性的普通函数，如清洗、截断和格式化，接入 Runnable 管道；Branch 适合基于明确条件选择少量支路；Fallbacks 在主模型或主链失败时切备用实现。它们不适合承载复杂长运行状态机：分支多、存在循环、要持久化恢复时应使用 LangGraph。Fallback 也不是无条件吞错，必须限定可降级错误并记录主链失败原因。

1.3 Prompt、Tool 与 Structured Output

S12. 同一项目里，什么时候用 system_prompt，什么时候用 ChatPromptTemplate？

推荐回答： 标准 Agent Loop 的稳定身份和行为规则放进 create_agent(..., system_prompt=...)，用户轮次通过 messages 输入；固定 Chain/RAG 管道需要变量插值、多角色模板或 MessagesPlaceholder 时使用 ChatPromptTemplate。运行时动态裁剪 Prompt、模型或工具集合更适合 Middleware。二者不是互斥概念，而是分别服务 Agent harness 与确定性链的主要入口。

S13. 为什么新链路优先 schema 驱动的 Structured Output，而不是自由文本加正则或经典 OutputParser？

推荐回答： Schema 能明确字段、类型和必填项，并在生成或返回阶段校验，失败可观测且便于业务消费；自由文本加正则容易受措辞、代码围栏、漏字段和截断影响。单次模型调用可用 with_structured_output，Agent 最终交付可用 response_format 并读取 structured_response。但结构合法不等于业务正确，金额、权限、引用和置信度范围仍需应用侧规则验证。

S14. 一个工具经常被误选或生成错误参数，你会先检查哪些地方？

推荐回答： 先检查工具名是否稳定且可区分，description 是否写清“何时用、何时不用”，参数类型、枚举、范围和必填项是否能生成明确 JSON Schema；再检查是否一次暴露了过多相似工具，以及 Trace 中究竟是选错工具、漏参还是执行错误。身份、租户等系统已知字段不应让模型自由填写，应通过 Runtime Context 注入。高风险参数即使 schema 合法，也必须做权限和业务校验。

S15. context_schema 与把 user_id 写入 system 字符串相比，解决了什么问题？

推荐回答： context_schema 为每次调用定义结构化运行时上下文，工具可通过 ToolRuntime 读取 user_id、租户、功能开关等数据；它不会把这些字段混入自然语言 Prompt，也不依赖模型正确复述。这样能保持输入类型清晰、减少敏感信息暴露并便于测试。它属于 per-run 上下文，不替代 checkpointer 的对话状态，也不替代后端鉴权。

S16. 工具抛错后，为什么不能简单吞掉异常并返回“暂无结果”？

推荐回答： 吞错会让模型和观测系统把失败误当成合法空结果，可能产生错误回答或假完成。应将可恢复错误以明确的 ToolMessage 或结构化错误写回，让 Agent 决定有限重试、换策略或向用户说明；瞬时失败可由 ToolRetry Middleware 治理，不可恢复的参数或权限错误应直接停止对应动作。副作用工具重试前还要依赖幂等键或状态查询，避免重复执行。

1.4 Retrieval 与 RAG Pipeline

S17. 请从原始文档到最终回答描述一条完整 RAG pipeline。

推荐回答： 离线阶段由 Loader 读取来源并生成 Document，TextSplitter 按语义和长度切块，保留来源、章节、时间等 metadata；Embedding Model 将文档块向量化后写入 VectorStore。在线阶段将查询送入 Retriever，执行相似度或混合召回，可选重排与压缩，再把少量高质量片段连同问题交给 Prompt 和 ChatModel；最终答案应返回引用并接受忠实度校验。索引与 Embedding Model 要成对版本化，换模型通常需重建索引。

S18. Loader、Splitter、VectorStore、Retriever 的边界分别是什么？

推荐回答： Loader 负责把文件、网页或 API 数据转换为 Document；Splitter 控制块粒度与重叠；VectorStore 保存向量和 metadata，并提供相似度搜索；Retriever 向上暴露统一的“查询到 Document 列表”接口，可包住 VectorStore，也可组合关键词检索、过滤和重排。边界清楚后，召回失败才能区分是没加载、切坏、索引错还是检索策略不合适。

S19. 哪些场景用 LCEL RAG 链，哪些场景把 Retriever 封成 Tool？

推荐回答： 每个问题都固定执行一次“检索后生成”时，用 LCEL RAG 链，路径简单、延迟和成本可控；模型需要判断是否检索、如何改写查询、是否多次检索或与其他工具协同时，把 Retriever 封成 Tool 交给 Agent。Tool 描述要限制滥用，Observation 要限制长度并保留引用。若存在复杂多跳、多检索器状态和可回退验证，则考虑 LangGraph 显式编排。

S20. Hybrid Search、Reranker、Query Expansion、Context Compression 分别针对哪类检索失败？

推荐回答： Hybrid Search 结合关键词与向量，补强编号、专名和语义召回；Reranker 对初检候选精排，降低高召回带来的噪声；Query Expansion 改写或扩展表达，解决原问题与文档措辞不一致；Context Compression 在进窗前抽取相关部分，降低冗余。它们都不是默认越多越好，应先用 Recall@K、MRR、引用正确率和端到端任务成功率定位瓶颈，并保留退回朴素检索的降级路径。

S21. 检索结果过长时，如何避免 Context 被撑爆又不丢关键证据？

推荐回答： 先按相关性阈值、Top-K、metadata 权限与时效过滤，再去重、重排和压缩；为单个 Tool Observation 设置 Token 上限，只保留直接支持问题的片段。摘要必须保留来源指针、否定条件、数字和时间等关键事实，必要时允许按引用二次取原文。不能机械截断列表尾部，也不能让压缩摘要替代原始证据的可追溯性。

1.5 create_agent、轨迹、Streaming 与 Memory

S22. 你要实现天气 Agent：给定模型、天气工具和系统规则，请描述 create_agent 后一次 invoke 的完整消息轨迹。

推荐回答： create_agent 用 model、tools 与 system prompt 构造标准 harness；调用方通过 {"messages": [{"role": "user", ...}]} 输入。模型先生成含天气工具 name、city 参数和 call ID 的 AIMessage；Harness 校验并执行工具，追加同 ID 的 ToolMessage；模型再次读取轨迹并输出无 tool_calls 的最终 AIMessage，于是本轮结束。返回值是包含完整 messages 的状态字典，最终文本读末条；若配置结构化输出，还可从 structured_response 读取校验对象。

S23. response_format、with_structured_output 与最终 AIMessage 有什么关系？

推荐回答： with_structured_output 面向单次 ChatModel 调用；response_format 面向整个 Agent harness 的最终交付，框架可根据模型能力选择 ProviderStrategy 或 ToolStrategy，并把结果放进 structured_response。末条 AIMessage 仍属于消息轨迹，适合展示或继续对话；结构化对象适合业务消费。生产代码不应靠解析末条自然语言来重建已存在的结构结果。

S24. 为什么“最终 AIMessage 不再调用工具”不等于“业务合同已满足”？

推荐回答： 无 tool_calls 只是 harness 的默认环结束信号，模型可能提前放弃、遗漏必填字段、没有引用证据，甚至在工具失败后声称成功。业务 Done 应由 response_format、确定性校验节点、工具后置核验、测试或人工审批判断；不满足时可有限重试、回到修复步骤或明确失败。停止条件要区分“模型停止生成动作”和“系统验收通过”。

S25. 没有 checkpointer 时，即使每次都传同一个 thread_id，Agent 为什么仍记不住上一轮？

推荐回答： thread_id 只是持久化状态的隔离键，本身不保存任何消息；只有编译 Agent 时配置 checkpointer，Runtime 才会在同一线程下保存并恢复 state。没有 checkpointer 时，每次 invoke 只看到本次显式传入的 messages。同一用户应稳定复用线程键，不同用户和新会话必须隔离；生产环境还要使用持久化实现，而非仅依赖进程内存。

S26. 短时记忆、长期记忆与 Runtime Context 有何区别？

推荐回答： 短时记忆通常由 checkpointer 按 thread_id 保存当前会话的 messages 和 state；长期记忆可通过 store 跨线程保存用户偏好或知识，并在需要时检索；Runtime Context 是本次调用注入的身份、租户或配置，不属于可对话历史。三者都必须有隔离、权限和过期策略，且长期信息只有被检索并重新放入本轮 Context，模型才真正可见。

S27. Agent 的 updates、values、messages 三种 stream mode 各适合什么？

推荐回答： updates 输出各节点产生的局部 state 更新，适合进度条和节点级调试；values 输出每步后的完整 state，便于观察状态演化，但数据量更大；messages 输出模型 token 与 metadata，适合聊天 UI 增量展示。多模式可同时订阅，但消费端要按 mode 分流。更细粒度的工具、子图和中断事件可使用 stream_events。

S28. Streaming 改善了什么，又没有改善什么？

推荐回答： Streaming 让模型 token 或节点更新尽早到达客户端，降低用户感知等待并支持进度、日志和取消；它不会减少 Prompt Prefill、模型调用次数、总 Token 费用，也不自动缩短完整任务耗时。结构化结果和工具参数可能被拆成多个 chunk，必须缓冲到完整事件后再校验和执行，不能边收到半截 JSON 边触发副作用。

S29. 什么时候应继续用 create_agent，什么时候应把它作为 LangGraph 的一个节点？

推荐回答： 标准“模型选择工具—执行—再思考”的单 Agent 环，配合 Middleware 已能满足需求时继续用 create_agent。若外围还要固定预处理、多个验证节点、复杂条件分支、跨阶段回退、长任务恢复或多 Agent 协作，则用 LangGraph 显式定义拓扑，并把编译后的 create_agent 当成其中一个 Runnable 节点。不要为了可视化就过早下沉，也不要用 Middleware 隐藏本应显式的业务状态机。

1.6 Middleware、Hooks、Guardrails 与可观测性

S30. 请沿一次 Agent 调用说明 Middleware hooks 可能插在哪里。

推荐回答： before_agent 可在启动时校验输入或加载信息；before_model 可裁剪、摘要历史和去 PII；wrap_model_call 包围模型调用，适合重试、缓存及动态切模型、Prompt 或 Tools；after_model 检查模型结果或在高风险 tool call 前触发审批；wrap_tool_call 负责工具重试、白名单和拦截；after_agent 做通知、落盘和清理。Hook 的具体签名以当前版本文档为准，但生命周期职责应保持清晰。

S31. Middleware 与“在 Agent 外面再写一个 while 循环”有什么本质差别？

推荐回答： Middleware 运行在 create_agent 编译出的图和共享状态中，能在模型、工具及 Agent 生命周期的明确位置介入，并复用 checkpointer、streaming、interrupt 和 tracing；外层 while 通常只能看到整轮输入输出，难以安全拦截单次工具调用，也容易重复状态、重试和停止逻辑。若需求是另一个业务级循环或显式拓扑，应使用 LangGraph，而不是让 Middleware 承担所有编排。

S32. 模型 API 偶发超时、工具偶发 503、删除工具参数越权，应分别在哪一层治理？

推荐回答： 模型瞬时失败用 ModelRetry 类 Middleware，并设置退避、总时限和可重试错误；工具瞬时失败用 ToolRetry 或工具客户端重试，同时保证幂等；删除参数越权不是重试问题，应在 wrap_tool_call、after_model 或业务执行层做 allowlist、鉴权、参数范围检查和 HITL。Prompt 可以降低越权倾向，却不能替代确定性拒绝。

S33. SummarizationMiddleware 如何与“压缩不能丢合同”同时成立？

推荐回答： 摘要对象应主要是冗长历史与 Observation，系统规则、任务合同、剩余预算、审批状态、关键实体 ID 和错误计数等应保存在不可随意摘要的消息或结构化 state 字段中。压缩后要保留来源与必要原文指针，并用回归样本验证否定条件、数字和未完成事项没有丢失。摘要只是 Context 治理手段，不是删除审计状态的许可。

S34. 为什么 Human-in-the-Loop 通常要配 checkpointer？

推荐回答： HITL 会在高风险工具执行前暂停，等待人工批准、编辑或拒绝；等待可能跨请求甚至跨进程。Checkpointer 保存暂停点的 messages、待执行 tool call 和其他 state，使相同 thread_id 能从中断处恢复，而不是重新运行前序步骤。没有持久化，审批回来后容易丢失上下文或重复调用已有副作用的工具。

S35. Guardrails 应只写在 Prompt 中吗？输入、模型输出与工具执行分别可做哪些控制？

推荐回答： 不应。输入侧可做长度、类型、PII 和注入风险检测；模型输出侧可校验 schema、引用、敏感内容和待调用工具；工具执行侧必须做鉴权、allowlist、参数约束、幂等、沙箱与审批。Prompt 是概率性行为引导，Middleware 和业务 Runtime 提供确定性拦截。真正安全的设计是即使模型被诱导，危险 Action 也无法直接落地。

S36. 多枚 Middleware 组合时，为什么顺序值得专门测试？

推荐回答： Middleware 往往像 Web 中间件一样包裹调用：进入阶段按声明顺序执行，返回阶段可能反向展开。若先重试再脱敏，敏感数据可能被多次发送；若先执行工具再审批，HITL 已失去意义；摘要、动态工具裁剪与缓存的顺序也会改变缓存键和模型可见内容。因此要基于实际版本确认执行序，写集成测试并在 Trace 中验证，不应只凭列表视觉顺序推断。

S37. L0、L1、L2 三个实践层级分别应证明什么？何时需要 Deep Agents？

推荐回答： L0 用 create_agent、少量 Tool 和可机检输出证明最小闭环；L1 加 checkpointer、Streaming 与 RAG Tool，证明多轮、检索和中间态可用；L2 加摘要、重试、调用限制、Guardrails、可选 HITL 与 LangSmith，证明 harness 可治理。只有明确需要虚拟文件系统、Skills、subagent 和开箱即用的厚能力，并接受更大抽象成本时再考虑 Deep Agents。

S38. 线上出现“Agent 反复调用同一工具”，你会如何借助 Trace 定位并止损？

推荐回答： 先在 LangSmith 或等价 Trace 中检查每轮 AIMessage 的 tool call、参数、ToolMessage 结果、错误类型、Prompt/Model 版本和 Middleware 决策，确认是工具持续失败、Observation 不清晰、模型忽略结果还是状态未正确写回。止损要用最大模型调用数、工具调用数、总时限和重复参数指纹等硬限制；随后修复工具描述、错误合同或状态更新。仅在 Prompt 中写“不要重复”不足以阻止调用风暴。

S39. LangSmith 在这一阶段最低限度应观测什么？

推荐回答： 至少能打开一条成功和一条失败的完整 Trace，看清 Prompt 与消息、模型调用、tool call 参数、ToolMessage、Middleware 介入、延迟、Token 和最终状态。这样才能区分模型选错、工具失败、Context 压缩丢信息和门禁拒绝。评测数据集与线上监控可逐步建设，但若连一条轨迹都无法还原，就不应声称 Agent 可调试。

S40. 如果业务要求最大 8 次模型调用、3 次同工具调用、30 秒截止和高风险工具审批，应该如何落地？

推荐回答： 用调用限制类 Middleware 或自定义 state 计数实现模型与工具硬顶；对“同工具”按工具名和规范化参数指纹计数，防止换序绕过；在 Agent 外层设置端到端 deadline，并把剩余预算传入 state；高风险工具在执行前由 HITL/Guardrail 中断，配合 checkpointer 恢复。所有退出都要返回明确原因并进入 Trace。Prompt 可告知预算帮助模型规划，但不能充当唯一计数器。

2. 面试真题

以下题目按主题归纳、改写自公开面经与题库，用于训练表达，并非逐题对应某一场真实面试；综合参考来源见文末「参考面经与题库」。

I1. 为什么选择 LangGraph，而不是直接使用 LangChain Agent？

推荐回答： 我先看控制流是否需要显式化。标准工具调用闭环用 LangChain create_agent 已足够，它提供 Messages、Tools、Memory、Streaming 和 Middleware；若业务包含文档解析、规则检索、证据校验、风险复核、人工审批等固定节点，并有分支、循环、跨故障恢复，就用 LangGraph 的 State、Node、Edge 和 Checkpoint 固化允许的路径。两者不是替代关系，create_agent 可以作为 LangGraph 的一个节点。

I2. LangChain 和 LangGraph 分别提供什么能力？优势在哪里？

推荐回答： LangChain 的优势是标准化组件与快速组装：统一 ChatModel、Messages、Prompt、Tool、Retriever、LCEL 和 create_agent，适合从固定链到单 Agent harness；LangGraph 的优势是显式有状态编排和 durable runtime，能定义分支、循环、中断、恢复、子图与多 Agent。前者降低能力接入成本，后者提高复杂流程的可控、可审计与可恢复性。选型应由控制流复杂度决定，而不是由项目规模或流行度决定。

I3. LangChain 里的 “Chain” 应该怎样理解？它和 Agent 有什么区别？

推荐回答： Chain 是输入输出合同明确、执行路径基本确定的 Runnable 组合，LCEL 用 | 和 Parallel 表达顺序、扇出与汇合；Agent 则让模型根据当前 Messages 动态选择 Tool，并在 Observation 写回后继续决策。固定 RAG 问答优先 Chain，自主工具选择用 Agent，复杂业务状态机用 LangGraph。关键不是有没有多步，而是下一步由程序拓扑决定还是由模型动态决定。

I4. 请设计一个企业知识库 RAG，并说明 LangChain 在每层承担什么。

推荐回答： 离线用 Loader、Splitter、Embeddings 和 VectorStore 建索引，metadata 记录租户、版本、地区、章节和生效时间；在线由 Retriever 做向量与关键词多路召回，按权限过滤，可用 RRF 融合、Cross-Encoder 重排与压缩；固定问答用 LCEL 把 context/question 送入 Prompt 和 Model，需要自主检索则封成 Tool；最终用结构化输出返回答案、引用与置信信息。评测拆成 Recall@K/MRR、引用忠实度和端到端成功率。

I5. 讲讲大模型 ReAct，以及它如何映射到 LangChain 的消息轨迹。

推荐回答： ReAct 把推理与动作交替进行；工程上不需要保存或暴露完整隐藏思维，关键轨迹是 HumanMessage 提供 Goal，AIMessage 的 tool_calls 表示 Action，ToolMessage 表示 Observation，下一条 AIMessage 基于观察继续动作或给出 Final Answer。create_agent 负责驱动这条环，Middleware 负责预算、重试和审批。没有真实 ToolMessage 时，模型的执行声明不能算 Observation。

I6. 工具调用失败怎么办？如何避免重试造成重复副作用？

推荐回答： 先分类：超时、429 和部分 5xx 可有限退避重试；参数、权限和业务规则错误应修正或停止；错误要以结构化 ToolMessage 写回，不能吞掉。模型与工具重试分别由对应 Middleware 或客户端治理，并设置总时限。写操作必须使用幂等键、执行状态查询、审批和必要的补偿机制，重试前先确认是否已成功；Trace 记录每次 call ID、参数、结果和尝试次数。

I7. 如何防止 Agent 死循环或工具调用风暴？

推荐回答： 不能只在 Prompt 中要求“不要重复”。Runtime 要同时设置最大节点或模型步数、总工具调用数、单工具次数、累计 Token/费用和绝对截止时间；对连续相同工具与规范化参数生成指纹，达到阈值后熔断；不可恢复错误直接停止，信息不足时追问。LangSmith Trace 用于定位循环根因，LangGraph 还可通过 state 计数和条件边把超限路径显式导向人工或失败节点。

I8. RAG 与持久化记忆有什么区别？两者如何协同？

推荐回答： RAG 面向当前问题从外部知识库检索事实，强调来源、时效、权限和召回质量；持久化记忆保存会话状态、用户偏好或历史任务信息，短时通常按 thread_id 进入 checkpointer，长期可进入 store。二者都不是“模型自动记住”：只有相关内容被检索并重新注入本轮 Context 才生效。知识事实不应混成未经验证的用户偏好，敏感记忆还要有隔离、过期和删除策略。

I9. 前端要展示流式输出和工具进度，你如何设计后端事件？

推荐回答： 后端分别订阅 messages token 流和 updates 节点更新，转换为带 request ID、事件类型与单调序号的 SSE；文本事件可增量渲染，工具开始、成功、失败和审批中断用独立事件展示。结构化结果与工具参数必须缓冲完整后再校验，副作用执行与 UI 文本流解耦。断线重连按事件 ID 去重；若上游不支持断点续推，应明确重启语义，不能假装无损恢复。

I10. 一个合规审校 Agent 为什么更适合状态图，而不是纯 ReAct？

推荐回答： 合规审校包含必须经过的解析、规则检索、证据验证、风险复核和人工审批，遗漏任一步都不可接受；纯 ReAct 把下一步更多交给模型，轨迹会随采样和 Context 波动。状态图把关键节点、转移条件、失败回退和审批点显式固化，模型只在受控节点内做分类、抽取或候选决策；Checkpoint 还能支持跨故障恢复。这种“模型参与计算、程序控制流程”的分工更适合强审计场景。

I11. 如果让你从 L0 到生产逐步建设一个 LangChain Agent，你会怎样分阶段？

推荐回答： L0 先用少量 Tool、清晰 system prompt 和结构化输出跑通成功与失败轨迹；L1 加持久化 checkpointer、thread 隔离、RAG Tool 和 Streaming，建立基本体验；L2 加 Model/Tool Retry、调用预算、摘要、PII/Guardrails、高风险 HITL 与 LangSmith 评测。每阶段都以任务成功率、工具一次成功率、Schema 合规、越权率、P95 延迟和成本验收。出现复杂固定拓扑时再引入 LangGraph，而不是一开始就堆全部抽象。
