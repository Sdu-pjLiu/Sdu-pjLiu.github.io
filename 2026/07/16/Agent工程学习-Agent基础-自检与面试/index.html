AI-Agent工程学习-Agent基础(自检与面试)

发表于 2026-07-16 更新于 2026-07-20 分类于 计算机
Agent 基础模块学习自检与面试导向问答；含完整推荐回答。

本文是 Agent 基础（一）～（六）的阶段验收。目标不是背名词，而是能从目标闭环、推理规划、记忆工具、Runtime、评测、安全和能力扩展等层面，说明一个 Agent 为什么能工作、为什么会失败，以及如何把失败变成可观察、可归因、可修复的问题。

0. 使用说明

建议先遮住“推荐回答”，在 90～120 秒内口述。合格答案通常包含四部分：概念边界、选型条件、主要风险、工程措施。遇到场景题时，还应说出可观察字段和验收标准，不能只回答“优化 Prompt”或“换更强模型”。另请自检：能否区分 Agent Harness 与 LangGraph Orchestration Runtime。

本文共 50 道自检题、14 道面试题。自检题覆盖六篇正文，并吸收（四）（五）（六）的全部阶段收口问题；面试题结合公开真实面经，侧重架构、路由、评测归因、假完成、MCP 与审批分级。

1. 学习自检

1.1 闭环与选型（一）

S1. Agent 与 Chat、Workflow 的根本区别是什么？

推荐回答： Chat 主要完成当前一轮生成，下一步通常由用户触发；Workflow 的控制流由人预先写成固定步骤或 DAG；Agent 则围绕 Goal 在循环中读取 State、选择 Action、观察结果并决定继续、改道或停止。路径固定、可枚举时优先 Workflow，只有任务需要边观察边决策时才值得使用 Agent。调用一次搜索工具只是 Tool-augmented Chat，不自动等于 Agent。

S2. Agent 五件套分别负责什么？缺少 Runtime 会怎样？

推荐回答： LLM 负责理解状态与提出决策，Memory 决定哪些历史和知识进入当前 Context，Tools 查询或改变外部世界，Planning 拆解目标并组织步骤，Runtime 驱动循环、执行工具、维护状态并落实校验、预算、权限和停止。缺少 Runtime 时，模型的 Action 只是自然语言提案，系统无法确认工具是否真执行，也难以阻止无限循环、越权调用和无证据的假完成。

S3. Environment、Action Space、Action 与 Observation 如何对应？

推荐回答： Environment 是 Agent 所处的外部世界，如搜索、数据库、文件系统或 HTTP 服务；Action Space 是当前被允许的动作集合，通常由工具白名单和 Schema 描述；Action 是模型从集合中提出的一次调用或最终回答；Observation 是 Runtime 真正执行后的结果、错误或超时。Observation 必须关联调用 ID 写回 State 与 messages，否则下一轮模型看不到现实反馈，只能继续猜测。

S4. 请完整描述 Agent Loop，并说明每一环由谁负责。

推荐回答： Runtime 在预算内循环：模型根据 Goal 和 State 进行 Reason，选择工具、追问或 Final；Runtime 校验工具名、参数与权限后 Execute；工具返回 Observation；Runtime 更新 messages、Trace、Working state 和预算，再进入下一轮。模型主要负责 Reason 与 Select，应用负责 Execute、Observe、Update 和硬停止。Reflection 可显式成为一步，也可隐含在下一轮判断中，但不能替代真实校验。

S5. Thought、Action、Observation、Reflection 各自应产出什么？

推荐回答： Thought 表示基于当前状态形成的判断或假设；Action 是可执行的工具 Invocation、向用户追问或 Final Answer；Observation 是工具的真实 Result、Error、超时等环境反馈；Reflection 对照目标和验收标准判断缺口、纠错或停止。工程上不要求向用户暴露完整隐藏推理，应优先保存结构化计划、调用参数、证据指针和评估结论，让轨迹可审计而不过度泄露内部思维。

S6. Agent 的 State 至少应包含哪些字段？

推荐回答： 最小 State 应有 Goal 与成功标准、当前 Working state、已执行 Trace、剩余 Budget 和停止信号。Working state 可拆成当前子目标、open[]、done[]、关键实体与待确认问题；Trace 记录工具名、参数、结果摘要、错误和副作用状态；Budget 包含步数、Token、费用与墙钟。显式结构化 State 比只依赖长对话更容易恢复、压缩、并行合并和编写确定性校验。

S7. Agent 应有哪些停止条件？模型级停止与系统级停止有何不同？

推荐回答： 系统级停止至少包括：满足 Rubric 的成功、不可恢复错误或目标冲突导致的失败、步数或 Token 等预算耗尽，以及高风险动作前转人工。EOS、stop 和 max_tokens 只结束某一次模型生成；max_steps、总超时和费用上限结束整个 Agent 运行。可靠系统不能只等模型说“完成”，而应由 Runtime 根据结果、证据和状态机决定是否落到终态。

S8. 空转、工具死循环和假完成分别如何识别与阻断？

推荐回答： 空转表现为连续生成分析却没有有效 Action；工具死循环表现为相同工具与相同参数重复调用且 Observation 无新增；假完成则是没有成功 Result 或证据指针却把任务标成 Success。Runtime 可通过最大步数、相同调用指纹、连续错误计数、进展字段和 Final Gate 阻断：无进展则换策略或降级，无 Observation 不准成功，高风险副作用还需执行后状态核验。

1.2 推理与规划（二）

S9. ReAct 是什么？与原生 Tool Calling 是什么关系？

推荐回答： ReAct 让 Reason 与 Act 交替，工具执行结果作为 Observation 进入下一轮推理，适合路径不能预先写死的中短任务。经典论文常用 Thought/Action/Observation 文本格式，现代工程更适合原生 Tool Calling：模型输出结构化 Invocation，Runtime 执行并用 tool 消息回写。二者循环语义一致，后者协议更硬、更容易校验，也不需要把完整思维链暴露出来。

S10. ReAct 与 Plan-and-Execute 如何选型？

推荐回答： 工具较少、任务较短、下一步高度依赖刚获得的反馈时，ReAct 边走边想更灵活；任务较长、步骤和依赖可预见、需要进度展示或并行时，先由 Planner 产出步骤或 DAG，再由 Executor 执行更可控。规划式的风险是错误计划被一路执行，因此必须设置中间校验和 Replan 触发；常见组合是高层计划、底层叶子节点使用 ReAct。

S11. Goal Decomposition 与 Task Decomposition 有什么区别？

推荐回答： Goal Decomposition 先回答“什么结果才算成功”，把模糊目标拆成可验收维度，如覆盖范围、证据、时效与安全；Task Decomposition 再回答“要做哪些动作”，形成搜索、分析、核验、成稿等步骤。若只拆任务不拆成功标准，执行完所有步骤仍可能产出无证据报告；若只有标准没有动作，又无法落地。正确顺序通常是先定 Goal Rubric，再拆 Task 与依赖。

S12. DAG Planning 有什么价值？哪些节点可以并行？

推荐回答： DAG 用节点表示子任务、用边表示数据或顺序依赖，使无依赖节点可并行、失败影响范围可定位、局部重规划可操作。只有输入互不依赖、没有冲突副作用、资源允许的节点才能并行，例如搜索多个独立来源；综合成文必须等待证据节点完成。并行结果需带稳定 ID、独立状态和错误，合并时处理重复、冲突和部分失败，不能把“同时发起”误当成天然安全。

S13. Dynamic Planning 应在何时触发？如何避免反复重规划？

推荐回答： 当 Observation 与预期不符、工具不可用、发现新约束、关键证据冲突或预算明显不足时，应触发 Replan。优先做局部替换、删除或重排受影响节点，只有核心假设失效才推翻全局计划。Runtime 应限制重规划次数，记录触发原因与计划版本，并要求新计划说明相对旧计划的变化和剩余验收缺口，避免每一步都重画地图、成本上升却没有实际进展。

S14. Hierarchical Planning 为什么适合长任务？

推荐回答： 分层规划把长期稳定的阶段目标放在高层，把阶段内依赖组织成中层 DAG，再让底层用 ReAct 处理具体工具参数。这样高层保持方向和验收不漂移，底层又能根据局部 Observation 灵活纠错。Research 场景可用“调研—分析—成稿”作高层，多源搜索作并行节点。层间必须传递 Goal、完成项、未完成项和硬规则，否则分层只是增加调用次数。

S15. Reflection 与 Self-Refine 有何区别？何时应该停止？

推荐回答： Reflection 偏向评价当前 Action、计划或答案是否满足标准，并决定继续、纠正还是停止；Self-Refine 是“生成—反馈—改写”的产物迭代循环。二者都会增加模型调用、延迟与成本，且自评未必可靠。应由固定 Rubric、最大轮次或分数提升阈值控制，事实性问题还要用工具与规则核验。若连续两轮没有可测提升，就应停止、降级或转人工，而非无限“再想想”。

S16. Debate、Tree Search 与外部工具探索应如何取舍？

推荐回答： Debate 通过不同角色提出对立观点并由裁判汇总，适合高不确定判断；Tree Search 保留多个候选状态并执行扩展、评估、剪枝和回溯，适合大搜索空间。两者调用成本都高，且模型自评可能同源偏差。若搜索、编译、测试、仿真等工具能给出真实反馈，应优先在工具空间探索；简单任务使用单链 ReAct 或 Workflow，不能把高级模式当成默认装饰。

1.3 记忆工具与 Runtime（三）

S17. 记忆四层分别解决什么问题？

推荐回答： 会话内 Context 保存近期消息、当前约束和最新 Observation；任务 Trace 记录本次执行轨迹，Checkpoint 则保存可恢复运行态；外存知识保存跨会话事实和文档，通常经检索重新注入；Procedural 保存“怎么做”的流程、模板和技能。Long-term 是跨会话持久化策略，可覆盖外存知识、轨迹摘要和偏好字段，并非神秘第五层。任何记忆只有进入本轮 Context，模型才真正可见。

S18. Checkpoint 与 Trace 有何区别？为什么长任务需要 Checkpoint？

推荐回答： Trace 面向复盘与观测，记录发生过什么；Checkpoint 面向恢复，保存计划版本、当前节点、open/done、预算、已完成副作用和必要输入等可继续执行的状态。长任务可能因超时、进程故障或人工审批暂停，没有 Checkpoint 就只能从头重跑，并可能重复写库或发送消息。恢复时还要校验外部副作用的真实状态，不能把一段自然语言“任务故事”直接当可执行快照。

S19. RAG 作为 Retrieval Tool 与 Runtime 预注入如何选？

推荐回答： 当“是否检索、检索什么、是否再次检索”需要模型根据中间结果判断时，把 RAG 暴露为 Tool；当业务每次都必须查固定知识、追求稳定延迟与可预测路径时，由 Runtime 在推理前预检索并注入。两者可以组合，例如先预注入权限政策，再允许按需搜索案例。无论哪种挂法，都要做权限过滤、相关性阈值、长度预算和来源保留，RAG 也不能保证答案一定忠实。

S20. Skill 与 Tool、Prompt Template、RAG 文档各解决什么？

推荐回答： Tool 是模型可提议、Runtime 真执行的动作；Skill 是可发现、可版本、按需注入的程序性知识包，教 Agent 如何完成一类任务；Prompt Template 是某个推理节点的输入合同；RAG 文档提供事实材料。加载 Skill 只是把其 body 放进 Context，不会新增消息角色，也不自动授予工具权限。Skill 可指导组合多个 Tool，但 allowed-tools 仍须受 Runtime 白名单和审批策略约束。

S21. Tool Schema 怎样写，才能降低误选与参数幻觉？

推荐回答： 工具名应稳定、语义明确，description 同时说明何时使用和何时不要使用；参数 Schema 要定义类型、必填、枚举、范围和格式，并减少模型不应决定的身份或权限字段。相似工具应合并、分组或通过路由裁剪，避免描述重叠。Runtime 在执行前仍需做 Schema、业务和权限三层校验，失败时返回结构化 Error，让 Agent 修正或换策略，而不是把非法请求打到真实系统。

S22. RAG 与 Memory 的关系是什么？Semantic Memory 一定存在模型参数里吗？

推荐回答： RAG 是从外部知识中检索并注入 Context 的机制，Semantic Memory 在 Agent 工程中通常就是带来源、时间和权限的外存事实，而不是模型“记在脑子里”。Memory 负责存什么、何时读写和冲突规则，RAG 可作为它的读取路径之一。模型参数知识不可精确更新和审计，不能承担用户订单、最新政策等动态事实；持久化内容也必须重新检索进本轮 Context 才可使用。

S23. Runtime 至少应提供哪些治理能力？

推荐回答： 最小 Runtime 应驱动循环，维护 State 与 Checkpoint，执行工具并处理超时、重试和错误分类；还要控制步数、Token、费用和墙钟预算，落实工具白名单、参数与业务校验、高风险 HITL、最终答案格式校验，以及 Trace、指标和审计。模型只负责提出候选决策。把鉴权、幂等或停止交给 Prompt，会因模型概率性、Context 漂移和注入而失效。

S24. 为什么硬规则不能随轨迹一起摘要？

推荐回答： 摘要是有损压缩，可能漏掉否定词、权限范围、金额上限或禁止事项；一旦这些硬约束从 Context 中消失，后续模型就可能行为漂移。Goal、验收标准、安全边界、工具白名单要点和未完成副作用记录应作为不可摘要字段，以全文、结构化字段或稳定引用保留。压缩主要作用于冷 Trace、重复轮次和冗长 Observation，并在压缩后运行约束完整性检查。

S25. 多个 Tool Calls 并行执行时，State 需要满足什么要求？

推荐回答： 每个调用必须有唯一 call ID、独立参数、超时、重试和状态，且 State 更新不能依赖不可控的完成顺序。并行前要确认无数据依赖和冲突副作用；结果用类似 allSettled 的语义分别记录成功与失败，再按稳定规则合并 Observation。若共享实体可被修改，应串行、加锁或使用事务。部分失败不能把整批标成成功，也不能盲目重放已经产生副作用的调用。

1.3b Harness（三 §6、六 §7）

S25b. Runtime 与 Harness 是什么关系？与五件套公式是否矛盾？

推荐回答： Runtime 是理论分解名，Harness 是实现层产品名，指同一层——环绕 Model 工具环、把概率性提案变成可验证运行的工程化执行架。官方公式 Agent = Model + Harness 与五件套 Agent = LLM + Memory + Tools + Planning + Runtime 不矛盾：Memory / Tools / Planning 在 Harness 内部被调度，不是与 Harness 并列的第二套公式。五件套帮助理解职责边界；Harness 帮助理解实现层如何打包这些职责。

S25c. Harness 内部分几层？Memory / Tools / Planning 如何映射进去？

推荐回答： 概念上可分 Prompt 层（system、skill、memory 注入）、Tool 层（registry、MCP、Execute）、State 层（messages、todos、files、checkpoint）、治理层（Budget、HITL、Guardrails、Permissions）、扩展层（Hooks / Middleware）、观测层（Trace、Metrics、Audit）。Memory 对应上下文组装与外存策略；Tools 对应注册、Schema 校验与 Result 写回；Planning 对应 plan/todo 状态与子任务委托接口；Runtime 五件套项则对应 Harness 本体——循环、Budget、HITL、Guardrails、Trace。

S25d. 薄 Harness、厚 Harness、自定义拓扑各适合什么场景？

推荐回答： 薄 Harness（如 LangChain create_agent）适合标准单 Agent 环，Middleware 按需叠加。厚 Harness（如 Deep Agents create_deep_agent）预装 FS、Skills、Subagent、压缩等，适合长任务 coding / research。自定义拓扑（LangGraph 手画 Node/Edge）适合复杂企业流程、确定性步骤与 Agent 步骤混合。手写 while 适合学习与极简原型。选型看任务长度、是否需要预装 context 治理、以及控制流是否需显式图级表达。

S25e. Agent Harness 与 LangGraph Orchestration Runtime 有何区别？

推荐回答： Agent Harness 是跑 Agent 工具环的那一层——维护 prompt、tools、state、治理与扩展。LangGraph Orchestration Runtime 是更底层的图调度引擎，负责 checkpoint 通道、interrupt、superstep、durable execution 等。关系：create_agent / create_deep_agent 编译产物是图，Harness 逻辑跑在 Orchestration Runtime 之上。LangGraph 不是 Harness 本身，而是 Harness 常借用的编排底座；需要精细拓扑或多 Agent 图时直接下沉 LangGraph。

1.4 评测与 Research（四）

S26. Agent 评测为什么要分为节点、轨迹、任务和安全四层？

推荐回答： 节点评单次 Prompt、工具选择和参数合法；轨迹评循环是否健康，如重复调用、恢复和假完成；任务评最终是否达到用户验收；安全评越权、泄露和危险动作是否被拦。分层后才能定位“参数对但结果没用”“答案对但过程越权”等问题。只看最终文本会掩盖偶然成功和高风险路径，只看局部节点又可能出现局部全绿、端到端失败。

S27. Task Success Rate 应如何定义才可计算？

推荐回答： 先为每类 Scenario 写明确成功 Rubric，如输出结构合法、关键事实有 Observation 指针、要求的副作用状态已核验、在预算内结束。Task Success Rate 等于满足全部硬验收的任务数除以总任务数；开放质量可另设分项分数，但关键安全条件不应被平均分抵消。评测需固定模型、Prompt、Tool Schema、工具桩和数据版本，确保不同版本可重放比较。

S28. Hallucination Rate 如何从轨迹中计算？与假完成有何关系？

推荐回答： 可把关键事实声明拆成原子断言，检查是否存在有效 Observation、可信来源或用户确认支撑；无依据断言数除以总断言数，可作为 Hallucination Rate。假完成是更具体的轨迹故障：Agent 声称任务或副作用已完成，却没有对应成功 Observation 或状态核验。两者可能重合，但幻觉还包括错误引用和曲解证据。评测必须保存声明到证据 ID 的映射，不能靠主观阅读。

S29. Tool Accuracy 为什么不能只看“工具有没有调成功”？

推荐回答： Tool Accuracy 至少拆成三段：是否选对工具、参数是否结构与业务合法、返回结果是否被最终决策正确使用。HTTP 200 只能说明调用完成，不代表工具选对；参数合法也可能查错实体；拿到正确结果却在答案中忽略或反着解释，同样是失败。分段指标能分别归因 description、Planner、Schema、执行服务和总结 Prompt，避免所有问题都被归为“工具调用不准”。

S30. 如何区分 Prompt、模型、工具、记忆和 Runtime 导致的失败？

推荐回答： 沿 Trace 做因果定位：计划或工具选择一开始就错，检查 Prompt、路由和模型；Invocation 合法但服务返回错误，检查工具与网络；检索到错误或过期事实，检查 Memory 写入、检索和冲突规则；有成功 Observation 却没被使用，检查上下文组装和总结节点；模型提出越权动作却真被执行，则是 Runtime 门禁失败。一次只改一个变量，用固定 Scenario 做消融验证。

S31. Research Agent 的默认组合是什么？为什么这样组合？

推荐回答： 常用组合是高层 Hierarchical 或 DAG Planner、叶子节点 ReAct + 搜索工具、成稿阶段轻量 Reflection。高层计划保证调研范围、依赖和验收稳定，多源搜索可并行；叶子 ReAct 能根据空结果、冲突和新线索改 query；成稿使用结构化 Working state、证据指针和模板，Reflection 只检查覆盖、引用与不确定性。全程由 Runtime 控制预算、Checkpoint、错误恢复和 Final Gate。

S32. Research Agent 如何把 Planner、Tools、Memory 与 Rubric 串起来？

推荐回答： 先把问题转成 Goal 与 Rubric，再由 Planner 产出子问题和依赖；Executor 调搜索或读取工具，把结果、来源和错误写入 Trace，并把去重后的证据摘要放入 Working state；遇到空结果或冲突时改 query 或 Replan；Writer 只基于已收集证据成稿；最后按覆盖度、引用忠实、事实与推测区分、预算和安全执行 Rubric，未通过则局部补证或明确失败。

S33. 一个 Research Agent 从 L0 到 L2 应如何递进验收？

推荐回答： L0 用两三个 mock 工具走通 Invocation、执行、Observation 回写与停止，证明闭环正确；L1 接真实搜索，并让 Planner 生成三到五步静态计划，证明任务能分解和按序执行；L2 加入空结果、冲突和超时，使 Agent 能改 query、换来源或局部 Replan。每级都要求关键事实可追溯、在预算内结束、工具失败可见且不假装成功，不能只展示一次理想 Demo。

1.5 工程坑（五）

S34. 为什么能力目录可以很大，但本次 Action Space 必须小？

推荐回答： 把全部 Tools 和 Skills 正文塞入 Context，会消耗 Token、稀释 Goal 与硬规则，并因描述相似增加误选、漏参和假调用。合理做法是 L0 常驻少量核心规则与工具，L1 只暴露能力名称和“何时用”的目录摘要，L2 在路由命中后才加载完整 Skill body 或细 Schema。目录规模与当前可见集合解耦，既保留扩展性，也提高选择准确率和安全可控性。

S35. 裁剪 Action Space 与 Progressive Disclosure 有何区别？

推荐回答： 裁剪 Action Space 是根据任务类型、租户、权限或当前阶段，直接限定本轮允许选择的工具子集，强调“哪些动作可见且可用”；Progressive Disclosure 是先展示目录级摘要，选中后再注入详细说明或 Skill body，强调“信息分阶段展开”。二者常组合：先用路由得到候选白名单，再按需加载细节。前者涉及权限与选择空间，后者主要优化 Context 与认知负担。

S36. 加入一批 Skills 后，应优先观察哪些指标？

推荐回答： 首先看 Tool 或 Skill 选型准确率是否下降，以及 Unnecessary Tool Calls 是否上升；同时观察输入 Token、平均步数、成功一单成本、延迟和注入安全回归。若退化，先检查 description 是否清楚说明适用与禁用场景、候选是否重叠、路由是否裁剪正确，而不是继续把所有 body 塞进 System。新增能力的收益必须在固定 Scenario 上超过它带来的选择噪声和成本。

S37. Context 压缩应在什么时机触发？

推荐回答： 常见触发包括输入达到窗口水位、每 K 步或阶段结束、单次 Tool Result 过大、从搜索切换到分析或成稿、以及剩余 Token 或步数告急。单次结果过大时应先裁剪该 Result，再考虑压缩历史，避免它一写回就挤掉关键约束。阈值需结合模型窗口和任务评测调整，压缩事件、输入输出 Token 与被丢弃内容指针都应写入 Trace 以便审计。

S38. Context 中哪些字段不可摘要，哪些内容可压缩？

推荐回答： Goal、成功标准、安全与权限硬规则、工具白名单要点、当前 open[]、关键实体 ID、未完成副作用和恢复所需 Checkpoint 字段不可随意摘要。冗长 Thought、重复历史轮次、已完成节点的详细 Observation、早期网页全文和低相关检索片段可以裁剪或摘要。关键事实即使压缩也应保留来源和原文指针，让后续需要时能重新检索核对。

S39. 压缩后为什么必须同步 Working state？

推荐回答： messages 被压缩后，若 Working state 仍指向已删除的上下文，Agent 会忘记未完成项、重复已完成动作，或错误恢复副作用。压缩应产生阶段摘要，并同步更新 Goal、open[]、done[]、关键实体、证据索引和 Budget，再记录一条压缩事件。随后执行一致性检查，确认不可摘要字段仍在、计划状态与 Trace 对齐。压缩不是纯文本操作，而是一次状态迁移。

S40. 写污染与脏读分别发生在哪一环？如何防护？

推荐回答： 写污染发生在存储阶段，例如把模型猜测当用户偏好或事实持久化；脏读发生在读取阶段，例如过期事实、旧偏好或错误版本被检索并覆盖新信息。写入侧要求 Observation 或用户确认、字段级权限、来源与时间戳、冲突检测；读取侧要求权限过滤、时效和来源优先级、相关性阈值及冲突显式呈现。高风险记忆还应支持撤销、审计和污染 fixture 回归。

S41. Checkpoint 误用通常是什么？如何避免？

推荐回答： 常见误用是把自然语言 Trace 摘要当成可恢复运行态，恢复后不知道具体节点、工具调用 ID、预算和副作用状态，导致重复执行或跳步。Checkpoint 应使用版本化结构保存计划、当前节点、输入输出引用、open/done、幂等键与外部状态，恢复时先验证 Schema 和依赖版本，再查询已有副作用。Trace 可帮助人理解发生了什么，但不能替代确定性恢复协议。

S42. 排障时“选错工具、忘约束、记错事实”分别先查什么？

推荐回答： 选错工具先查候选 Action Space、Tool/Skill description、路由和相似工具重叠；忘约束先查 Context 组装、Lost in the Middle、压缩记录以及不可摘要字段是否保留；记错事实先查 Memory 写入依据、检索结果、时间戳、来源优先级和冲突规则。若表现为空转或假完成，则进一步查 Runtime 的进展检测、Observation 指针和 Final Gate。先定位层级，再修改对应组件。

1.6 能力组件与安全（六）

S43. Skill 的最小结构和生命周期是什么？

推荐回答： 最小结构包括稳定的 name、说明何时用与何时不用的 description、包含步骤和检查清单的 body，以及可选 allowed-tools。生命周期是目录发现或检索、模型或 Runtime 选择、把 body 注入当前 Context、执行中引用并配合工具、任务结束后卸载或摘要。Skill 应版本化、评审并做选型与安全回归；它是 Procedural 的产品形态，不是新的执行权限。

S44. MCP 的 Tools、Resources、Prompts 如何映射到 Agent 工程？

推荐回答： MCP Tools 暴露可调用动作，对应 Tool Schema；Resources 暴露可读取的 URI、文件或数据内容，不一定通过函数调用；Prompts 提供可复用提示模板。MCP 解决外部能力的标准化描述、发现与接入，但不替代 Agent Loop：模型仍提出 Invocation，Runtime 仍要校验、执行并把 Result 写回。鉴权、租户隔离、超时、审批和审计也必须由 Client、Server 与 Runtime 共同落实。

S45. MCP 与 Function Calling 的区别是什么？

推荐回答： Function Calling 是模型输出结构化工具调用意图的交互机制，关注一次推理如何选择工具和生成参数；MCP 是 Client 与外部 Server 之间发现、描述和访问 Tools、Resources、Prompts 的标准协议，关注能力如何跨应用接入和复用。MCP Tool 最终仍可被转换为模型可见 Schema，并走 Function Calling 闭环。接入 MCP 不代表工具可信，更不意味着可以省略参数校验、权限与审批。

S46. 自动、确认、禁止三档审批应如何划分？

推荐回答： 只读、幂等、低风险且数据权限明确的动作可自动执行，如查询公开文档；写文件、发消息、改库、外联请求等有副作用或可造成损失的动作应先确认，并展示目标、参数和影响；读取密钥、任意 Shell、未授权网络或超出业务能力范围的动作应禁止。分档依据是副作用、可逆性、敏感度和授权，而非模型信心；策略必须由 Runtime 硬执行。

S47. 为什么 Prompt 写“禁止越权”不能替代沙箱与权限控制？

推荐回答： Prompt 只是概率性约束，可能被长 Context 稀释、被注入干扰或因模型版本变化而失效；沙箱和权限控制在模型之外确定性限制文件、网络、进程、工具和数据范围。正确分工是 Prompt 帮模型理解边界，Runtime 用白名单、鉴权、参数校验、审批和沙箱决定 Action 能否真正执行。即使模型完全被诱导，最小权限仍能限制事故半径并留下审计证据。

S48. 何时使用 Subagent，而不是继续加载一个 Skill？

推荐回答： Skill 适合教当前 Agent 一套流程，仍共享主 Agent 的 Context 和工具边界；Subagent 适合可独立验收、需要不同工具或大量局部材料、可并行处理且希望隔离 Trace 的子任务。若只是补充几条固定步骤，加载 Skill 更轻；若安全扫描、独立调研等会产生大量中间信息，可委派 Subagent，只回传结论与证据。默认先把单 Agent + Skill + 分层规划做稳，避免过早多 Agent 化。

S49. Subagent 为什么需要 Context Isolation？Handoff 必须携带什么？

推荐回答： 独立 Context 可防止子任务的网页、日志和长 Trace 挤占主窗口，也减少角色规则和不可信内容互相污染。主 Agent 只向子 Agent 传最小 Goal、输入材料、允许工具、预算和硬规则；返回时至少携带 Goal 摘要、已完成与未完成项、结构化结果、证据或错误，以及硬规则引用。若把完整子轨迹无差别灌回，隔离收益会消失，压缩和安全风险反而放大。

S50. 网页、Tool Result 与 Code Interpreter 输出为什么不能当作 system 指令？

推荐回答： 它们来自外部环境，可能过期、错误或包含 Prompt Injection，本质上都是不可信 Observation，而不是应用制定的高优先级规则。应以 tool role 或带 source、time、error、untrusted 标记的数据块进入 Context，必要时清洗、裁剪和摘要；材料中的命令只作为文本，不直接执行。后续任何 Action 仍要经过工具白名单、参数校验、权限档和沙箱，不能因来源“看起来像系统”就升格。

2. 面试真题

以下题目按主题归纳、改写自公开面经与题库，用于训练表达，并非逐题对应某一场真实面试；综合参考来源见文末「参考面经与题库」。

I1. 请设计一个生产级 Agent 的分层架构，并说明各层边界。

推荐回答： 我会拆为接入层、编排与状态层、模型层、工具与知识层、记忆层、Runtime 执行层、观测评测层和安全层。接入层做鉴权限流；编排层维护 Goal、计划、状态机和 Checkpoint；模型层只负责规划、选择和总结；工具/知识层提供外部事实与动作；记忆层负责受控读写；Runtime 校验、执行、重试、预算和停止；观测层保存 Trace；安全层统一做最小权限、审批、沙箱与审计。分层重点是模型提案、系统执行。

I2. ReAct、Plan-and-Execute 与状态图应如何选择？

推荐回答： 中短任务、工具少且下一步强依赖刚返回结果时用 ReAct；步骤可预见、需要并行和进度管理时用 Plan-and-Execute；存在循环、分支、人工审批、失败恢复或必须持久化的复杂流程时，用显式状态图承载控制流。三者不是互斥：状态图可作为 Runtime 骨架，高层 Planner 生成 DAG，具体节点内部再用受预算限制的 ReAct。路径完全固定时直接 Workflow，避免不必要的自主决策。

I3. 工具有几十甚至上百个时，如何设计路由？

推荐回答： 我不会把所有 Schema 一次塞给模型，而会采用“权限过滤—任务粗分类—语义召回 Top-K—模型精排”的分层路由。L0 常驻核心工具，L1 只放名称和适用边界，命中后再加载 L2 详细 Schema 或 Skill body。description 必须写清何时用与禁用场景，候选工具还要按租户和阶段裁剪。上线用选型准确率、无效调用、输入 Token 和成本回归；Runtime 最终只允许白名单中的工具执行。

I4. 如何判断工具调用失败是路由、参数、执行还是结果使用问题？

推荐回答： 我会为每次 Invocation 记录候选工具集、最终工具、参数校验、执行状态、Observation ID 和最终答案引用。选错工具属于路由或 description；工具正确但 Schema/业务校验失败是参数生成；校验通过却超时、5xx 或权限拒绝是执行层；成功 Result 未进入 Context 或被答案曲解是结果使用。分别统计选择准确率、参数合法率、执行成功率和 Observation 利用率，做同一 Scenario 的回放，避免用一个总成功率掩盖归因。

I5. 怎样定义并检测 Agent 的“假完成”？

推荐回答： 假完成是 Agent 把任务标成 Success 或声称副作用已发生，但 Trace 中没有满足验收的成功 Observation。检测时先为任务定义完成证据：查询类要求关键断言绑定来源 ID，写操作要求执行回执、幂等键和执行后状态核验，Research 要求关键事实可追溯。Final Gate 只读取结构化证据，不采信模型自述；证据不足则继续、降级、明确失败或转人工，并把假完成率作为轨迹级阻断指标。

I6. Agent 评测中，如何做到指标可计算且失败可归因？

推荐回答： 我会建立带工具桩和失败注入的 Scenario 集，分节点、轨迹、任务、安全四层。节点看路由、参数和 Schema；轨迹看重复调用、恢复、步数和假完成；任务按 Rubric 算 Success；安全看越权拦截与误拒。所有指标绑定 Trace 字段，如 call ID、Observation ID、状态迁移和版本。失败后沿“计划—调用—执行—证据使用—Final Gate”归因，再做固定变量的消融，不能看到答案错就只改 Prompt。

I7. 如何设计一个可恢复、不会重复副作用的长任务 Agent？

推荐回答： 状态图每个稳定边界保存版本化 Checkpoint，包括计划、当前节点、open/done、预算、工具调用 ID、幂等键和副作用状态。执行写操作前先记录 Intent，使用幂等键调用，执行后查询真实状态再提交节点完成；崩溃恢复时先校验依赖版本和外部状态，而不是直接重放。Trace 用于审计，Checkpoint 用于续跑。不可恢复冲突转人工，超过总时限或重试上限则安全落到失败终态。

I8. 请说明 MCP、Function Calling 和 Agent Runtime 的关系。

推荐回答： MCP 负责让 Client 以统一协议发现并访问外部 Server 暴露的 Tools、Resources 和 Prompts；Function Calling 负责模型在一次推理里输出工具名和结构化参数；Runtime 则把两者接成可靠闭环：过滤可见能力、校验 Invocation、执行 MCP Tool、处理超时鉴权，把 Result 写回并更新 State。MCP 是接入标准，不是执行授权，也不替代模型工具协议。生产中还需租户隔离、最小权限、审批、审计和服务端信任管理。

I9. 如何防止恶意 MCP Server 或 Tool Result 诱导 Agent 越权？

推荐回答： Server 的描述和返回内容都按不可信外部数据处理，不能升格为 system。接入前固定可信 Server 清单、能力与版本，运行时按任务和身份裁剪工具；Invocation 做 Schema、业务、权限与目标域校验，高风险动作进入确认档，文件、网络和进程运行在沙箱。Result 带来源和信任标记，清洗其中的伪指令，只提取任务相关事实。还要审计能力变更、敏感信息外发和异常调用，支持立即禁用 Server。

I10. 你会如何设计自动、确认、禁止三档审批策略？

推荐回答： 我会根据副作用、可逆性、数据敏感度、外联范围和用户授权分档。公开信息查询、只读且幂等的操作可自动；写文件、发邮件、改订单、调用外网等需展示工具、目标、关键参数和影响，获得一次性确认；读取密钥、绕过权限、任意 Shell 或未授权网络直接禁止。策略由 Runtime 根据身份和环境执行，不由模型信心决定。审批结果写入 Trace，参数变化后原确认失效，避免“确认 A、执行 B”。

I11. Context 越来越长导致 Agent 忘记约束，你如何处理？

推荐回答： 先从 Trace 确认是窗口超限、Lost in the Middle、检索噪声还是压缩丢规则。然后把 Goal、验收、安全边界、当前 open[] 和副作用状态设为不可摘要字段；旧 Trace、网页全文和重复轮次按水位或阶段压缩，单次大 Result 先裁剪；事实转外存并按需检索。压缩后同步 Working state 和 Checkpoint，运行约束完整性校验。若角色或阶段差异大，可用 Context Isolation，而不是只换更长窗口。

I12. 什么时候应该引入 Subagent？如何避免多 Agent 失控？

推荐回答： 当子任务边界清晰、可独立验收、需要不同工具或会产生大量局部 Context，并且并行收益超过交接成本时才引入 Subagent；简单流程优先单 Agent + Skill。主 Agent 只分发最小 Goal、输入、预算、工具白名单和硬规则，子 Agent 返回结构化结果、证据与未完成项，不回灌全部 Trace。Runtime 限制层级、并发、预算和超时，合并时处理冲突与部分失败，高风险工具仍统一走主权限策略。

I13. Research Agent 搜索结果互相冲突时，如何继续并完成报告？

推荐回答： 我会先保留来源、时间、版本和原文指针，不让 Writer 自行选边；按权威性、时效和独立来源数评估，必要时由 Planner 新增针对性检索或查一手资料。Working state 把“已确认事实、冲突项、缺口”分开，预算内仍无法消解时，在报告中并列证据并声明不确定性。评测同时看引用忠实、冲突披露和无依据断言，而不是强迫 Agent 给唯一结论。高风险业务可转专家确认。

I14. Agent 连续反思三次仍失败，系统应该怎么收尾？

推荐回答： 首先不能继续无限 Reflection。Runtime 应检查三次是否产生了新 Observation 或指标提升；若只是重复同一策略，触发熔断。根据任务选择降级：只返回已验证的检索片段、明确说明材料不足、换备用工具或模型、保存 Checkpoint 后转人工。最终回答要区分已完成、未完成和失败原因，不能伪装成功。Trace 保留每次策略、错误和预算，失败样本进入离线 Scenario，用于判断应改 Prompt、工具、数据还是流程。
