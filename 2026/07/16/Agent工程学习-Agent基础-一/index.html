AI-Agent工程学习-Agent基础(一)

发表于 2026-07-16 更新于 2026-07-17 分类于 计算机
Agent 基础开篇：与 Chat/Workflow 的边界、五件套公式、Environment、Agent Loop、State 与失败模式。

接 Prompt Engineering（三）、LLM 基础（四）· Tool Calling。讲清 Agent 如何做成闭环系统。

0. 本系列在学习路径中的位置

LLM 基础负责：模型怎么表示与生成、怎么调用 API、Tool Calling 闭环。

Prompt Engineering负责：怎么写可控输入、推理编排与版本评测。

Agent 基础负责：在工具闭环与可控 Prompt 之上，理解 目标驱动的循环系统——谁决策、谁执行、状态存哪、何时停止。Skill 认名在（三），架构收口在（六）。

依赖（已学，本文只引用）：

  1. 消息角色与「看不见则未发生」
  2. Chat Completion / Tool Calling
  3. Context Window
  4. Prompt 四积木与可截断
  5. Chaining vs Tool 多轮

1. Agent 是什么

什么是 Agent？

Agent 是在约束（工具、权限、预算、停止条件）下，用 LLM 做决策、用工具改世界（或查询世界）、用记忆保状态，直到任务完成或失败的系统。

先纠三偏：

  1. Agent ≠ 聊天机器人：聊天回答一问一答；Agent 为 目标完成 而持续行动。
  2. Agent ≠ 只等于 Tool Calling：Tool Calling 是「手脚」的 API 能力；Agent 还要有循环、状态、停止条件。
  3. Agent ≠ 把 LLM 塞进 while：真正工程件是 Runtime（超时、重试、校验、限流、审计）。

2. Agent vs Chat vs Workflow

形态 控制流 典型结构 何时够用
单轮 / 多轮 Chat 用户主导下一问 Prompt → Answer 翻译、摘要、简单抽取
Workflow / 流水线 人预设步骤（可含固定 DAG） Prompt Chaining ± 固定工具点 路径清晰、要可预期
Agent 模型在循环里选型 Goal + Loop + State + Tools 路径需试探、多工具协作

与 Prompt Chaining vs Tool 多轮 同一逻辑：路径固定优先 Workflow；需要边观察边改道再用 Agent。不知何时上 Agent，后面学 Loop 也会滥用。

易错：把「调了一次 search」就叫 Agent——那只是 Tool-augmented Chat。

3. 核心公式：五件套

组件 职责一句话 初学者对照 回指已学
LLM 读状态、推理、出决策 「大脑」 Inference、Chat Completion
Memory 决定下一轮 Context 里放什么 「笔记与档案」 Context ↔ Memory
Tools 真正查询 / 执行外部动作 「手脚」 Tool Schema → Result
Planning 把目标拆成可执行步骤 / 图 「作战地图」 Decomposition
Runtime 驱动循环：调度、校验、限流、停止 「操作系统」 本系列重点补

边界题：

  1. LLM：没有工具也会「说」；Agent 优势在闭环验证，不是修辞更好。
  2. Memory：不等于模型「自己记得」；是应用写回 messages / 外存。
  3. Tools：模型只提案；执行权在应用（防「已执行」幻觉，见幻觉）。
  4. Planning：简单任务可即时规划（下篇 ReAct）；不必每题先画宏大计划。
  5. 缺 Runtime：没有停止条件与校验 → 烧 Token、无限循环、假完成无人拦。

4. Environment / Action / Observation

把 Agent 放进一个世界观里，Loop 才说得清：

概念 含义 工程对应
Environment Agent 所处的外部世界 搜索引擎、DB、文件系统、HTTP API…
Action Space 允许的动作集合 Tool allowlist（白名单）+ 参数 Schema
Observation 行动后的反馈 Tool Result / Error / 超时 / 截断后的摘要

协议细节见 LLM 四 · Tool Calling：模型不直接碰数据库，应用执行后再写回。

5. Agent Loop

5.1 四段语义

环节 含义 常见产物 易错
Thought 基于 State 做推理 理由、中间假设 与用户可见答案混写
Action 选动作：调工具 / 回答 / 追问 Tool Invocation 或 Final Answer 空 Action、假完成
Observation 环境 / 工具回馈 tool 消息、错误 结果过大挤爆 Context
Reflection 对照目标评估进展 「够了吗 / 错在哪」 每步强行长反思 → 贵且慢

Reflection 可 显式（单独一步）或 隐式（下一次 Thought 里带评估）。下篇展开 Reflection / Self-Refine。

5.2 标准伪循环（建议能默写）

谁干活：

  1. Reason / Select：主要靠 LLM + Prompt（PE 一 合同）。
  2. Execute：必须靠 Runtime——绝不能「模型说执行了就算」。
  3. Observe / Update：Runtime + Memory 策略。

最小可运行 Loop（mock 工具 + Observation 写回 + 预算 + 停止）：

预期轨迹摘要：

步 事件 messages 变化
0 用户提问 +1 user
1 调 search +1 tool（Observation 写回）
2 Final Answer +1 assistant，done=True

关键结论（接 LLM 三 1.2、LLM 四 tool 消息）：

Observation 如果不写回本次 messages，下一轮 Inference 看不见——模型只能猜，幻觉高发。

5.3 停止条件

  1. 成功：满足验收标准（Rubric / 结构化 checker）。
  2. 放弃：工具连续失败、目标冲突、缺权限。
  3. 预算：max_steps、max_tokens、timeout（与模型级 EOS/max_tokens 分层：一层停「本次生成」，一层停「整个 Agent」）。
  4. 人工介入：写库、付款、发邮件等高风险 Action 前审批。

接 PE 一「可截断」：信息不足时应追问或停止，而不是空转。

停止条件语义见上；可收敛 Loop 的工程设计（合同、验证门、预算着陆）见 Loop Engineering（一）。

6. State：每时每刻至少有什么

字段 内容
Goal 用户任务与成功标准
Scratchpad / Working 当前子目标、中间变量、未决问题
Trace 调了哪些工具、结果摘要、错误
Budget 剩余步数、Token、费用、墙钟
停止信号 成功 / 失败 / 需人工 / 超时

工程建议：显式结构化 state（如 JSON），不要只靠非结构化的长段对话文字撑「记忆」。细节到本系列（三）。

7. 典型失败模式

  1. 空转：Thought 很多，从不 Action。
  2. 工具死循环：同一工具同参反复调。
  3. 假完成：没有 Observation 就宣称成功（幻觉 变种）。
  4. Context 膨胀：轨迹全量入窗 → 丢关键约束（Lost in the Middle / 裁剪）。

Runtime 的职责之一，就是检测并打断上述模式。

自学检查

  1. 默写 while … Reason → Select → Execute → Observe → Update。
  2. Observation 不写回 messages，下一轮会怎样？
  3. 去掉 Runtime、只留 LLM + Tools，系统缺什么？

总结

Agent：目标驱动的闭环系统，不是「会调工具的聊天」。

选型：Chat / Workflow / Agent 按路径是否固定来选。

五件套：LLM、Memory、Tools、Planning、Runtime；缺 Runtime 最危险。

Environment：Action Space 约束手脚；Observation 必须写回。

Loop：Thought → Action → Observation →（Reflection）→ Update State，带预算与停止条件。

State：Goal、Scratchpad、Trace、Budget、停止信号。
