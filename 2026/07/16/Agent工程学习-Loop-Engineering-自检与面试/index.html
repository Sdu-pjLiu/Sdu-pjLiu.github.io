AI-Agent工程学习-Loop Engineering(自检与面试)

发表于 2026-07-16 更新于 2026-07-20 分类于 计算机
Loop Engineering 一～三阶段自检与面试导向问答；覆盖收敛合同、验证门、嵌套环、预算、无进展、反模式、回归与实践阶梯。

完成 Loop Engineering（一）～（三）后，重点不是背会 Contract、Gate、Budget，而是能把它们拼成一条可收敛、可证明、可放弃的 Agent Loop。本文迁移三篇正文的全部自学检查与阶段收口题，并补充生产场景面试题。

0. 使用说明

建议先遮住“推荐回答”，在 60～120 秒内口述。自检题应说清“定义—机制—失败边界”，面试题则应进一步说明“信号—Runtime 动作—退出产物”。如果答案只剩“加 Prompt、让模型反思”，说明还没有站到 Loop Engineering 视角。

推荐三轮练习：

  1. 第一轮只答结论，确认概念边界。
  2. 第二轮补出 Contract、Gate、预算与退出路径。
  3. 第三轮随机抽场景题，在两分钟内给出可落地方案。

1. 学习自检

1.1 Contract、Gate 与 Maker–Checker

S1. Loop Engineering 与 Agent Loop 语义分别回答什么问题？

推荐回答： Agent Loop 语义描述循环的基本形状，即模型如何在 Thought/Reason、Action 与 Observation 之间迭代；Loop Engineering 则把整条循环作为工程对象，规定何时启动、如何验证、何时换策略、何时成功或放弃。前者回答“循环怎样运行”，后者回答“开放路径如何在约束内客观结束”。只有 Loop 语义而没有合同、门禁和预算，本质上仍是昂贵的 while True。

S2. Loop Engineering 与 Prompt Engineering、Workflow 的边界是什么？

推荐回答： Prompt Engineering 工程的是单次或分步模型输入合同，主要控制模型看到什么、输出什么；Workflow 预先写死步骤和分支，适合路径可预测的任务；Loop Engineering 管理路径开放的 Agent 循环，重点是进展、验收和停止。路径固定时优先 Workflow，不应为了“智能”强套 Agent；需要边观察边选动作时才启用 Loop，并用 Runtime 保证可封顶。

S3. 什么是收敛合同？为什么要在启动 Loop 前定义？

推荐回答： 收敛合同是循环开始前明确的成功、失败和放弃谓词，并尽量转成程序可检查的条件。它让内环知道目标，让验证环能返回 pass/fail 与缺口，也让外环在不可恢复时正确退出。若运行中才由模型临时解释“什么叫完成”，目标会随轨迹漂移，模型很容易把“已经做了不少”误判为成功。

S4. 举一个坏 Contract 和一个好 Contract。

推荐回答： “把调研报告写好”是坏合同，因为“好”没有可重复判断的标准。较好的合同是：“至少引用三个独立来源；每条关键主张带 observation_id；冲突资料明确标注；总工具步数不超过 10。”前者只能依赖主观感受，后者可通过计数、字段校验和来源规则检查；开放质量仍可补 Rubric，但不应放弃可自动化部分。

S5. 好 Contract 为什么至少要覆盖成功、失败、放弃三态？

推荐回答： 只有成功条件时，权限缺失、目标冲突或环境不可用都无法被正确表达，循环只能继续重试或异常崩溃。成功表示产物已满足验收；失败表示某次动作或阶段未通过但可能恢复；放弃表示当前约束下不可恢复，应保存状态并解释原因。三态把“不成功”拆成可重试与不可继续，才能让外环选择正确路径。

S6. 为什么“可机检 Done”优于纯自然语言判断？

推荐回答： Schema、单测、HTTP 状态、引用计数和业务规则可以稳定复现，能直接成为 Runtime 门禁；自然语言自评受措辞、模型版本和随机性影响，容易把流畅当正确。开放任务可以使用独立 Judge 和 Rubric，但确定性部分应先自动化。原则不是完全排斥模型判断，而是把最可靠的证据放在最高优先级。

S7. Verification Gate 的信任梯度是什么？

推荐回答： 通常从高到低是：确定性检查、独立 Checker、同模型自评。确定性检查如测试、Schema 和状态查询，模型难以伪造；独立 Checker 用隔离 Context、固定 Rubric 或另一模型验收；同模型自评仍受“维护自己答案”的偏差影响。环内 Gate 应优先使用前两级，自评只能作为辅助信号，不能单独关环。

S8. 为什么同模型自评不能作为唯一 Success 条件？

推荐回答： Maker 已生成答案并沿当前轨迹形成承诺，同一模型再次询问“是否完成”并没有获得新的外部真值，常会重复原判断或合理化缺口。它还可能把格式完整、语言自信误当作事实和副作用已完成。若必须使用自评，应叠加硬步数上限、外部 Observation 和抽样校验，并禁止其单独把状态写成 Success。

S9. Maker–Checker 的职责和权限如何划分？

推荐回答： Maker 负责规划、调用工具和产生候选产物；Checker 只依据 Contract 检查证据、规则和缺口。Checker 宜只读，不应同时拥有写库、发信或修改产物的权限，否则验收失败时它可能直接“替自己修到通过”，角色重新合并。实现上可用确定性规则、同进程隔离 Prompt 或独立子 Agent，关键是验收依据与写操作权限分离。

S10. Checker 是另一模型就一定独立可靠吗？

推荐回答： 不一定。若 Checker 共享 Maker 的完整推理、模糊目标和相同激励，只是换一次 Completion，仍可能复述原结论。有效独立还要求固定 Contract、最小只读 Context、可追溯 Observation、明确输出 Schema，必要时使用不同模型或确定性规则。模型身份只是隔离手段之一，真正的独立来自证据、权限和判断流程。

1.2 嵌套环、退出与预算

S11. 内环、验证环、外环各负责什么？

推荐回答： 内环执行短步 Reason→Act→Observe，取得真实 Observation 并更新局部状态；验证环对照 Contract 运行 Gate，返回 pass/fail 和结构化缺口；外环根据进展、剩余预算和失败类型决定继续、重规划、换工具、HITL 或退出。分层避免同一步既修改世界又给自己打分，也让局部工具失败不必直接升级为整任务失败。

S12. 为什么内环失败不等于整个任务失败？

推荐回答： 一次工具超时、参数不合法或搜索无结果只说明当前动作没有推进，不代表合同不可达。验证环应把失败转成可解释缺口，外环再按错误类型选择有限重试、改参数、换工具或缩小子目标。只有权限缺失、合同冲突、环境长期不可用等不可恢复条件成立，才进入放弃路径。

S13. Loop 应有哪些计划内退出类型？

推荐回答： 至少包括收敛成功、硬顶、无进展和不可恢复四类。成功由 Contract Gate 证明；硬顶由步数、Token/费用或墙钟预算强制触发；无进展由重复调用或指标不改善触发；不可恢复覆盖缺权限、目标冲突和环境不可用。每类都应有明确状态码和落地动作，而不是统一抛出“Agent 失败”。

S14. 模型级停止与 Agent Runtime 硬顶有什么区别？

推荐回答： EOS、stop sequence 和 max_output_tokens 只停止一次模型生成；Runtime 的 max_steps、总 Token/费用和总 timeout 控制的是整条 Agent Loop。一次 Completion 正常结束后，Agent 仍可能继续调用工具和模型，因此模型级停止不能替代整环预算。硬顶必须由 Runtime 强制执行，不能依赖模型看到提示后自觉停止。

S15. 硬顶与软任务预算如何配合？

推荐回答： 硬顶是不可突破的安全上限，负责防止跑飞和无限烧钱；软任务预算是模型可感知的剩余工作量提示，用于调整节奏、优先级和提前收尾。软预算可能被忽略或略微超出，因此不能替代硬顶。合理组合是 Runtime 保留绝对天花板，同时把剩余步数、Token 或时间写入状态，让外环在接近上限时转入收口策略。

S16. 压缩后为什么必须 forward remaining？

推荐回答： Context compaction 会替换历史消息，如果剩余步数、费用、Contract 和 open[] 只存在于被摘要的文本中，压缩后治理状态会被重置，Agent 可能误以为又有完整预算。应把这些字段放在结构化、不可摘要的 Runtime State，并在新 Context 中续传。压缩的是叙事历史，不是合同、权限与剩余额度。

S17. 什么是优雅收尾？它与假完成有什么区别？

推荐回答： 优雅收尾是在硬顶或不可恢复条件触发时，有计划地停止：保存 Checkpoint，返回部分结果、未完成项、已尝试策略和建议下一步。它明确标记当前不是 Success，因此允许用户或下一次运行安全接续。假完成则隐瞒缺口，把“预算没了”包装成“任务完成”，会污染指标并让下游错误使用不完整产物。

S18. 预算耗尽时最少要留下哪些信息？

推荐回答： 最少应留下可恢复的 Checkpoint 和 handoff note。Checkpoint 记录 Contract、当前计划、已完成/未完成项、关键 Observation、剩余或耗尽的预算以及已经发生的副作用；handoff note 说明停止原因、尝试过的策略、当前缺口和建议下一步。面向用户还应返回可用的部分结果，并明确其边界。

S19. 如何检测 No-Progress？

推荐回答： 可组合三类信号：调用层检测归一化后的同工具同参数重复、相同错误码序列；状态层检查失败用例数、open[] 长度或证据覆盖率是否改善；信息层检查新 Observation 是否带来新增事实。单看“调用次数不同”不够，因为 Agent 可能在多个工具间循环；也不能把正常交叉验证误判为空转，所以阈值要结合子目标和 Contract。

S20. 检测到无进展后有哪些出路？

推荐回答： 第一是换策略，如改 query、换工具、缩小子目标或重新规划；第二是保留 Contract 与有效 Observation，丢弃可能污染决策的脏轨迹后重启；第三是 HITL，请人补权限、约束或判断。若已确认不可恢复，则直接放弃并优雅收尾。禁止原样无限重试，因为它既无信息增益，也会放大成本与副作用。

1.3 反模式、组件拼装、回归与 L0～L2

S21. 什么是“有验证无上限”？为什么仍会烧预算？

推荐回答： “有验证无上限”指每轮确实运行测试或 Checker，但 Gate 失败后没有最大步数、总时限和无进展熔断，于是 Agent 可以永远“修改—验证—再修改”。验证只回答当前是否通过，并不保证未来一定收敛。可靠 Loop 必须把 Gate 与硬顶、错误分类和外环退出策略一起设计。

S22. 请列出三种典型 Loop 反模式及改法。

推荐回答： 无合同 while 应改为启动前定义成功、失败、放弃谓词；自评唯一门应改为确定性 Gate 或独立只读 Checker；撞预算不收尾应改为 Checkpoint、handoff 和部分结果。其他高频反模式还有验证无上限、压缩丢合同/预算、内环兼验收，以及把固定 Workflow 硬套成 Agent。

S23. 为什么固定路径任务不应强行使用 Agent Loop？

推荐回答： 路径固定时，Workflow 能明确表达顺序、分支、重试和失败位置，更可预测、便宜且易测试。完整 Agent Loop 会额外引入模型选型的不确定性、工具误选和停止治理成本。是否使用 Agent 的判断标准不是任务“看起来复杂”，而是下一步是否必须根据运行时 Observation 动态决定。

S24. 在组件拼装中，Contract 与 Skill 谁先谁后？

推荐回答： 逻辑上 Contract 先定义“什么算完成和何时停”，Skill 再指导内环“这类任务通常怎么做”。Tools 提供动作，Memory/Checkpoint 保存状态，Runtime 执行预算、权限、Guardrail、Hooks 和 HITL，LLM+Prompt 负责决策。Skill 可以改变路线，却不能覆盖 Contract 或获得 Runtime 未授权的能力。

S25. Loop Engineering 与 Tools、Memory、Runtime 的关系是什么？

推荐回答： Loop Engineering 不替代这些组件，而是规定它们如何围绕收敛协作。Tools 产生真实 Observation 和副作用，Memory/Checkpoint 让跨步状态可见，Runtime 强制权限、预算和 Gate，LLM 依据 Prompt 与状态选择下一步。缺少任一层都可能运行，但不能形成可靠生产闭环：例如有 Tools 无 Gate 会假完成，有 Gate 无预算会无限验证。

S26. 如何把假完成率接到 Runtime 门禁？

推荐回答： 先定义“模型宣称完成但没有通过必要 Gate”的事件，并在 Trace 中记录终止原因、证据引用和 Gate 结果。Runtime 收到 Final 候选时必须重新运行确定性检查或独立 Checker，未通过则不能写 Success，只能返回缺口给外环。离线统计自评关环率和假完成率，超过阈值时阻断 Loop 版本发布。

S27. 哪些轨迹指标适合回归 Loop？

推荐回答： 核心指标包括任务成功率、假完成率、重复/不必要工具调用率、平均步骤、每次成功成本、Tool Error Recovery Rate，以及各类退出占比。成功率看结果，重复率和步骤看效率，恢复率看外环是否会换策略，退出分布能暴露硬顶或不可恢复异常。必须按场景分层，避免一个总体均值掩盖某类工具风暴。

S28. 修改 Contract、Gate 或预算后，为什么必须做 Scenario 回归？

推荐回答： 这些配置共同决定整条 Loop 的行为，微小变化可能让成功条件过松、正常任务被误拦或成本突然增加。因此它们都应作为 Loop 版本，与 Prompt、模型和工具 Schema 一并固定；使用成功、边界、无答案、工具失败、无进展和预算耗尽场景回归。发布不仅看任务成功率，还要设置安全、成本和延迟护栏。

S29. L1 与 L2 的分水岭是什么？

推荐回答： L1 已有 Maker–Checker 分离，即内环执行、验证环用确定性规则或只读 Checker 验收；L2 在此基础上增加外环治理，能识别无进展后换策略，并在预算耗尽时优雅收尾，还能在压缩后续传剩余预算。分水岭不是模型更强，而是系统是否具备策略切换和可恢复退出。

S30. L0→L2 各自证明了什么？

推荐回答： L0 用单一可机检 Contract 加 max_steps，证明系统至少知道 Done 且不会无限运行；L1 加入独立验证环，证明生成与验收已分离；L2 加入无进展检测、外环重规划、双层预算和优雅收尾，证明复杂 Loop 能在失败与资源约束下安全收敛。实践应逐级建设，先有客观门，再增加复杂规划。

2. 面试真题

以下题目按主题归纳、改写自公开面经与题库，用于训练表达，并非逐题对应某一场真实面试；综合参考来源见文末「参考面经与题库」。

I1. Agent 连续调用多个工具后陷入“工具风暴”，你会在哪里阻断，如何处理？

推荐回答： 我会在 Runtime 的 tool executor 统一入口前放控制中间件，而不是只写 Prompt 或把逻辑分散到每个工具。调用前检查工具白名单、权限、参数、会话与单工具预算；调用后记录归一化参数哈希、错误码、输出摘要和状态 diff。相同调用连续出现、多个工具来回切换但 Contract 指标不改善、连续可重试错误超阈值时触发 loop_detected 或熔断。随后按“有限重试→换策略/降级→HITL→放弃”处理；命中总步数、Token、费用或墙钟硬顶则强制停止。退出时保存 Checkpoint、已发生副作用和 handoff，返回部分结果与明确缺口，绝不能让模型自行宣布成功。

I2. 请设计一个从 Contract 到退出的可靠 Agent Loop。

推荐回答： 启动时加载结构化 Contract，包括 success/failure/abandon 谓词、允许工具、硬顶和软预算。内环每次只做短计划、一次或少量动作并写回真实 Observation；验证环运行确定性 Gate，无法自动判断的部分交给只读 Checker，输出结构化缺口；外环依据缺口、进展和剩余预算选择继续、重规划、HITL 或退出。所有 Final 候选必须过 Gate，所有工具都经权限和参数校验。终止状态区分 success、budget_exceeded、no_progress 和 unrecoverable，并统一落 Trace、Checkpoint 与 handoff。

I3. 编码 Agent 的测试一直失败，你如何区分“正常迭代”和“无进展死循环”？

推荐回答： 我不会只看失败次数，而会定义进展向量，例如失败用例数、错误类型集合、lint 数、修改文件范围和 Contract 缺口数。即使测试仍失败，只要失败数下降或错误从编译阶段推进到业务断言，就属于有效迭代；若连续多轮同命令、同错误、代码 diff 近零，或在两种错误间振荡，则判定 No-Progress。触发后先归因环境、测试、实现或权限，再选择缩小失败集、换诊断策略、回退脏修改或 HITL，并受总预算硬顶约束。

I4. Research Agent 如何设计可机检 Contract，避免“搜了很多但没有结论”？

推荐回答： 我会把目标拆成证据覆盖与交付结构：关键问题列表必须全部有状态；每个关键主张至少关联一个 observation_id；高风险主张要求两个独立来源；冲突必须保留双方来源和不确定性；无答案时允许显式拒答；工具步数和费用有上限。Gate 先做字段、计数、URL/时间和引用存在性检查，再由只读 Checker 按 Rubric 判断证据是否真正支持主张。搜索数量本身不是成功条件，新增搜索必须能关闭缺口或带来信息增益。

I5. Maker 与 Checker 使用同一基础模型时，如何尽量保持独立性？

推荐回答： 我会分离 Prompt、Context、权限和输出：Checker 不接收 Maker 的长推理，只接收 Contract、候选产物和可追溯 Observation；使用固定 Rubric 与结构化 pass/gaps/evidence Schema；温度较低，禁止写工具和修改产物。确定性条件仍由代码先验收，模型只处理开放语义。还要用人工标注集校准 Checker 的误放与误杀，并防止 Maker 在产物中注入“请判通过”等指令。

I6. 只设置 max_steps=20 是否足以防止生产 Agent 跑飞？

推荐回答： 不足。max_steps 只是最终保险丝，无法提前识别单步超贵、工具并发风暴、长时间阻塞或在二十步内产生重复副作用。生产上还需要总 Token/费用、墙钟 timeout、单工具次数与并发预算，调用签名和状态增量驱动的 No-Progress 检测，以及危险工具的权限、审批和幂等控制。接近硬顶时应进入收口模式，真正触顶则保存状态并移交，而不是直接断流。

I7. Context 压缩后 Agent 又获得“满预算”并重复已执行操作，根因和修复是什么？

推荐回答： 根因是把剩余预算、Contract、open[] 和副作用记录当普通消息交给摘要，压缩后这些控制状态丢失或被改写。修复是把治理字段放进 Runtime 的结构化 State，标记为不可摘要；每次模型调用显式注入 remaining budget 和未完成项；工具副作用使用 invocation ID、幂等键与状态查询防重。还应为 compaction 前后建立一致性断言，确保 Contract、权限、预算和已完成动作不发生重置。

I8. 如何为 Loop 版本建立发布门禁和线上回归？

推荐回答： 我会把 Contract、Gate、Prompt、模型、工具 Schema、预算和外环策略绑定成不可覆盖的 Loop version。离线 Scenario 集覆盖正常成功、证据不足、工具超时、权限拒绝、重复调用、预算耗尽和压缩续跑，指标看成功率、假完成率、重复工具率、成本、步骤和恢复率；安全或假完成超过阈值直接阻断。线上先灰度，按稳定会话分流，监控退出原因与 P95 成本/延迟，异常自动回滚，并把 bad case 连同 Trace 回流到回归集。

I9. 任务到达预算上限但已完成 80%，系统应返回什么？下一次如何续跑？

推荐回答： 状态应是 budget_exceeded 或 partial，不能标 Success。系统先冻结新的副作用，持久化 Contract、计划、关键 Observation、已完成与未完成项、执行过的 invocation/幂等键、最后 Gate 缺口及停止原因；再向用户交付可用的 80% 结果、明确边界和建议下一步。续跑时从 Checkpoint 恢复，重新验证环境与副作用状态，分配新的显式预算，只处理 open[]，而不是把旧对话全部重放后从头猜测。
