AI-Agent工程学习-LLM基础学习(二)

发表于 2026-07-14 更新于 2026-08-20 分类于 计算机
接第一篇：Inference、Logits、解码策略、Temperature / Top-k / Top-p、停止条件，以及 KV Cache 与 Prefill/Decode。

接第一篇：从「预测下一个 Token」讲清推理与采样

1. Inference（推理）

什么是 Inference？

Inference（推理）指：模型已经训练好之后，用当前输入 生成输出 的过程。聊天、补全、Agent 调 API，用的都是 Inference，不是在现场重新训练模型。

与 Training 的对比：

Training（训练） Inference（推理）
目的 学参数 用参数生成
是否更新权重 是 否
典型场景 预训练、SFT Chat、API、Agent

负责：读入 Context → 前向计算 → 得到下一 Token 的分布 → 选出 Token → 写入序列 → 重复，直到结束条件满足。

第一篇讲到 Transformer 输出表示后「预测 Token」；本篇从这里往下拆：怎么从模型输出变成一个个 Token，以及怎么算得更快。

1.1 自回归（Autoregressive）生成

现代 Decoder-only LLM 是 自回归（Autoregressive, AR） 的：

  1. 每次只预测 下一个 Token（Next-Token Prediction）。
  2. 把新 Token 追加 到序列末尾，作为下一步的输入。
  3. 重复，直到触发停止条件（见 1.4）。

「自回归」= 用已经生成的内容，回归地预测下一步。这与第一篇的 Causal Attention一致：每一步只能看见过去，不能看见未来。

1.2 Inference 与第一篇概念的关系

  1. Tokenization：输入先变成 Token ID；输出也是 Token，再解码成文字。
  2. Context Window：已有输入 + 已生成输出都占同一窗口；输出越长，剩余输入预算越少。
  3. Causal Attention：只能看过去 Token，因此可以逐步生成，也才能用 KV Cache。

1.3 Inference 对 Agent 的影响

Agent 一次任务往往多次 Inference：规划、调工具、读结果、再规划。每次都会产生延迟与 Token 费用。采样参数（Temperature 等）还会影响：是否稳定执行工具、是否胡编参数、回答是否发散。

1.4 生成何时停止：EOS / stop / max_tokens

自回归不会无限跑下去，常见停止条件：

  1. EOS（End of Sequence）：模型生成了表示「结束」的特殊 Token（具体 ID 因 Tokenizer / 对话模板而异），服务端据此停。
  2. stop 序列：API 可配置遇到某些字符串 / Token 序列就停（如三个反引号、自定义分隔符），便于截断到指定格式边界。
  3. max_tokens（或 max_output_tokens）：输出长度上限。到顶就停，即使句子没说完——所以第一篇强调要在 Context 里给输出预留额度，并合理设上限。

Agent 调工具时：既要设够 max_tokens 装下完整 JSON / 参数，又可用 stop 减少废话尾巴。

2. Logits

什么是 Logits？

Logits 是模型在词表上、对每个候选 Token 给出的 原始分数（未归一化）。可以理解为：「下一个词是这个 ID 有多合适」的打分表，但这时 还不是概率。

假设词表大小为 $V$（如数万～十几万），某一步会得到长度为 $V$ 的向量：每个位置一个 logit。

2.1 Softmax：从分数到概率

Softmax 把一组 Logits 变成和为 1 的概率分布（第一篇 Attention里也用 Softmax，那里是把匹配分数变成关注权重；这里是把词表分数变成「下一个 Token」的概率）：

$$P_i = \frac{e^{z_i}}{\sum_{j=1}^{V} e^{z_j}}$$

其中 $z_i$ 是第 $i$ 个 Token 的 logit。

容易混淆的点：

  1. Logits：可正可负，和不必为 1。
  2. 概率：Softmax 之后，每项在 $(0,1)$，总和为 1。
  3. Decoding 往往先对 Logits 做变换（如除以 Temperature、做 Top-k / Top-p 截断），再 Softmax 或在截断后的集合里采样。

2.2 LM Head 与流水线中的位置

Transformer 最后一层给出每个位置的隐藏向量后，还要经过一层线性投影（常称 LM Head / 语言建模头），把向量维度映射到 词表大小，才得到 Logits。

没有 Logits，就谈不上 Temperature 或采样：它们都是在「改分数 / 截候选」，再决定下一个 Token。

3. Decoding Strategy（解码策略）

什么是 Decoding Strategy？

Decoding Strategy（解码策略）指：拿到 Logits（或概率）之后，用什么规则选出下一个 Token。同一套 Logits，策略不同，生成风格可以差很多。

3.1 两大类

  1. Greedy Decoding（贪心）：每一步选当前概率最高的 Token。确定、可复现，但容易呆板、重复。
  2. Sampling（采样）：按概率随机抽。更自然、更多样，但同一 Prompt 多次结果可能不同。

Temperature、Top-k、Top-p 都是在 采样路径 上控制「有多随机、候选池多大」。

Greedy 与 Temperature → 0：

  • 理论上，$T \to 0$ 时 Softmax 会极端尖锐，采样结果 几乎总是 最高分 Token，行为接近 Greedy。
  • 工程上不少 API 提供 temperature=0 表示「尽量确定」；是否内部直接改成 argmax，因实现而异。
  • 需要严格可复现时：用 Greedy / temperature=0，并固定其他随机源；仍可能因实现细节有极小差异。

3.2 策略如何挂在生成链上

工程上常见组合：Temperature + Top-p，或 Temperature + Top-k，有的 API 允许两者同时开（先按各自规则过滤，再采样）。

3.3 和 Agent 的关系（预告）

  • 写代码、填 JSON、调 Tool：偏贪心或低温，要稳。
  • 头脑风暴、文案：可提高 Temperature / 放宽 Top-p，要活。

具体参数见下面几节。

4. Temperature

什么是 Temperature？

Temperature（温度）是一个标量 $T$，在 Softmax 前把 Logits 除以 $T$，用来控制分布的 锐利程度：

$$P_i = \frac{e^{z_i / T}}{\sum_{j} e^{z_j / T}}$$

4.1 直观效果

Temperature 分布形态 生成感觉
$T \to 0$ 几乎只剩最高分 近似贪心，很稳、很死板
$T = 1$ 模型原始分布 默认基准
$T > 1$ 更平坦 更随机、更跳跃，也可能更胡说

$T$ 越小，高峰越尖，更容易反复选同一批「安全」Token；$T$ 越大，小概率 Token 也更容易被抽到。

4.2 常见使用区间

口头上常说的「低温 / 高温」大致是：

  1. 0～0.3：事实问答、格式严格、工具参数。
  2. 0.5～0.8：一般对话、写作。
  3. 0.9～1.2+：创意、多样性优先（需能接受不稳定）。

具体数值因模型和厂商默认值而异，调参要以实测为准。

4.3 Temperature 对 Agent 的影响

Agent 若要 可靠调用工具（字段名、路径、JSON 不能飘），Temperature 宜低。若某一步是「想几个方案」，可单独提高 Temperature，再在执行步降回来——不同步骤可以用不同采样参数。

5. Top-k Sampling

什么是 Top-k Sampling？

Top-k：每一步只保留 Logits / 概率 最高的 k 个 Token，其余概率视为 0，再在这 k 个里按（重新归一化后的）概率采样。

5.1 工作机制

例如 $k = 50$：无论词表多大多小，这一步最多从 50 个词里抽。

5.2 特点

  1. 候选数量固定：好理解，好设默认。
  2. 分布很尖时：真正有意义的候选可能远少于 k，等于白留了一些低质量尾巴。
  3. 分布很平时：真正合理的词可能超过 k，会被硬切掉。

所以 Top-k 简单，但对「这一步有多不确定」不够自适应。

5.3 与 Temperature 的配合

通常先 Temperature 缩放 Logits，再做 Top-k 截断，最后采样。只调 k、不调 Temperature，也能改变多样性，但两者控制的维度不同：Temperature 改相对差距，Top-k 改候选个数上限。

6. Top-p Sampling（Nucleus Sampling）

什么是 Top-p Sampling？

Top-p（又称 Nucleus Sampling）：不固定个数，而是按概率从高到低累加，取 累积概率刚好达到（或超过）p 的最小集合，只在这个「核」里采样。

例如 $p = 0.9$：覆盖约 90% 概率质量的那些头部 Token，其余砍掉。

6.1 工作机制

6.2 Top-p 与 Top-k 对比

Top-k Top-p
截断依据 固定个数 k 累积概率阈值 p
候选规模 恒定 随分布尖/平自动变多或变少
直观性 更直观 对「不确定程度」更自适应

模型很有把握时，Top-p 集合可能只有很少几个 Token；拿不准时集合会变大——这是它常被默认推荐的原因之一。

6.3 常见组合

许多 API 同时提供 temperature、top_p、top_k：

  1. 只开 Temperature + Top-p 很常见。
  2. Top-k 与 Top-p 一起开时，以具体实现为准（通常是两者过滤条件都满足才保留）。
  3. 调参建议：先定任务要稳还是要活（Temperature），再用 Top-p 挡住明显的长尾胡话。

6.4 对 Agent 的影响

Tool 调用、结构化输出：Top-p 可偏低（如 0.8～0.95 且配合低温），减少抽到稀奇 Token。开放生成：可略提高 Top-p，但仍建议设上限，避免完全放任长尾。

6.5 同一组 Logits 的采样对照（算例）

设某步 Logits（Softmax 前）仅 4 个候选（教学简化，已省略其余词表）：

Token Logit $z_i$ 基准 $P$（$T=1$）
「Paris」 3.0 0.809
「London」 1.0 0.110
「Berlin」 0.5 0.066
「???」 −1.0 0.015

（四数之和为 1；由 Softmax $e^{z_i}/\sum_j e^{z_j}$ 直接算出。）

Temperature（只改 $T$，不截断）：

策略 效果 on 候选集
$T=0.3$ 「Paris」≈ 0.998，几乎贪心
$T=1$ 上表基准分布
$T=1.5$ 「Paris」降至 ≈ 0.66，「London」「Berlin」相对上升

Top-k（$T=1$，$k=2$）： 只保留 Paris、London → 重归一后 $P(\text{Paris})≈0.88$。

Top-p（$T=1$，$p=0.9$）： Paris 已 0.809，再加 London 累积 ≈ 0.92 ≥ 0.9 → 候选 {Paris, London}，Berlin 与长尾「???」均被砍掉。

同一 Logits 下：低温压尖峰；Top-k 固定个数；Top-p 随分布自适应宽度——Agent 调工具参数宜「低温 + 偏低 Top-p」。

7. KV Cache

什么是 KV Cache？

KV Cache 是 Inference 时的加速手段：把历史 Token 已经算好的 Key（K）和 Value（V） 存起来，新 Token 只需算自己的 Query（Q）以及自己的 K、V，再与缓存中的 K、V 做 Attention。

第一篇 2.1 / 2.7 已指出：Causal Attention 下历史 K、V 不会因「未来 Token」而改变，因此可以缓存。本节把它放进完整推理链路里看。

7.1 为什么需要它

若每生成一个新 Token 都对整段序列从头算 Attention，历史部分会 重复计算。序列越长，浪费越大。

7.2 Prefill 与 Decode

带 KV Cache 的 Inference 常分成两阶段（读延迟相关资料时会遇到这两个词）：

阶段 做什么 特点
Prefill 一次吃进整段 Prompt（已有 Token），算出并写入整段 K、V 可并行算多 Token；决定 首 Token 前等待（常称 TTFT）
Decode 之后每步只追加 1 个新 Token，读缓存、写新的 K/V 基本串行；输出越长总耗时越长

因此：Prompt 很长 → Prefill 贵；回答很长 → Decode 步数多。Agent 堆历史与 Tool 结果，两边都会变慢。

7.3 与 Causal Attention 的关系

  1. 因果掩码：位置 t 看不到 t 之后 → 过去位置的表示在生成过程中可视为固定。
  2. 因此：过去的 K、V 算一次即可复用。
  3. 新 Token：追加到序列末尾，缓存长度随生成增长。

7.4 代价：显存

KV Cache 用 显存换时间：

  1. 层数越多、头数越多、Hidden 越大 → 每 Token 缓存越大。
  2. Context 越长（输入 + 已生成）→ 缓存越长。
  3. 并发请求越多 → 多份缓存同时占显存。

这与第一篇 Context Window、Attention O(n²) 的限制是同一类工程现实：长上下文不但算得慢，缓存也更贵。

7.5 对 Agent 的影响

Agent 多轮、多 Tool 结果 → 序列长 → Prefill / Decode / KV Cache 都更贵。优化仍回到第一篇的 Context 管理：压缩、摘要、检索、滑动窗口，从源头缩短参与 Attention 的 Token 数。

本模块自检与面试

总结

Inference：训练后的自回归生成；用 EOS / stop / max_tokens 结束；含 Prefill（吃 Prompt）与 Decode（逐步吐 Token）。

Logits / Softmax / LM Head：隐藏向量经 LM Head → Logits；Softmax 变成词表概率。

Decoding Strategy：Greedy 求稳（≈ Temperature→0）；Sampling 求活；Temperature、Top-k、Top-p 是常用旋钮。

Temperature：除以 $T$ 调分布锐度；Agent 工具调用宜偏低。

Top-k：只保留前 k 个再采样；候选数固定。

Top-p：按累积概率截「核」；候选数随把握程度变化，常与 Temperature 联用。

KV Cache：缓存历史 K、V 加速 Decode；省算力、耗显存；与 Context 长度强相关。
