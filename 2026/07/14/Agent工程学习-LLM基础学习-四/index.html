AI-Agent工程学习-LLM基础学习(四)

发表于 2026-07-14 更新于 2026-07-15 分类于 计算机
调用侧：Chat Completion、流式输出、多模态/VLM、结构化输出全套，以及 Tool Calling 从 Schema 到错误处理的闭环。

接第三篇：把消息送进 API，学会结构化输出与工具调用闭环

1. Chat Completion

什么是 Chat Completion？

Chat Completion（聊天补全）是现代 LLM 产品最常见的 调用入口：你提交一组带角色的 messages（以及可选的 tools、采样参数等），服务端做一次（或一轮内多次）Inference，返回 assistant 的回复（或工具调用意图）。

相对更早的「纯文本 Continuation / Completion」（给一段前缀往后补），Chat Completion 以 对话消息列表 为合同，便于多轮、system 约束与工具协议。

1.1 一次调用在做什么

对应：Context Window（第一篇） → Inference / Prefill·Decode（第二篇）。

与已学概念的对应：

  1. 每条 message 都经 Tokenization，占用 Context；输出受 max_tokens / EOS / stop 约束。
  2. 采样参数（Temperature、Top-p 等）仍作用在 Logits → Token 链上。
  3. 多轮不是模型「自己记得」，而是应用把历史 messages 再次提交（见第三篇消息角色）。

1.2 对 Agent 的影响

Agent 的「一步思考」往往就是一次 Chat Completion；调工具、读结果、再决策 = 多次 Completion 串起来。费用与延迟按次数与 Token 累加。

2. Message Role（复习与扩展）

system / user / assistant 的含义见第三篇第 1 节。本篇补上工具相关角色在多轮中的位置。

角色 谁写入 作用
system / user / assistant 应用 / 用户 / 模型（由应用回写） 普通对话
assistant（含 tool_calls） 模型经 API 返回，应用写入历史 声明要调哪些工具及参数
tool（或旧称 function） 应用在真实执行工具后写入 把 Tool Result / 错误送回模型

没有把 tool 消息写回 Context，模型就看不到工具结果，只能靠「猜」——这正是幻觉高发区（见第三篇 Hallucination）。

3. Streaming Output（流式输出）

什么是 Streaming？

Streaming（流式输出）指：Decode 每产生一些 Token（或 chunk），就通过网络推给客户端，而不是等整段生成完再一次性返回。

3.1 与 Prefill / 延迟的关系

观感 主要卡在
发出请求后迟迟不出第一个字 Prefill / TTFT（第三篇延迟名词；第二篇 Prefill）
第一个字出现后，文字一个个蹦出 Decode 逐步推进；Streaming 让用户提前看见

Streaming 不改变 模型算什么，只改变 结果何时送达。总 Token 数、Context 占用与非流式相同。

3.2 对 Agent 的影响

  1. 聊天 UI：流式体验好，用户感知延迟更低。
  2. 等完整 JSON / Tool 参数：往往要等流结束（或缓冲到可解析边界）再 JSON.parse / 执行工具；半截 JSON 不能当正式 Invocation。
  3. 需要严格结构化时：可非流式，或流式仅用于展示、工具路径仍等完整 chunk。

4. Multimodal Input 与 Vision-Language Model

4.1 Multimodal Input（多模态输入）

一次 Chat Completion 的 content 可以不只是纯文本，还可以包含 图像、音频 等（视模型与 API 而定）。消息里常见「文本块 + 图片块」的复合 content。

要点：

  1. 图片等也会被编码进模型可用的表示，并 占用 Context（计费单位因厂商而异，不一定按「一张图 = 固定 Token」的简单直觉）。
  2. 与第一篇 Tokenization「文本切分」不同：多模态另有视觉/音频侧处理，名词级只需知道 输入通道变多了。

4.2 Vision-Language Model（VLM）

VLM（视觉-语言模型）：能同时理解图像与文本、并生成文本（或再调工具）的模型。Chat + 看图问答、UI 截图理解、单据识别等，通常依赖 VLM 能力。

对 Agent：工具可以返回图片 URL / 截图，再作为多模态消息送回下一轮 Completion——Context 与费用会明显高于纯文本。

5. Structured Output（结构化输出）

第三篇第 4 节已给出「软→硬」总览。本节展开清单中的名词，并分清 模型侧约束 与 应用侧校验。

场景片段： 输入「提取订单号 A102，状态为已发货。」→ 输出 {"order_id":"A102","status":"shipped"}；应用再按 Schema 校验字段。

5.1 JSON Output

要求模型输出 JSON 文本（对象或数组），便于程序解析。实现路径包括：Prompt 约定、API 的 JSON Mode / response_format、或更强的 Schema 约束解码。

失败模式：不是合法 JSON、多余 markdown 代码围栏、尾部废话、字段缺失。

5.2 JSON Schema

JSON Schema 是描述「JSON 长什么样」的标准：类型、必填字段、枚举、嵌套结构等。用于：

  1. 告诉模型 / 约束解码器：只能生成符合该形状的内容。
  2. 告诉应用：如何校验、如何生成类型或表单。

Tool 的参数定义，在多数 API 里 就是一份 JSON Schema（见第 6 节 Tool Schema）。

5.3 Schema Validation（模式校验）

Schema Validation 发生在 应用侧：拿到模型字符串 → 解析 JSON → 用 JSON Schema（或等价规则）检查是否合法。

与「模型保证生成合法 JSON」不是同一件事：

约束解码 / JSON Mode Schema Validation
谁做 推理服务 / 解码器 你的后端 / Agent 运行时
何时 生成过程中 生成完成之后
失败时 尽量不生成非法 Token 拒绝、重试、或报错给上游

Agent 最佳实践：即使开了 JSON Mode，仍做 Validation——尤其是 Tool 参数、写库、调付费 API 之前。

5.4 Typed Output（类型化输出）

Typed Output 多指 SDK / 框架把「符合 Schema 的 JSON」再映射成语言里的 类型对象（如 TypeScript interface、Pydantic 模型）。名词级：Schema → 校验通过 → 得到类型安全的结构，供后续代码使用。

它不替代 Schema Validation，而是 Validation 之后的开发体验层。

5.5 层次关系（合看）

6. Tool Calling（工具调用）

Tool Calling 让模型在对话中 提出要调用的外部工具及参数，由 应用真实执行，再把结果写回消息列表继续推理。这是 Agent「能办事」的 API 基础能力。

6.1 Function Calling 与 Tool Calling

历史上不少文档称 Function Calling；现多称 Tool Calling。能力本质相同：模型不直接碰你的数据库/HTTP，而是输出结构化的「调用意图」。

本篇统一用 Tool Calling；读旧文看到 Function Calling，可视为同义。

6.2 Tool Schema

Tool Schema 描述「有哪些工具、干什么、参数是什么」，通常包括：

  1. name：工具标识（模型用来点名）。
  2. description：自然语言说明；影响模型是否选对工具。
  3. parameters：多为 JSON Schema（类型、必填项、枚举等）。

Schema 写得含糊（描述不清、缺必填、同名冲突）→ 选错工具或参数幻觉（见第三篇）。

6.3 Tool Invocation（工具调用意图）

Tool Invocation = 模型在某次 Completion 中返回的「请执行：工具名 + 参数」。

注意：

  1. 此时工具 尚未执行；只是 assistant 消息里的结构化意图（常伴 tool_calls 一类字段）。
  2. 参数应先做 Schema Validation，再执行。
  3. 一次回复可能包含 多个 Invocation（并行调多个工具），视 API 与编排策略而定。

6.4 Tool Result（工具结果）

应用执行成功后，把结果写成 tool（或 function）角色消息，内容多为文本或 JSON 字符串，并带上对应调用的 id，以便模型对齐「这是哪一次调用的返回」。

Result 会进入 Context，占用 Token；过大时需截断或摘要（第一篇 Context 管理）。

6.5 Tool Error Handling（工具错误处理）

工具会失败：超时、4xx/5xx、权限不足、参数合法但业务拒绝等。处理原则：

  1. 把错误写回 tool 消息（明确错误类型与可行动信息），让模型有机会改参或换工具——不要静默吞掉。
  2. 不要把错误当成功：禁止伪造「已完成」的 Result；那会放大幻觉。
  3. 重试策略在应用层：可重试的瞬时错误 vs 不可重试的参数错误；限制次数，避免死循环烧 Token。
  4. 降级：连续失败则向用户说明、或走人工/默认路径，而不是无限 Completion。

与 Structured Output 的关系：Invocation 的参数用 Schema Validation；Result / Error 的格式也建议固定，便于下一轮模型与日志解析。

6.6 对 Agent 的影响

没有可靠的 Schema、Validation 与 Error Handling，Agent 只是「会说话的脚本」；有了闭环，才进入可编排的系统（见 Agent 基础（一）：ReAct、规划、记忆等）。

7. 调用韧性（Agent 相关）

协议闭环之外，生产 Agent 还会碰到 并行工具、缓存、API 限流。认名即可；Skills/MCP 见 Agent 基础（六）。

7.1 并行 Tool Calls

现代 API 允许 一轮 Completion 返回多个 Tool Invocation（彼此无依赖时）。

工程要点：

  1. Result 写回顺序：建议固定（如按 tool_call_id），便于日志与模型对齐。
  2. State 合并：多个 Observation 同时进入 Trace；Working state 要记录「哪些子动作已完成」。
  3. 部分失败：A 成功、B 超时——分别写回 Error，不要整轮当成功（回链 Agent 一 · Loop）。

7.2 Prompt Caching（前缀缓存，认名）

部分厂商对 重复前缀（相同 system、稳定工具目录）缓存 KV，降低 Prefill 成本与延迟。

区段 典型内容 是否宜缓存
稳定前缀 system 硬规则、L0 工具/Skill 目录 宜保持稳定
易变后缀 用户消息、Trace、Tool Result 每轮变化

与 Agent 五 · 压缩 呼应：长任务优先 追加摘要 + 滑动丢原文，少无差别重写整段历史，以免打穿缓存。

7.3 API 限流与重试

与 §6.5 业务工具错误 分层：

层 典型错误 策略
API 层 429 限流、5xx 网关 指数退避、上限次数、换区域/模型（若有）
业务工具层 参数错、权限不足 写回 tool Error，让模型改参或换工具

原则：API 重试在 HTTP 客户端；工具重试在 Runtime，且区分可重试瞬时错误与不可重试逻辑错误（Agent 三 · 工具治理）。

场景片段： 第一次请求返回 429 → 等待 1 秒 → 第二次仍为 429 → 等待 2 秒；第三次成功则返回结果；权限错误 403 不做同类重试。

总结

Chat Completion：以 messages 为合同的主调用入口；一次调用 ≈ 一次（轮）Inference。

Message Role：在第三篇三角色之上，用 tool 消息承载执行结果。

Streaming：边 Decode 边推送；改善 TTFT 之后的体感；结构化/工具路径常需等完整再解析。

Multimodal / VLM：输入可含图等；VLM 能看图说话；Context 与费用更贵。

Structured Output：JSON Output → JSON Schema →（模型侧约束）→ Schema Validation → Typed Output；校验在应用侧不可省。

Tool Calling（含旧称 Function Calling）：Tool Schema → Invocation → 应用执行 → Result/Error 写回 → 再 Completion。

调用韧性：并行 Tool Calls、Prompt Caching 稳定前缀、API 限流与退避；与业务工具错误分层处理。
