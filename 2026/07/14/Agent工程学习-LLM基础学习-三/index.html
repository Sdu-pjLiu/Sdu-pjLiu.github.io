AI-Agent工程学习-LLM基础学习(三)

发表于 2026-07-14 更新于 2026-07-15 分类于 计算机
模型侧认名收口：消息角色、Pretrain/SFT/RLHF、指令遵循与幻觉、结构化输出总览、延迟名词；调用侧见第四篇。

接第一篇、第二篇：补齐读模型说明时常碰到的认名概念（调用侧见第四篇）

1. 消息角色（Message Roles）

什么是消息角色？

Chat 类 API 通常不把整段对话当成「一大坨纯文本」，而是拆成带 role 的消息列表。模型按对话模板理解：谁在说、该听谁的约束。

常见三种：

角色 含义 典型内容
system 系统 / 开发者设定 人设、硬规则、输出格式、安全边界
user 用户 当前问题、任务、附件说明
assistant 模型自己的历史回复 上一轮回答；多轮时由应用写回

部分协议还有 tool / function 角色（把工具执行结果写回对话）。其在 Chat Completion 多轮中的位置、与 Tool Schema / Invocation 的关系，见第四篇。

1.1 与 Context Window 的关系

每一条消息经 Tokenization 后都占用 Context（见第一篇第 5 节）。多轮对话 = 把历史 user / assistant（有时还有 system）再次送进同一次 Inference。

对应：Context Window（第一篇） → Inference（第二篇）。

1.2 对 Agent 的影响

  1. 规则放 system：工具用法、禁止事项、输出契约，优先放 system，减少每轮重复堆在 user 里（仍占 Token，但职责更清晰）。system 是 工程优先级，不是绝对鉴权——关键动作仍靠 Runtime。
  2. Chat Template（对话模板）：开源 / 本地部署时，各模型有自己的 special tokens 与角色序列化格式（Jinja chat template）。模板错、缺角色标记，常表现为「不听话」——与 Prompt 写得好坏无关。托管 Chat API 通常已替你套好模板。
  3. 知识截止日期（knowledge cutoff）：参数内知识有训练截止日；过新事实必须靠 Tool / RAG，否则易幻觉。
  4. 历史要裁剪：轮数一多就触碰 Context 上限，需摘要 / 滑动窗口（第一篇 5.7）。
  5. 不要假设模型「真的记住」：没有写入本次消息列表的内容，本轮 Inference 看不见。

2. 训练阶段认名：Pretrain / SFT / RLHF

读模型卡、技术报告时，常按阶段描述「这个模型怎么来的」。名词级只需分清目的，不必会训。

2.1 Pretrain（预训练）

在大规模语料上做 下一 Token 预测（与第二篇自回归同一目标），学会语言与世界知识的统计规律。产物多为 基座模型（Base）：补全能力强，但不一定「听话聊天」。

2.2 SFT（Supervised Fine-Tuning，监督微调）

用「指令 → 优质回答」等高质量示范数据继续训练，让模型学会 按指令行事、对话格式、助手口吻。Chat 模型多经过 SFT。第二篇 Inference表里的「SFT」即指这一阶段。

2.3 RLHF / Alignment（对齐，认名即可）

RLHF（Reinforcement Learning from Human Feedback） 等：用人类（或 AI）偏好信号，进一步让输出更符合「有用、无害、诚实」等目标。还有 DPO 等同类思想的不同算法，产品文案里常统称 Alignment（对齐）。

和 Agent 的关系：你调的几乎都是对齐后的 Chat 模型；Base 模型一般不适合直接当 Agent 大脑。对齐不能消灭幻觉，只能降低某些不良行为概率。

3. Instruction Following 与 Hallucination

3.1 Instruction Following（指令遵循）

指模型 按你的约束执行 的能力：格式、步骤、语言、禁止事项、工具调用约定等。

影响因素（与已学概念的联系）：

  1. 模型是否经过 SFT / 对齐（本节第 2 节）。
  2. Prompt / system 是否写清（消息角色）。
  3. Temperature 等是否过「活」（第二篇）：工具参数、JSON 宜低温。
  4. Context 是否被挤爆或 Lost in the Middle（第一篇）：关键指令被淹没会「听不见」。

3.2 Hallucination（幻觉）

模型生成了 听起来合理、但事实错误或无依据 的内容：编造引用、假 API 字段、不存在的论文等。

要点：

  1. 本质仍是「选下一个高概率 Token」，不是在查真伪数据库（除非你接了检索 / 工具）。
  2. RAG、工具调用、要求引用原文 是工程上降幻觉的主手段，不是把 Temperature 调到 0 就万事大吉（低温只更稳，不保证真）。
  3. Agent 场景：幻觉常表现为 捏造工具参数、假路径、假 ID——必须校验工具返回，不能盲信模型自述「已完成」。
Instruction Following Hallucination
问的是 听不听指令、守不守格式 内容是否属实、有无依据
失败表现 漏字段、不按步骤、忽略 system 言之凿凿的假信息

4. 结构化输出与约束解码（总览）

Agent 经常要模型输出 可解析的结构（JSON、XML、特定 schema），而不是无固定字段的自由文本。约束由软到硬大致三层：

  1. Prompt 约束：在 system / user 里写清格式并给示例，配合低温；偶发漏括号、多废话。
  2. JSON Mode / response_format：API 要求输出合法 JSON；仍可能不符合业务字段。
  3. Schema / Guided Decoding：生成时只允许符合语法或 JSON Schema 的 Token；更适合严格表单与 Tool 参数。

与第二篇关系：约束作用在解码可选 Token 集合上，和 Top-k / Top-p「截断候选」同一类思想。

展开：JSON Output、JSON Schema、Schema Validation、Typed Output，以及它们与 Tool 参数的关系，见第四篇 Structured Output。本篇只建立「软→硬」心智模型即可。

5. 延迟与吞吐相关名词（可选）

部署或读性能文档时常见：

名词 含义
Latency 一次请求的耗时（需说明是首字还是整段）。
TTFT（Time To First Token） 发出请求到收到 第一个 输出 Token 的时间；与 Prefill 强相关（第二篇 7.2）。
Throughput 单位时间处理量（如 tokens/s、请求数/s）。
Batch 多条请求一起算，提高吞吐，可能增加单请求等待。

Agent 体感：工具多、轮次多 → 多次 Inference 叠加；历史长 → Prefill / TTFT 变差。优化仍优先减 Context、减轮次，而不是先调采样参数。

场景片段： 输入 20K Token 文档；2.4 秒后出现首字，8 秒后完成回答 → TTFT = 2.4 秒，整请求 Latency = 8 秒。

6. 部署与成本认名（可选）

读模型卡、选部署形态或控 Agent 费用时常见（认名即可，不展开训练）：

名词 含义
MoE（Mixture of Experts） 按 Token 路由到部分「专家」子网络；影响延迟与计费体感，不等于「参数量越大一定越慢」。
量化（Quantization） 用更低精度存算权重（如 INT8/FP8）；降显存与成本，可能损精度。
模型路由 / 级联 小模型分流简单请求，大模型攻坚难例；与 Agent Budget、Loop Engineering 双层预算 同一类成本治理。

计费口径（Agent 预算必知）： 多数 API 输入 Token 与输出 Token 单价不同（输出通常更贵）；带 Prompt Caching 时，cached input 往往更便宜。估 Agent 成本时不要只乘「总 Token × 一个均价」。

场景片段： 100 个客服问题中 90 个为常见问答、10 个需复杂推理 → 路由输出：90 个交小模型，10 个升级到大模型。

调用侧已学：Prompt Caching（前缀缓存）、API 限流与重试见第四篇 §7。

总结（模型侧收口）

本篇（模型 / 产品认名）：

  • 消息角色：system / user / assistant 构成 Chat Context；tool 角色见第四篇。
  • Pretrain → SFT → RLHF/对齐：基座会补全，Chat 模型更听话；对齐 ≠ 无幻觉。
  • Instruction Following / Hallucination：听指令 vs 内容是否属实。
  • 结构化输出：仅总览软→硬三层；细节见第四篇。
  • TTFT / Prefill / Decode / Throughput：用来读懂「为什么慢」。
  • MoE / 量化 / 模型路由：部署与成本认名；调用韧性见第四篇。
